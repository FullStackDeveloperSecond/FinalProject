## 更改內容

### 摘要

新增管理員登入（帳密＋TOTP 兩階段、首次登入強制綁定 TOTP、Recovery Code）、管理員自行重新綁定 TOTP（完成 Session 撤銷情境的觸發入口）與後台會員管理（列表＋會員中心）的前後端實作。過程中發現並修正 6 個新程式碼本身的 bug，以及 2 個既有但從未被實際觸發過的環境/pipeline 問題（CORS 中介軟體順序、Development 環境 HTTPS 轉址）。所有變更皆以真實瀏覽器操作＋curl 對真實資料庫驗證過，含直接改資料庫驗證 Session 撤銷機制，尚未寫成自動化測試。

### 新增

- 後端 `DoSelect.Api/Admin/Auth/AdminAuthController.cs`：`GET session`、`POST login`、`POST logout`⚠、`POST totp/verify`、`POST recovery-codes/use`、`POST totp/enroll/begin`⚠、`POST totp/enroll/confirm`⚠、`POST totp/rebind/begin`⚠、`POST totp/rebind/confirm`⚠（⚠ = 規格 4 端點以外新增，見下方清單）。`totp/rebind/*` 是已登入管理員自行換裝置用的，完成 UC-ADMIN-AUTH-01「TOTP 重新綁定使既有 Session 失效」情境的實際觸發入口——確認新碼後會 bump SecurityStamp、撤銷其他所有裝置的既有登入，並用新 Stamp 重新簽發「這次操作」所在的 Session（不會把自己登出）。
- 後端 `DoSelect.Api/Admin/Members/AdminMembersController.cs`：`GET /api/v1/admin/members`、`GET/PUT /api/v1/admin/members/{publicId}`、`POST .../reset-password`、`POST .../status`（⚠ 全新範圍，無既有規格）。
- 後端 `DoSelect.Application/Security/*`：`AdminLoginUseCase`、`AdminTwoFactorUseCase`、`IAdminAuthGateway`、`ITotpQrCodeGenerator`、`EmailMasking`、`LocaleCodes`。
- 後端 `DoSelect.Application/Members/*`：`IAdminMemberQueryReader`、`IAdminMemberWriter`、`IAdminMemberPasswordResetInitiator`、對應 UseCase。
- 後端 `DoSelect.Infrastructure/Security/*`：`IdentityAdminAuthGateway`（一律透過既有 `UserManager`/`AspNetUserTokens`，未新增資料表）、`QrCodeGenerator`（⚠ 新套件 QRCoder 1.6.0）。
- 後端 `DoSelect.Infrastructure/Members/*`：`AdminMemberQueryReader`、`AdminMemberWriter`、`AdminMemberPasswordResetInitiator`。
- 新 Policy：`Member.Manage`、`Member.ManageSensitive`（⚠ 新提案，待 alex 核准）。
- 新 Cookie Scheme：`DoSelect.AdminChallenge`（⚠ 代表「密碼已驗證、2FA 尚未完成」的短效憑證，取代新建資料表）。
- 前端 `admin-web/src/features/auth/*`：`LoginPage`、`TotpVerifyPage`、`TotpEnrollPage`、`TotpRebindPage`（⚠ 新頁面，`/security/totp-rebind`，header 有連結）、`useAdminAuthStore`。

### 修改

- `SecurityServiceCollectionExtensions.cs`：⚠ Admin Cookie 新增 `OnValidatePrincipal`（SecurityStamp 撤銷檢查，沒有 claim 就放行，避免打壞既有測試）；新增 `AdminChallenge` Cookie 註冊；新增 `Member.Manage`/`Member.ManageSensitive` Policy。
- `SecurityController.cs`：antiforgery-token 端點維持原行為（曾嘗試 fallback 到 AdminChallenge scheme，發現會被殘留 Cookie 干擾，已還原）。
- `PersistenceServiceCollectionExtensions.cs`：`AddIdentityCore` 加 `Lockout.MaxFailedAccessAttempts = 5`；不在此處呼叫 `AddDefaultTokenProviders()`（見下方套件影響）。
- `Program.cs`：⚠ `UseCors` 移到 `UseHttpsRedirection` 之前，且 `UseHttpsRedirection` 只在非 Development 套用（既有 pipeline 排序問題，這次第一次真的從瀏覽器打 API 才浮現，詳見下方風險章節）。
- `DoSelect.Infrastructure.csproj`：新增 `FrameworkReference Microsoft.AspNetCore.App`（`AddDefaultTokenProviders()` 需要，僅在 `AddDoSelectAdminAuth()` 呼叫，不影響純單元測試專案）。
- `AdminAuthPorts.cs`：`IAdminAuthGateway` 新增 `ResetAuthenticatorSecretAsync`（無條件重設，跟既有 `GetOrCreateAuthenticatorSecretAsync` 不同——後者有既有秘鑰就直接沿用）。
- `AdminTwoFactorUseCase.cs`：新增 `BeginRebindAsync`／`ConfirmRebindAsync`。
- `IdentityAdminAuthGateway.cs`：實作 `ResetAuthenticatorSecretAsync`。
- `AdminAuthController.cs`：新增 `RequireCurrentAdminUserId()` 私有方法；`totp/rebind/confirm` 成功後呼叫 `UserManager.UpdateSecurityStampAsync` 撤銷其他既有 Session，並記錄一筆 `logger.LogWarning` 作為稽核替代（目前沒有 AuditLogs 資料表）。

### 必須維持的規則

- 密碼、TOTP 秘鑰、Recovery Code 一律不落地明文，全部透過 `UserManager` 既有機制存取（`AspNetUserTokens`）。
- 會員 PublicId 對外，內部 `bigint Id` 不外洩。
- `AdminMemberDetailDto` 刻意不含性別／會員等級欄位（資料庫沒有對應欄位，非漏做）。

### 禁止或不建議的取用方式

- 不可由前端直接存取資料庫。
- 不可跨模組直接操作其他模組的 Repository 或資料表。
- 不可對外暴露資料庫內部 `bigint Id`；對外識別使用 `PublicId`。
- 其他：不要用 `[Authorize(AuthenticationSchemes = AdminChallenge)]` 保護新端點——會跟 antiforgery token 的身分綁定機制衝突（見風險章節）；請沿用本次 `RequireChallengeAsync` 的手動驗證模式。

## 相容性、風險與注意事項

- 相容性影響：`Program.cs` 的 `UseCors`/`UseHttpsRedirection` 順序調整、Development 停用 HTTPS 轉址，影響所有從瀏覽器呼叫 API 的既有與未來前端功能（正面修正，過去從未被實際驗證過，因為在此之前沒有任何前端真的用瀏覽器打過 API）。
- 已知風險（⚠ 全部待 alex 覆核）：
  1. Admin Cookie `OnValidatePrincipal` 撤銷檢查——沒有 SecurityStamp claim 的 Cookie（例如既有測試用的假身分）會略過檢查而非拒絕，是為了不打壞既有管理端整合測試的取捨。
  2. 新增 `Member.Manage`/`Member.ManageSensitive` Policy，角色對應是合理猜測（比照 `SupportTicket.Handle`/`Supervise`），非既有核准規則。
  3. 會員個資欄位（Email/電話/生日/訂單紀錄）沿用一般後台可見層級，未套用既有 `PersonalData.ViewFull`——此判斷待確認是否要收緊。
  4. 會員統計數字（總消費金額/總訂單數/退貨率）口徑為新提案（見程式註解），非既有規則。
  5. ~~管理員登入沒有「重新綁定/解除 TOTP」端點~~ 本輪已補上 `totp/rebind/begin`／`totp/rebind/confirm`，Session 撤銷情境已有實際觸發入口，見下方測試紀錄。
  6. `TotpRebindPage.vue` 原本一進頁面就自動呼叫重設金鑰，測試過程中證實太容易被誤觸發（見下方意外事件），已改成需要先按「開始重新綁定」按鈕才會真的呼叫後端。
- 開發過程中的真實意外事件（已排除、記錄供交接參考）：
  - 測試 `totp/rebind` 期間，`beginRebind()` 在還沒設計成需要手動確認前，疑似因瀏覽器分頁/HMR/導覽的某種時序意外執行，導致種子管理員 `admin@doselect.local` 的 TOTP 秘鑰在使用者不知情下被重設（`ResetAuthenticatorKeyAsync` 執行、但因為沒有走完 `ConfirmRebindAsync` 所以 Recovery Code 沒有跟著重新產生）。這件事本身間接證明了 `ResetAuthenticatorSecretAsync`／SecurityStamp 撤銷機制確實有效，但也凸顯「一進頁面就呼叫有副作用的端點」的設計風險，已於本輪加上明確按鈕確認來源頭修正。
  - 使用者在 Chrome（含無痕模式）測試登入的 TOTP 驗證表單時，點擊/Enter 都無法送出（開發者工具 Console 無錯誤），改用 Microsoft Edge 後恢復正常；研判是 Chrome 端某擴充套件或原生政策攔截了這個 `<form>` 的送出事件，非本應用程式的程式碼問題。交接時若有人遇到類似「表單按鈕看似沒反應」的回報，建議先請對方換瀏覽器排除。
- 回復方式：全部為新增檔案／新增 Policy／pipeline 排序調整，無資料庫異動，可直接 revert 相關檔案復原。
- 需要其他負責人配合：alex 覆核上述⚠清單；yinyin 覆核功能與流程。
