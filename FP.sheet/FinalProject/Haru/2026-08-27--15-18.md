## 尚待裁定或外部依賴

### 1. 平行重寄 successor 識別碰撞

目前 successor lookup 使用 `(EmailHash, OrderHash, ExpiresAtUtc)`；`ExpiresAtUtc` 在 SQL Server 為毫秒精度。相同訂單與 Email 若在同一毫秒建立兩條獨立 challenge chain，平行重寄輸家可能取到另一條 chain 的 Request ID。

- 建議：不新增 migration，改為重寄時更新原 challenge，並以同交易的獨立限流事件列計數，移除 successor lookup。
- 替代：新增 self-FK／chain relationship migration，成本與部署風險較高。
- 不建議直接接受：此情境可達，會回傳錯誤 challenge ID。

### 2. 中央 Outbox 尚未完成

正式規格要求核心資料、Audit、Outbox 在同一 SQL transaction，commit 後由 dispatcher 寄信。目前仍是 DB commit 後排入記憶體 email queue；服務在兩者之間中止時，可能留下有效 challenge 但沒有可恢復的寄信事件。此項需等待中央 Outbox 基礎能力完成，再做最終整合與驗證。
