## 共通欄位基線

| 概念 | 建議欄位 | 規則狀態 |
|---|---|---|
| 主鍵 | `Id` | `bigint identity`；內部使用 |
| 公開識別 | `PublicId` | Application 產生 UUID v7；`uniqueidentifier`＋非叢集唯一索引 |
| 建立時間 | `CreatedAtUtc` | UTC、`datetime2(3)`、必填 |
| 修改時間 | `UpdatedAtUtc` | UTC、`datetime2(3)`；不可修改資料可省略 |
| 軟刪除 | `DeletedAtUtc`／狀態欄位 | 僅適用已確認可軟刪除資料，不可全面套用 |
| 併發 | `RowVersion` | 用於後台可編輯且有覆寫風險的資源 |
| 顯示排序 | `SortOrder` | 只有人工可排序資料使用 |
| 外部識別 | `ExternalReference` | 付款、物流等模擬 Provider 需唯一或具範圍唯一 |
| 冪等 | `IdempotencyKey` | 建立訂單、付款／退款通知等高風險命令 |

## 索引與資料完整性檢查

- 所有 FK 必須明確決定刪除行為，不使用未審核的 Cascade Delete。
- 搜尋、列表、報表、庫存保留、SLA 到期及背景清理查詢需依實際查詢建立複合索引。
- 唯一性若只適用有效資料，需評估 SQL Server Filtered Unique Index。
- 金額使用適當的 `decimal`，不得使用 `float`／`real`。
- 新台幣金額採 `decimal(18,2)`；百分比／折扣率採 `decimal(9,6)`；數量採 `int`。
- 日期時間使用 UTC `datetime2(3)`；需保存外部原始時區偏移時才使用 `datetimeoffset(3)`。
- RowVersion 使用 SQL Server `rowversion` 並對應 EF Core Concurrency Token。
- 敏感欄位不得進入一般全文搜尋、Log 或稽核差異全文。
- Email 最長 320、電話 32、姓名 100、Code 64、標題 200、URL 2048、一般說明 4000；超長內容必須使用用途明確的欄位，不全面使用 `nvarchar(max)`。
- 所有 FK 預設 Restrict；只有 Aggregate 內沒有獨立生命週期的 Owned Detail 可 Cascade。
- Constraint／Index 採 `IX_{Table}_{Columns}`、`UX_{Table}_{Columns}`、`FK_{Child}_{Parent}_{Column}`、`CK_{Table}_{Rule}`；所有 FK 先建立索引，再依實際查詢調整複合順序。
- 一般字串輸入 Trim＋Unicode NFKC；Email 使用 Identity NormalizedEmail；系統 Code 使用正規化大寫欄位與不分大小寫唯一索引。
- 只限制有效資料的唯一性使用 SQL Server Filtered Unique Index；軟刪除資料仍保留歷史。
- PublicId 適用 Member、Admin、Product、Sku、Order、Payment、Shipment、Return、Refund、SupportTicket、ReportCase、BuildList、分享連結、圖片與附件等所有對外資源。
- PublicId API 統一小寫 Guid `D` 格式；只有具獨立 Route、稽核或生命週期的 Join Entity 配置 PublicId。
- Cascade 白名單為 CartItem、BuildListItem、ImportRow；未列關聯一律 Restrict。
- Owner／Assignee 使用一般 Identity FK；append-only History 的 Actor FK 可為 Null。Identity 有交易依賴時不實體刪除，以停權、軟刪除或匿名化維持參照完整性。
- V1 InventoryReservation 僅以 OrderId 建立；不得加入 CartId。ReturnShipment 為退貨領域獨立 Aggregate，不重用 outbound Shipment。

## 正規化審核欄位

每張表除欄位定義外，還必須標示：

| 項目 | 必填說明 |
|---|---|
| 真實來源 | 哪張表／哪個 Aggregate 可以寫入此資料 |
| 正規化理由 | 主資料、關聯、明細或歷程如何避免更新／插入／刪除異常 |
| 重複資料分類 | `none`、`transaction_snapshot`、`derived_balance`、`read_projection`、`report_aggregate` |
| 同步方式 | 同交易、Outbox、背景重建或查詢時計算 |
| 允許延遲 | 必須強一致，或可接受的最長延遲 |
| 重建來源 | 反正規化資料損壞時由何種正規化資料重建 |
| 防漂移驗證 | Constraint、整合測試、核對工作或管理報表 |

詳見 [[03-架構/03-資料與一致性/資料庫正規化與反正規化策略]]。

## EF Core 實作審核

- 逐表欄位、保留／刪除、附件 StorageKey、AI／匯入來源、One-of Constraint、PublicId 與反正規化分類已分散在三份領域資料字典定版。
- 建立 Entity／Fluent Mapping 後，仍須在 Migration Review 比對型別、Null、Default、FK、Filtered Index、RowVersion、Check Constraint 與 Cascade 白名單。
- Migration 產生結果若與本資料字典不同，不得以「EF Core 自動產生」視為合理；必須修改 Mapping 或建立新的設計決策。
