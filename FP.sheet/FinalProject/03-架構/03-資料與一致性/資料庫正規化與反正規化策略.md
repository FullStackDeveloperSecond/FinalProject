# 資料庫正規化與反正規化策略

本文件規範 SQL Server／EF Core 資料模型如何避免重複真實來源，同時保留電商交易所需的歷史快照與高頻讀取投影。它不代表所有資料都必須拆到最細，也不授權在沒有量測與一致性設計時新增快取表。

## 目標

1. 可變主資料只有一個可寫真實來源，避免更新、插入及刪除異常。
2. 關聯、明細、狀態歷程與多值資料使用明確資料表及 FK，不藏在逗號字串或任意 JSON。
3. 歷史交易在主資料日後變更時仍能還原當時的名稱、價格、成本、折扣、政策與收件資訊。
4. 任何反正規化欄位都能說明來源、同步、延遲、重建及驗證方式。
5. 先以正規化查詢與正確索引達到 10,000 筆展示資料門檻；量測不足才評估額外讀取模型。

## 正規化基線

交易寫入模型以第三正規化形式作為審核基線：

- 每張表代表一種清楚的 Entity、Value／Owned Detail、關聯或不可變歷程。
- 非鍵欄位依賴該表的完整鍵，不依賴另一個非鍵欄位。
- 品牌、分類、角色、物流方式、規格定義等重複概念使用 FK，不在多張可寫表重複保存名稱作目前值。
- 多對多關聯使用 Join Table；需要排序、建立時間或狀態時，Join Table 視為具屬性的 Entity。
- Product 與 SKU 分工固定：Product 保存共用資訊，SKU 是售價、庫存、可售狀態及規格值的實際單位。
- 狀態歷程與稽核紀錄不可塞進目前狀態欄位；目前狀態供快速判斷，歷程表保存每次合法轉移。
- 欄位若可由同一交易模型穩定計算，預設不再建立可人工編輯的副本。
- `SkuSpecificationValue` 使用互斥型別欄位與 Check Constraint；核心規格值不以任意 JSON 取代。
- 多對多關聯一律使用明確 Join Entity；需要排序、狀態或建立者時直接成為 Join Entity 欄位。

## 已核准的受控反正規化

| 類型 | 例子 | 為何允許 | 一致性規則 |
|---|---|---|---|
| 交易快照 | `OrderItem` 商品／SKU 名稱、單價、成本、折扣分攤；Order 收件、運費、政策版本 | 必須還原交易成立時的法律與商業事實 | 訂單建立交易內寫入，成立後不可由目前主資料覆寫 |
| 衍生餘額 | `InventoryBalance` 的 OnHand／Reserved／Available | 結帳需要高頻、原子條件更新 | 與 `InventoryMovement`／Reservation 同交易更新；提供核對與調整流程 |
| 唯讀工作台投影 | SupportTicket、ReportCase、ReturnRequest 的共同注意等級、期限、建立時間 | 後台需要跨領域一致排序 | 原領域仍是唯一寫入來源；投影不可接受跨領域通用寫入 |
| 顯示摘要 | 訂單主要摘要狀態與徽章 | 簡化前端顯示與篩選 | 優先查詢時計算；若日後實體化，必須由五個正式狀態推導並可重建 |
| 報表讀取模型 | `ReportSnapshot`／預彙總候選 | 只有量測證明即時查詢未達 P95 才需要 | 第一版預設不建立；需定義刷新、延遲、重建、版本及失敗降級 |

- 統一案件工作台第一版採 SQL `UNION ALL` View＋EF Core Keyless Entity，不持久化重複案件資料。
- 訂單主要摘要狀態第一版在查詢時推導，不保存第二份可寫狀態。
- 七個報表以交易表與索引實作；只有個別報表在查詢優化後仍超過 P95 3 秒，才建立新的反正規化決策。
- 任何 Report Snapshot 必須保存 `AsOfUtc`、來源版本與重建狀態，畫面標示資料時間。

## 不允許的重複

- Product 與預設 SKU 各保存一套可獨立修改的售價或庫存。
- 訂單只保存目前 Product／SKU FK，卻在查詢時用最新名稱或價格回推歷史。
- 在 Order 上另存可任意修改且取代正式狀態機的摘要狀態。
- 在會員、訂單、客服等多表複製 Email／姓名作目前主資料，卻沒有快照目的與匿名化規則。
- 以 CSV 字串保存角色、標籤、規格集合、訂單明細、物流歷程或退款分攤。
- 為了少寫 Join 而把可查詢、需索引或具完整性規則的核心資料放入任意 JSON。
- 由多個 Service 各自更新同一個衍生數字，且沒有單一 Application Use Case、交易或重建來源。

## JSON 與結構化欄位邊界

- 相容性、搜尋、價格、庫存、退款、授權與報表篩選需要的欄位必須結構化並可驗證、索引。
- AI 原始安全回應摘要、外部模擬事件的非關鍵除錯片段可評估 JSON，但不得取代正式狀態、金額或識別欄位。
- 使用 JSON 前必須記錄 Schema Version、最大長度、是否含個資、查詢需求與保存期限。
- 若資料需要 FK、Unique、Check Constraint、範圍查詢或高頻篩選，優先拆成關聯欄位／資料表。

## 反正規化核准條件

新增重複欄位、投影表、快取表或報表彙總前，必須在 PR／設計紀錄回答：

1. 目前正規化查詢在代表性資料與索引下的量測結果是什麼？
2. 唯一可寫真實來源是哪一個 Aggregate／資料表？
3. 副本由同交易、Outbox、Hangfire 或查詢時計算中的哪一種方式更新？
4. 可接受的一致性延遲與使用者可見影響為何？
5. 更新失敗、重複事件或順序顛倒如何處理？
6. 如何由真實來源完整重建？重建期間如何降級？
7. 有哪些 Constraint、核對查詢與自動化測試防止資料漂移？
8. 刪除、匿名化、備份與還原如何同步處理所有副本？

沒有上述答案時，維持正規化查詢，不先建立副本。

## EF Core 與 SQL Server 實作要求

- 關聯由 Fluent API 明確設定 FK、Required／Optional、DeleteBehavior、Unique／Filtered Index 與精度，不完全依賴慣例。
- FK 預設 Restrict；只有沒有獨立生命週期的 Owned Detail 可 Cascade。
- 所有受控反正規化寫入由 Application Use Case 協調；Controller、Vue 或背景 Job 不得繞過同一規則直接拼裝資料。
- 庫存、訂單、退款等強一致資料在同一 SQL Server 交易完成；跨交易投影使用 Outbox／冪等工作。
- 對可重建投影保存 `SourceVersion`、`UpdatedAtUtc` 或等價版本資訊，避免舊事件覆蓋新資料。
- Migration 新增反正規化欄位時，必須提供 Backfill、驗證、切換與必要 Roll-forward 策略。
- 所有對外資源使用 Application 產生的 UUID v7 PublicId 與非叢集唯一索引；內部 `bigint identity` 維持叢集主鍵。
- 一般文字 Trim＋Unicode NFKC；Email 交由 Identity 正規化；系統 Code 正規化為大寫並以不分大小寫唯一索引限制。

## 測試與驗收

- 正規化關聯：FK、Unique、Check Constraint 與刪除行為整合測試。
- 交易快照：修改目前商品、優惠、地址或政策後，歷史訂單仍顯示成立時內容。
- 庫存餘額：Movement／Reservation／Balance 核對，並涵蓋併發、重試及失敗回滾。
- 工作台投影：三領域資料能重建相同排序，且投影授權不擴張寫入權限。
- 報表／快取：與交易真實來源對帳，涵蓋刷新失敗、重建與過期資料標示。
- 匿名化與刪除：所有受控副本一起處理，不留下無文件記錄的個資副本。
