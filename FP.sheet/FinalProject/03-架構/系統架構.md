# 系統架構

狀態：部分已確認

## 系統組成

```text
Vue 消費者前台 ─┐
                 ├─ ASP.NET Core Web API
Vue 管理後台 ───┘          ↓
                       Application
                            ↓
                          Domain
                            ↑
                      Infrastructure
                            ↓
                  EF Core / SQL Server
```

採前後端分離與模組化單體，不在第一版拆成微服務。

## 建議專案結構

```text
src/backend/
├─ DoSelect.Api/
├─ DoSelect.Application/
├─ DoSelect.Domain/
└─ DoSelect.Infrastructure/

frontend/
├─ customer-web/
└─ admin-web/

tests/
├─ DoSelect.Domain.Tests/
├─ DoSelect.Application.Tests/
├─ DoSelect.Infrastructure.Tests/
└─ DoSelect.Api.IntegrationTests/
```

品牌正式名稱為 `DoSelect 懂選`，Solution 與根 Namespace 統一使用 `DoSelect`。消費者前台與管理後台資料夾分別固定為 `customer-web`、`admin-web`。

## 後端責任

### API

- HTTP Request／Response。
- Authentication 與 Authorization。
- API Contracts。
- 輸入格式驗證。
- CORS。
- 全域例外處理。
- OpenAPI 文件。
- 呼叫 Application Use Case。

Cookie Scheme、CORS、CSRF、分頁、Problem Details、冪等性與併發規範統一記錄於 [[03-架構/API共通規範]]。
M 功能的候選路由、權限與 DTO 對照記錄於 [[03-架構/API Endpoint目錄]]；完整 OpenAPI Schema 尚未定版。

### Application

- 使用案例與流程協調。
- DTO、Validator 及 Result。
- 外部能力介面。
- 不依賴 HTTP 或 Vue。

### Domain

- Entity、Value Object、Enum。
- 商業規則與領域例外。
- 不依賴 API、EF Core、SQL Server 或 Vue。

### Infrastructure

- EF Core 與 SQL Server。
- Repository 或 Application 所需資料存取實作。
- Identity、OpenAI、檔案儲存。
- `IEmailSender` 的 Brevo SMTP 實作，以及開發環境不寄送的本機實作。
- Hangfire 與 SQL Server 持久化儲存，用於庫存逾時、Email、通知、AI 紀錄清理及其他可重試背景工作。
- 模擬 Payment Gateway 與 Shipping Provider。
- 背景排程與外部服務 Adapter。

客服、檢舉及退貨附件第一版存放於網站根目錄之外的本機私有目錄，下載必須經過 API 驗證及授權。不得將附件直接放在 `wwwroot` 供靜態存取。Application 使用 `IFileScanner`；Infrastructure 以 Microsoft Defender 掃描暫存檔，並在掃描前驗證副檔名、MIME 與檔案簽章。掃描不可用或結果不明時拒絕保存。

## 依賴方向

```text
Api → Application → Domain
Api → Infrastructure
Infrastructure → Application + Domain
Domain → 無其他專案依賴
```

兩個 Vue 應用程式只能透過 API 使用後端，不直接存取資料庫。

## API 路由

```text
/api/v1/products
/api/v1/cart
/api/v1/orders
/api/v1/support

/api/v1/admin/products
/api/v1/admin/inventory
/api/v1/admin/orders
/api/v1/admin/returns
/api/v1/admin/reports
```

API Controller 保持精簡，不直接操作大量 `DbContext` 或包含商業規則。

### 客服、檢舉與退貨邊界

```text
SupportTicket ─┐
ReportCase ────┼─ 統一管理工作台查詢
ReturnRequest ─┘
```

- 三個領域各自擁有資料、狀態及寫入流程，不共用案件主表。
- 管理後台可以透過統一 API 查詢工作台摘要，但後續動作必須送往各自領域的 Application Use Case。
- 一般客服案件使用共用自領佇列；檢舉與退貨保留各自佇列及權限。
- `CustomerServiceSupervisor` 負責一般客服案件的指派、轉派、優先級覆核及 SLA 升級。
- 統一查詢的 12 個欄位、分支授權、Cursor 排序與一致性規則已定於 [[03-架構/統一案件工作台設計]]。
- 第一版統一查詢使用 SQL `UNION ALL` View 與 EF Core Keyless Entity；View 只提供授權後的摘要查詢，任何命令仍進入原領域 Application Use Case。

## 前端

### customer-web

- Vue 3、TypeScript、Vite。
- PrimeVue 作為 UI 元件庫。
- TanStack Query 管理 API Server State；Pinia 管理登入狀態、UI 偏好與跨頁客戶端流程。
- 手機與桌面響應式介面。
- 商品、AI 搜尋、組裝、購物車、結帳、訂單及會員功能。
- 第一版繁體中文；日文與韓文列為 S。

### admin-web

- Vue 3、TypeScript、Vite。
- PrimeVue 作為 UI 元件庫。
- TanStack Query 管理 API Server State；Pinia 管理登入狀態、UI 偏好與跨頁客戶端流程。
- 第一版桌面版與繁體中文。
- 商品、庫存、訂單、物流、退貨退款、客服、優惠券、權限及報表。
- 商品管理包含批次上下架、批次調價與 Excel 匯入匯出。
- 報表包含七個已確認為 M 的分析畫面。

兩個 Vue 應用共用下列 API 契約策略：

- 從 ASP.NET Core OpenAPI 文件產生 TypeScript 型別與 typed fetch client。
- 產生工具使用 `openapi-typescript`＋`openapi-fetch`，套件版本由 lock file 固定。
- 產生碼不可手動修改，契約變更後必須重新產生。
- 認證、共通錯誤處理與 Correlation ID 放在共用 fetch wrapper，不修改產生碼。
- CI 重新匯出 OpenAPI、產生型別、要求 Git Diff 為空，並執行前台及後台 Typecheck；詳見 [[03-架構/OpenAPI與前端Client流程]]。

## 報表查詢

- 七個 M 報表第一版以 SQL Server 即時彙總及必要索引實作。
- 不預設加入報表快取或每日預彙總表。
- 使用 10,000 筆展示資料量測並完成查詢與索引優化後，個別報表若仍超過 P95 3 秒，才建立新的反正規化決策。
- 未來 Report Snapshot 必須可由交易資料重建，保存 `AsOfUtc`、來源版本及重建狀態，並在畫面顯示資料時間。
- 毛利查詢使用 `OrderItem` 的成交成本快照。

## 安全邊界

- API 最終驗證所有角色、訂單所有權、金額、優惠、庫存及狀態轉換。
- Vue Router Guard 只改善體驗，不是安全邊界。
- AI 不直接查詢資料庫，也不能執行寫入操作。
- 個資送往 OpenAI 前由後端最小化與去識別化。
- 管理員完整個資存取與退款需要稽核。
- 設定、API Key、連線字串及 Email 密碼不得提交 Git。
- Hangfire Dashboard 只允許完成 TOTP 的 `SuperAdmin`，且為唯讀；人工重試必須走具理由與稽核的管理 API。

### 登入邊界

- ASP.NET Core Identity 使用 `HttpOnly` Cookie，會員與管理員採不同 Cookie Scheme。
- 會員閒置期限 8 小時、最長 7 天；管理員絕對期限 2 小時且必須完成 TOTP 2FA。
- 明列允許的 CORS Origin，Cookie 跨來源請求搭配 Credentials；狀態變更請求必須驗證 Anti-forgery Token。

## AI 搜尋架構

- OpenAI 以版本化 JSON Schema 產生結構化搜尋條件，後端再做 Schema 與商業規則驗證。
- 第一版不使用向量資料庫或 Embedding；SQL Server 取得候選商品，確定性相容性與排序規則決定有效結果。
- AI 輸出不合法、拒絕或外部服務失敗時不直接查詢，降級為補問、一般關鍵字搜尋或篩選。
- 搜尋管線、客服工具、引用與版本邊界詳見 [[03-架構/AI應用詳細設計]]。
- 商品搜尋解析及摘要使用 `gpt-5.6-luna`，AI 客服使用 `gpt-5.6-terra`；統一由 Responses API Adapter 呼叫。

## 模擬外部服務

```text
IPaymentGateway   → SimulatedPaymentGateway
IShippingProvider → SimulatedShippingProvider
```

模擬器必須保留真實服務常見的非同步回呼、逾時、失敗、重複通知與冪等處理概念，使未來可替換實際 Provider。

## 本機展示啟動

第一版不使用 Docker，提供：

```text
scripts/
├─ start-all.ps1
├─ stop-all.ps1
├─ status.ps1
├─ reset-demo-data.ps1
└─ health-check.ps1
```

`start-all.ps1` 檢查 SQL Server、啟動 API、前台、後台，等待 Health Check，並輸出服務網址。停止腳本使用本專案保存的 PID，不可一次終止電腦上的所有 Node 或 .NET 程序。
