# 安全與供應鏈強制驗收標準

## 目的與適用範圍

本標準是所有功能、API、背景工作、檔案、AI 工具、匯入匯出與套件變更的合併阻擋條件。任一項未提供證據或測試失敗，該功能不得標記完成或合併。

「其他使用者內容」指其他會員、訪客訂單持有人、管理員或案件參與者擁有的非公開資料。依正式需求公開的商品、已核准評價或公開組裝分享不屬於越權讀取，但仍只能回傳公開 DTO；具有正式角色、Policy 與業務目的的管理員存取不視為越權。

## 強制驗收矩陣

| ID | 驗收問題 | 通過標準 | 最低證據 | 失敗處理 |
|---|---|---|---|---|
| SEC-ACC-01 | 任何使用者能否用任何方式讀到其他使用者的非公開內容？ | 不可。所有明細、列表、搜尋、匯出、附件、通知、AI 工具、快取及背景結果都必須由後端依登入身分、角色、資源所有權與 Actor Scope 過濾；不得先查出全部資料再由前端隱藏。 | 每種私人資源至少有「本人成功、未登入拒絕、使用者 B 以使用者 A 的 PublicId 拒絕、列表與匯出不含 A 資料」整合測試。 | 阻擋合併；依一致的 403／404 契約拒絕且不得洩漏資源是否存在。 |
| SEC-ACC-02 | 任何使用者能否用任何方式修改其他使用者的內容？ | 不可。Create Child、PUT／PATCH、狀態 Action、批次、匯入、附件與背景命令都必須從後端身分取得 Actor，不接受 Request 內的會員／管理員 ID 作為授權依據。 | 每個寫入能力至少有 B 替換 A 的路由 ID、Body ID、Parent ID、批次列與 Action 參數的負面整合測試；資料庫前後快照證明無副作用。 | 阻擋合併；拒絕請求且不得產生部分寫入、Outbox、通知或檔案副作用。 |
| SEC-ACC-03 | 做任何刪除前是否確認操作者有權刪除該筆資料？ | 必須。Hard Delete、Soft Delete、附件刪除、批次刪除與清理命令都要在伺服器端於異動前驗證身分、角色、資源範圍、所有權及允許刪除的業務狀態；前端確認視窗不算授權。 | 每個刪除能力至少有本人／授權角色成功、其他使用者、錯誤角色、跨範圍、非法狀態與批次混入未授權列測試；失敗後資料、檔案及關聯均保持不變。 | 阻擋合併；高風險刪除另需 AuditLog，批次不得略過逐筆授權或產生未定義的部分成功。 |
| SUP-ACC-01 | 新增或使用的 Package 是否真實存在且來源正確？ | 必須可由專案設定的正式 Registry 解析、Restore／Install，名稱與版本必須與官方文件、專案首頁或來源 Repository 對得上；不得只因 AI 建議就加入近似名稱或無法查證套件。 | NuGet 以乾淨 Restore，npm 以 `npm ci` 驗證所有直接與間接依賴；新增直接套件的 PR 記錄 Registry 頁面、用途、版本與官方來源，並提交 lock／中央版本檔。 | 無法解析、來源不明、疑似 Typosquatting 或套件身分不一致時阻擋合併。 |
| SEC-ACC-04 | 提交內容是否直接包含 API Key 等敏感資訊？ | 不可。工作樹、Staged Diff、Commit、PR Diff、設定檔、測試快照、Log、Vue Bundle、文件、圖片及影片不得包含真實 API Key、密碼、Token、私鑰、Cookie、TOTP Seed、Recovery Code 或含密碼連線字串。 | 提交前人工檢查 Diff 並執行 Secret 掃描；CI／PR 執行自動掃描；前端 Production Build 另掃描敏感值。範例只保留 Key 名、空值或明顯無效占位值。 | 立即阻擋合併；若值曾進 Commit，即使尚未 Push 也先撤銷／Rotation，再依事故流程清除，不得只刪除新檔案。 |

## 資源授權測試模板

每個含私人資料的資源至少準備 `UserA`、`UserB`、未登入者與必要管理角色，並驗證：

1. `UserA` 可在正式規則允許時讀取、修改或刪除自己的資源。
2. `UserB` 使用 `UserA` 的 PublicId、父資源 ID、附件 ID、分享外的 Token 或批次列時被拒絕。
3. 未登入者被拒絕，訪客訂單只接受綁定單筆訂單且未過期的驗證權杖。
4. 列表、搜尋、報表、匯出、通知、AI 回答及快取不出現 `UserA` 的資料。
5. 拒絕後資料列、`rowversion`、檔案、Outbox、通知、庫存與 Audit 以外的商業狀態沒有改變。
6. 管理員只能依角色與 Actor Scope 存取，不因知道 PublicId 或直接呼叫 API 而擴權。

## 刪除實作規則

- 授權判斷必須在 API／Application 伺服器端執行；Vue 隱藏按鈕與確認對話框只改善 UX。
- 優先以已套用 Actor Scope 的查詢取得目標，或在異動前呼叫正式 Authorization Policy；不得信任 Request 傳入的 `userId`、`ownerId` 或 `role`。
- 批次刪除需定義 All-or-Nothing 或逐筆結果，且每一筆都要授權；不得只檢查第一筆。
- 背景清理工作也需以資料類型、保存期限、Legal Hold 與工作權限限制範圍，不因沒有互動使用者就跳過安全邊界。

## Package 驗證規則

- 新增套件前核對精確名稱、官方用途、支援的 .NET／Node／Vue 版本、Registry 身分及來源 Repository。
- .NET 套件版本只進 `Directory.Packages.props`；npm 變更必須同時提交 `package.json` 與 `package-lock.json`。
- Repository 以 `FP.dev/NuGet.config` 清除繼承來源並只允許官方 `https://api.nuget.org/v3/index.json`；npm 設定只允許位於 `frontend/customer-web/.npmrc` 與 `frontend/admin-web/.npmrc`，使實際執行 `npm ci` 的兩個專案都只使用官方 `https://registry.npmjs.org/`。Repository 根目錄及其他位置不得另設 `.npmrc`。
- 兩份專案層級 `.npmrc` 都必須強制 `strict-allow-scripts=true`；兩個 Vue Manifest 的 `allowScripts` 只接受兩種形式：審查後的精確 `package@version: true` 核准，或名稱型 `package: false` 明確拒絕。禁止名稱型 `true`、版本限定 `false`、`--all` 與 `dangerously-allow-all-scripts=true`；套件版本或正式支援平台變更時必須重新檢視。
- Restore／Install 成功只證明套件存在，不代表可信；新增直接依賴仍需人工核對來源，並執行既定漏洞掃描。
- PR 不得提交來源不明的本機 `.nupkg`、壓縮套件、修改後套件或略過 Lock File 的相依變更；若確有需要必須另立高風險決策。
- `scripts/verify-package-sources.ps1` 驗證 Registry 白名單、NuGet 中央精確版本、npm 直接版本、Lock 來源與 Integrity、兩份必要專案設定、嚴格安裝腳本模式及精確版本核准；`scripts/test-package-source-verifier.ps1` 必須證明非官方 NuGet／npm 來源、必要 `.npmrc` 缺少、額外 `.npmrc`、關閉嚴格模式、危險全域允許、非版本化腳本核准與版本限定腳本拒絕會被拒絕。
- GitHub Actions 的 `Package Source Evidence` 執行上述正向與拒絕測試，並與 Backend 的乾淨 Restore、Frontend 的 `npm ci` 一同納入 `CI Required`。新增直接 Package 時，PR 模板仍須逐筆填寫精確版本、用途、Registry 頁面與官方專案／來源 Repository。

## Secret 驗收規則

- Secret 值只放 .NET User Secrets、受控環境變數或後續核准的 Secret Store。
- `appsettings*.example.json`、`.env.example`、測試與文件只可保存 Key 名、空值或明顯無效占位值。
- 自動 Secret Scanner 採固定版本 Gitleaks CLI `8.30.1`；GitHub Actions 必須先驗證官方 Linux x64 SHA-256，再以完整 Checkout History 掃描 Git 歷史，兩個 Vue Production Build 後另掃描各自 `dist`，並全部使用 `--redact`。
- Repository 歷史掃描、兩個 Build Artifact 掃描與 Gitleaks 下載校驗均為 `CI Required` 的阻擋條件；不得改用 `latest`、略過校驗或在 Log 顯示完整疑似 Secret。
- 第一版不建立 Baseline、廣泛路徑 Allowlist 或 `.gitleaksignore`。誤報優先改為明顯無效的合成值；必要忽略只能限制於特定 Fingerprint／單一合成值並在 PR 留下原因，真實 Secret 不得忽略。
- 偵測到疑似 Secret 時停止提交；確認是真值後立即 Rotation，記錄受影響範圍，再處理 Git 歷史與衍生產物。

## 完成定義

- 五項強制驗收都有對應證據，且所有負面測試通過。
- 新增私人資源或寫入／刪除 Endpoint 時，同一 PR 新增 Actor A／B 授權測試。
- 新增 Package 時，同一 PR 提供來源核對、乾淨 Restore／Install、Lock File 與漏洞掃描結果。
- Commit／PR／前端產物不含 Secret；任何疑似外洩已完成撤銷與 Rotation。
- `QA-08` 的 Secret Scanner 與 Package 來源證據流程已落實；Actor A／B 授權矩陣與刪除無副作用尚未全部自動化前，仍須在 PR 中誠實標示人工與自動證據，不得把未執行的檢查寫成通過。
