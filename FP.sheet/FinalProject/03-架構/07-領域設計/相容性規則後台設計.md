# 相容性規則後台設計

## 管理邊界

- 規則 Code、比較運算式、受保護 Semantic Key、硬性阻擋條件及 PSU 八個級距由程式碼固定，後台不可改寫。
- `CatalogManager` 與 `SuperAdmin` 可查看規則、執行測試，以及在安全範圍內修改警告門檻。
- 規則整體啟停只允許 `SuperAdmin`，需二次確認及原因；停用硬性規則只限 Demo／維護，不得默默視為相容。
- 一般後台角色只可查看已套用於商品的結果，不取得門檻設定權限。

## 可調警告門檻

| Setting Code | 預設 | 安全範圍 | 行為 |
|---|---:|---:|---|
| `GpuClearanceWarningMm` | 20 mm | 10～50 mm | 顯示卡長度未超限，但剩餘空間小於或等於門檻時警告 |
| `CoolerClearanceWarningMm` | 10 mm | 5～30 mm | 散熱器高度未超限，但剩餘空間小於或等於門檻時警告 |
| `PsuReserveWarningPercent` | 35% | 30～50% | 已通過硬性 30% 規則，但額外餘裕低於設定值時提示未來升級空間有限 |
| `RemainingRamSlotWarningCount` | 0 | 0～2 | 安裝後剩餘 RAM 插槽小於或等於門檻時警告 |
| `RemainingStoragePortWarningCount` | 0 | 0～2 | 安裝後相容儲存連接埠小於或等於門檻時警告 |

設定值超界回 `compatibility_threshold_out_of_range`，不得自動截斷。BIOS 映射、Socket、DDR、尺寸上限、容量上限、接頭與 PSU 最低需求都不是可調警告門檻。

## 規則測試 API

### Request

`POST /api/v1/admin/compatibility-rules/test`

```json
{
  "items": [
    { "skuPublicId": "019...", "quantity": 1 }
  ],
  "ruleCodes": ["CPU_SOCKET", "PSU_CAPACITY"],
  "useDraftSettings": false
}
```

- `items` 1～20 筆；同一 SKU 先合併數量，數量 1～8。
- `ruleCodes` 可省略，表示執行全部適用規則；最多 20 個且未知 Code 整筆拒絕。
- `useDraftSettings=true` 只允許在同一請求帶入已通過範圍驗證的暫存警告設定，不保存設定。
- 測試可引用未上架 SKU，但不能繞過 Catalog 資源權限。

### Response

```json
{
  "overall": "Blocked",
  "results": [
    {
      "ruleCode": "CPU_SOCKET",
      "severity": "Blocked",
      "messageKey": "compatibility.cpu_socket_mismatch",
      "subjectSkuPublicIds": ["019...", "019..."],
      "facts": { "cpuSocket": "AM5", "boardSocket": "LGA1700" }
    }
  ],
  "settingsVersion": 3,
  "evaluatedAtUtc": "2026-08-13T00:00:00Z"
}
```

`overall` 只允許 `Compatible`、`Warning`、`Blocked`、`InsufficientData`。`facts` 只包含白名單的結構化規格，不回傳內部 SQL Id、成本或未授權欄位。

## 設定 API 與併發

| Method／Route | 用途 | Policy |
|---|---|---|
| `GET /api/v1/admin/compatibility-rules` | 查詢規則與目前門檻 | `CompatibilityRule.View` |
| `PATCH /api/v1/admin/compatibility-rules/{ruleCode}/warning-settings` | 更新警告門檻 | `CompatibilityRule.ManageWarnings` |
| `PATCH /api/v1/admin/compatibility-rules/{ruleCode}/activation` | 啟停整條規則 | `CompatibilityRule.ManageActivation`（SuperAdmin） |
| `POST /api/v1/admin/compatibility-rules/test` | 執行無寫入測試 | `CompatibilityRule.Test` |

更新命令必須包含 RowVersion；衝突回 `409 concurrency_conflict`。成功更新建立新 Settings Version，既有訂單與組裝快照不回寫。

## SKU 相容性屬性 API

`SkuCompatibilityAttributes`／`SkuStorageInterfacePorts` 兩張表在此之前只有測試 Fixture 與 dev seeder 會寫入，一般 SKU 建立流程建立的商品永遠拿不到相容性資料。以下是唯一的正式管理讀寫路徑，放在 Builds 模組（本設計文件範圍）而非 Catalog，因為 Catalog 對 attribute key／storage interface code 沒有既有依賴：

| Method／Route | 用途 | Policy |
|---|---|---|
| `GET /api/v1/admin/compatibility-rules/skus/{skuPublicId}/attributes` | 讀取目前狀態與 RowVersion | `CompatibilityRule.View` |
| `PUT /api/v1/admin/compatibility-rules/skus/{skuPublicId}/attributes` | 全量替換（資源本身即完整快照，非差異合併） | `CompatibilityRule.ManageWarnings` |

Request／Response（`SkuCompatibilityAttributesDto`）：

```json
{
  "skuPublicId": "019...",
  "attributes": { "COOLER_SUPPORTED_SOCKETS": ["AM5", "LGA1700"] },
  "storagePorts": { "SATA": 4 },
  "rowVersion": "AAAAAAAAB9E="
}
```

- `rowVersion` 為目標 SKU 自己既有的 RowVersion（不另外發第二個併發權杖），寫入時需帶上一次讀取到的值，衝突回 `409 concurrency_conflict`。
- `attributes` 每個 key 只對其對應的單一 `BuildComponentCategoryCodes` 有意義（例如 `COOLER_SUPPORTED_SOCKETS` 只適用 Cooler 分類），分類不符回 `validation_failed`，不得靜默寫入後被規則引擎忽略。
- 值一律正規化（Trim + Unicode NFKC + 轉大寫），正規化後長度、數量上限與重複值超界回 `validation_failed`。
- `storagePorts` 只適用 Motherboard 分類。
- Product 換分類時，若旗下 SKU 仍有這兩類資料會拒絕改分類（`validation_failed`），避免分類專屬資料被靜默孤立；兩個寫入共用 Product 的 RowVersion 作為併發邊界。

## 稽核欄位

相容性規則不建立專用 Audit 表或重複稽核欄位，一律沿用中央 `IAuditWriter`／`AuditLogs`。三個 Action 固定為：

- `compatibility_rule.warning_setting.update`
- `compatibility_rule.activation.update`
- `compatibility_rule.test`

警告門檻與啟停以本次新增的 `CompatibilityRuleSetting.PublicId` 為 Resource PublicId；管理員測試以本次新增的 `CompatibilityCheckRun.PublicId` 為 Resource PublicId。中央 Audit 白名單只允許 `ruleCode`、`settingCode`、`value`、`isActive`、`settingsVersion`、`inputHash`、`overall` 等安全結構化欄位，並使用既有的 Actor PublicId／角色、遮蔽 IP、Reason、CorrelationId、TraceId、Before／After 與 Schema Version 契約。

核心資料與 Audit 必須使用同一 DbContext／SQL Server 交易：成功操作恰有一筆 Audit，Audit 失敗時整體回滾。規則測試只在 Audit 保存輸入 SKU PublicId 集合的 SHA-256 Hash、結果摘要、設定版本與 TraceId，不保存完整商品內容副本。

## 資料格式與 Migration Gate

- `CompatibilityCheckResult.FactsJson` 固定使用 `{"schemaVersion":1,"facts":{...}}` Envelope；未來變更內容結構時增加版本，不得猜測舊格式。
- 稽核欄位、遮蔽 IP、Schema Version 與 365 天保留已由中央 Audit 實作提供，因此本功能不新增 EF Migration。
- 若現有中央 Audit 無法承載上述安全欄位或同交易寫入，必須停止實作並重新進入 Migration Gate，不得在功能分支建立第二套 Schema。

## API 契約收斂

- 啟停 Request 帶 `isActive`、`reason` 與 `rowVersion`，並使用上表的 `PATCH .../{ruleCode}/activation`；不使用 `POST .../actions/set-activation`。
- `BuildListDto` 不回傳固定值 `owner:member`。擁有權由後端 Actor Scope／Owner Query 強制驗證，不以 DTO 常數代表授權；公開 `SharedBuildDto` 仍不得回 Owner。

## 驗收重點

- 邊界最小值、最大值可保存；超界與非數字拒絕。
- 無權限角色無法讀取或修改；未登入與越權不靠前端隱藏。
- 相同 RowVersion 的兩次更新只有一次成功。
- 停用規則後結果顯示 `RuleDisabled`，不得回 `Compatible`。
- 測試與正式購物流程使用同一 Application 規則服務及相同設定版本。
