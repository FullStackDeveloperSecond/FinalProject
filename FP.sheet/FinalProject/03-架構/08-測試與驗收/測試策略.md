# 測試策略

## 工具選擇

| 層級 | 工具 | 主要用途 |
|---|---|---|
| .NET 單元測試 | xUnit | 領域規則、計算、狀態轉移與純 Application 邏輯 |
| API 整合測試 | xUnit + `Microsoft.AspNetCore.Mvc.Testing` | 驗證路由、驗證、授權、序列化、資料庫與交易行為 |
| Vue 單元／元件測試 | Vitest + Vue Test Utils | Composable、Store、元件互動與錯誤狀態 |
| 瀏覽器 E2E | Playwright | 驗證前台、後台與 API 組合後的核心展示流程 |

## 測試資料庫

- 整合測試使用專用 SQL Server 測試資料庫，不連線到開發或展示資料庫。
- 測試開始前套用正式 EF Core Migration，確保測試涵蓋實際 SQL Server 行為。
- 每次測試執行必須可重複清理與重建所需資料，避免測試順序相依。
- 純單元測試不連資料庫；不以 InMemory Provider 取代需要驗證 SQL Server 查詢、約束或交易的測試。
- `CouponRuleReader` 必須使用 SQL Server Provider-backed 整合測試驗證實際查詢、範圍包含／排除、狀態與期限；不新增 EF InMemory 或 SQLite Provider 作為 SQL Server 正確性的替代證據。

### GitHub Actions 第一段實作

- `.github/workflows/ci.yml` 在對 `main`／`dev` 的 Pull Request、Push，以及手動觸發時執行。
- `Backend` Job 使用 `global.json` 的 .NET SDK，依序執行 Restore、`-warnaserror` Build、Format Verify、Solution Test 與直接／間接 NuGet 弱點報告。
- `Frontend (customer-web)` 與 `Frontend (admin-web)` 以 Matrix 平行執行 `npm ci`、Typecheck、零警告 Lint、Vitest、Production Build、Gitleaks `dist` 掃描與正式相依弱點稽核。
- `Secret Scan` 以完整 Checkout History 執行 Gitleaks Git 掃描；版本與 Linux x64 SHA-256 固定，輸出使用 `--redact`。
- `Package Source Evidence` 驗證 NuGet／npm 官方 Registry、中央與直接精確版本、Lock 來源與 Integrity、雙前端專案層級 `strict-allow-scripts=true`、精確 `package@version: true` 腳本核准及名稱型 `package: false` 腳本拒絕；隔離 Fixture 必須證明非官方來源、必要／額外 `.npmrc`、關閉嚴格模式、危險全域允許、非版本化核准與版本限定拒絕會被拒絕。
- `CI Required` 是 Branch Protection 唯一穩定的必要 Check；只有 Secret Scan、AI Evaluation Contract、Package Source Evidence、Backend 與兩個 Frontend 全部成功才會成功。
- Workflow 只授予 `contents: read`、Checkout 不保留 Git Credential，並取消同一分支已被新 Commit 取代的舊執行；官方 Action 以完整 Commit SHA 固定。
- 第一段不連 SQL Server、不執行 Migration、不呼叫 OpenAI／Brevo，也不接觸任何 Secret。

合併至 `dev` 後固定執行以下五條核心 Playwright E2E 流程：

1. 新手以自然語言描述需求，取得可解釋推薦，完成相容組裝並阻擋不相容替換。
2. 訪客加入多 SKU、使用優惠券、選擇配送與模擬付款，建立訂單並正確保留庫存。
3. 兩個並行結帳競爭最後庫存，只有一筆成功且不超賣。
4. 會員同意 AI 客服後只查到自己的去識別化訂單；越權、拒絕同意或 AI 故障時安全拒絕／降級。
5. 後台出貨扣庫，受理單項退貨與部分退款，最終報表反映退款後數字。

以下高風險變更在 PR 中必須附對應測試：

- EF Core Migration 或資料約束。
- 登入、Cookie、2FA、角色或資源所有權授權。
- 任何私人資源的讀取、列表、搜尋、匯出、附件、修改、刪除、批次或背景操作。
- 訂單金額、折扣、運費、付款或退款。
- 庫存保留、釋放、出貨與併發購買。
- AI 個資遮蔽、結構化輸出驗證與降級行為。
- PublicId 不暴露內部 Id、正規化唯一鍵、Filtered Unique、Check Constraint 與 Delete Behavior。
- Outbox／冪等重送、處理中衝突、匯入 Staging 過期、Hash 變更與全批回滾。

## 測試分層原則

- 單元測試快速覆蓋大量商業規則與邊界值。
- 整合測試驗證 ASP.NET Core 管線、SQL Server、交易、冪等性與併發控制。
- E2E 只保留最具商業價值與展示風險的跨系統流程，避免用瀏覽器測試取代所有較低層測試。
- 測試名稱描述「條件、動作、結果」，失敗時應能看出哪個商業規則被破壞。

## 優先測試情境

1. 多人同時購買最後庫存時只允許合法保留，且不超賣。
2. 重複建立訂單、付款回呼或退款請求不產生重複副作用。
3. 付款失敗後可在原期限建立新付款嘗試，逾時才取消並釋放庫存。
4. 優惠券以適用商品小計判斷門檻；部分退貨依最低消費與適用旗標快照重算，折扣／免運扣回、組裝費與最終退款方向正確。
5. 管理員 2FA、會員與管理員 Cookie 隔離、未授權資源存取被拒絕。
6. AI 結構不合法、外部 API 失敗或超出用量時安全降級，且基本電商功能正常。
7. 重複 Idempotency-Key 同 Request 取得相同結果，不同 Request Hash 被拒絕，並行請求不產生雙重副作用。
8. 交易提交與 Outbox 同成同敗；Dispatcher 重跑不重複寄信或建立站內通知。
9. 商品／庫存匯入在 24 小時 Staging 內可確認，過期、非擁有者、Hash 不同或任一庫存列失敗時不得部分提交。
10. PublicId 可定位授權資源但不洩漏內部連號；重複 Code、互斥 Profile 及規格 One-of 由 SQL Server 阻擋。
