# 核心商業規則

狀態：已確認

共用語彙與英文命名以 [[01-需求/專案名詞表]] 為準；狀態與合法轉移確認後以 [[03-架構/03-資料與一致性/狀態機設計]] 為準。

## 共通原則

1. 前端送出的價格、折扣、運費、組裝費、庫存及權限資訊一律不可信任，後端必須重新計算及驗證。
2. API 不直接回傳或接收 EF Core Entity，對外使用 Request、Response 與 DTO。
3. 訂單成立後，商品名稱、SKU、規格、單價、折扣、運費、組裝費、收件資料與政策版本以快照保存。
4. 已成立訂單不因商品、優惠券、運費或退貨政策日後修改而改變。
5. 訂單、付款、物流、退貨與退款不得直接刪除，透過狀態與歷程追蹤。
6. 所有金額使用適合貨幣的精確型別，不使用浮點數。
7. 系統主要幣別為新台幣。
8. 關鍵狀態改變需留下時間、操作者與稽核紀錄。
9. 建立訂單與執行退款必須支援冪等請求；相同 Key 不可產生重複商業副作用。
10. 一般可編輯資料以 `rowversion` 偵測衝突；庫存異動另使用資料庫交易與條件更新確保不超賣。
11. 可變主資料與交易關聯以正規化結構作唯一可寫來源；畫面需要的摘要原則上由查詢推導，不建立可互相矛盾的第二份主資料。
12. 訂單快照、庫存餘額及統一案件工作台屬刻意重複資料，必須分別標示為交易快照、衍生餘額或唯讀投影，並定義同步、重建及防漂移規則。
13. 對外資源使用不可猜的 UUID v7 PublicId；資料庫內部以 `bigint identity` 關聯，API 不暴露連號主鍵。
14. SKU、優惠碼及其他系統 Code 採不分大小寫唯一並以大寫正規化保存；顯示名稱不套用此規則。
15. 金額分攤統一使用 `MidpointRounding.AwayFromZero` 至兩位小數，最後一筆吸收尾差，前端不得自行重算。

## 商品與價格

1. 商品與 SKU 分離，實際售價及庫存原則上落在 SKU。
2. 商品可以有品牌、分類、標籤、多張圖片、草稿、上架及下架狀態。
3. 下架、刪除或缺貨的 SKU 不可新加入購物車，但舊訂單快照仍可正常顯示。
4. 購物車價格只是預覽，結帳時必須重新取得最新價格。
5. 組裝電腦內每個零件仍是獨立 SKU，方便庫存、退貨與保固追蹤。
6. SKU Code 建立後不可變更；Excel 更新必須以 SKU Code 精確比對，不以名稱或規格猜測。
7. 相容性程式引用的規格語意鍵與資料型別受保護，不得直接刪除或變更。

## 組裝與相容性

1. AI 負責理解用途、預算與偏好，不能作為相容性的最終判斷者。
2. 後端確定性規則必須驗證完整組裝清單。
3. 不相容組合不能進入組裝商品結帳流程。
4. 分享或重新開啟組裝清單時，重新檢查價格、庫存、上下架與相容性。
5. 每台組裝電腦收取固定 NT$300 組裝費。
6. 同一組裝清單可一次購買多台；庫存按總數原子保留，每台建立獨立組裝工作。
7. 電源建議瓦數以結構化功耗加總後增加 30% 餘裕、向上取常見瓦數級距，且不得低於 GPU 廠商建議值。

## 訂單與庫存

1. 加入購物車不保留庫存。
2. 建立訂單時以資料庫交易原子保留庫存。
3. 最後一件商品的競爭由後端資料庫交易解決，不依賴前端即時更新。
4. 付款逾時、取消或商家取消時釋放保留庫存。
5. 出貨時才同時減少實體在庫與保留庫存。
6. 訂單完成只更新訂單及報表狀態，不再改變實體庫存。
7. 不允許缺貨預購。
8. 貨到付款適用一般宅配及超商取貨，折扣後且包含運費等費用的最終應付金額不得超過 NT$20,000；組裝電腦及其他限制品不得使用貨到付款。
9. 貨到付款訂單成立時仍只保留庫存；宅配送達或超商取貨完成後才將付款標為成功，出貨時才扣除實體庫存。

## 金額計算

建議固定順序：

```text
商品原價
→ 商品特價
→ 優惠券
→ 組裝費
→ 配送及免運判斷
→ 訂單應付總額
```

所有折扣必須分攤至訂單明細，以支援單項退貨與部分退款。

訂單明細必須保存成交時的 SKU 單位成本快照；歷史毛利不得以查詢當下的 SKU 成本回推。

## AI

1. 基本購物、結帳、訂單與客服案件功能不能依賴 AI 才能運作。
2. AI 搜尋失敗時降級為關鍵字搜尋。
3. AI 客服失敗或使用者不同意外部 AI 處理時，轉人工客服案件。
4. AI 只讀，不可代替使用者執行取消、退貨、退款或資料修改。
5. 送往外部 AI 的資料採最小化與去識別化原則。

## 時間與時區

- 商業時間以台灣時區呈現。
- 資料庫時間建議統一保存 UTC，顯示時轉換。
- 優惠券、付款期限、庫存保留、退貨期限與 Token 都必須保存明確到期時間。
