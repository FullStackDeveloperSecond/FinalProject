# 角色與權限

狀態：已確認

## 前台參與者

前台的「參與者」不一定都是資料庫 RBAC 角色。

| 參與者 | 說明 |
|---|---|
| 匿名訪客 | 未登入，可瀏覽、AI 搜尋、購物車及訪客結帳 |
| 已驗證訪客購買者 | 以訂單 Email 一次性驗證取得單筆訂單的短效存取權 |
| 會員 | 已驗證 Email 的註冊使用者 |
| 已購買會員 | 具有已完成訂單的會員，符合條件時可評價商品 |
| 停權會員 | 帳號狀態受限，不是獨立角色 |

實際前台帳號的基本角色為 `Member`。訪客沒有帳號；已購買資格由訂單動態判斷；停權使用帳號狀態表達。

## 訪客訂單授權

流程：

```text
輸入訂單編號與購買 Email
→ 寄送一次性驗證碼或驗證連結
→ 驗證成功
→ 核發短效 GuestOrderAccessToken
→ 僅能操作該筆訂單
```

要求：

- Token 只能存取指定訂單。
- 建議有效時間 30 分鐘。
- 限制驗證碼發送與輸入次數。
- 錯誤訊息不得洩漏訂單是否存在。
- 重要操作可以要求再次確認。
- 訪客不能使用 AI 客服或存取其他訂單。

## 後台角色

一位管理員可以擁有多個角色，第一版以角色層級控制權限。

- 多角色權限使用各角色允許權限的聯集，不設顯式 Deny。
- 敏感操作不只檢查角色名稱，需使用明確 Authorization Policy 驗證角色、資源範圍及業務前置條件。
- `SuperAdmin` 具有全域管理與緊急監督權限，但具名 Policy 仍以其允許角色為準；`SuperAdmin` 不會自動取得日常客服處理 Policy。個資、高風險庫存、退款、權限及設定操作仍需完成管理員 2FA 與稽核。

| 角色 | 負責範圍 |
|---|---|
| `SuperAdmin` | 所有功能、角色及系統設定 |
| `CatalogManager` | 商品、SKU、分類、品牌、規格、圖片及上下架 |
| `InventoryManager` | 庫存、保留庫存、手動釋放、庫存異動及低庫存管理 |
| `OrderManager` | 訂單、取消、出貨、物流、退貨流程及包裹限制維護 |
| `FinanceManager` | 付款、退款、優惠券、模擬發票／折讓及財務報表 |
| `CustomerService` | 客服案件、評價審核及一般檢舉佇列處理／自領 |
| `CustomerServiceSupervisor` | 具一般客服權限，另可指派、轉派、覆核優先級、處理 SLA 升級、覆核高風險檢舉及查看客服報表 |
| `MarketingAnalyst` | 優惠活動、優惠券及一般營運報表 |
| `PrivacyAdmin` | 查看完整會員個資及個資處理 |
| `SecurityAdmin` | 查詢登入、角色、安全與系統操作稽核；不因此取得完整會員個資或商業操作權限 |

日常允許一位管理員擁有多個角色，但高風險功能使用不同 Policy 與示範帳號。第一版不建立所有操作都必須兩人線上核准的工作流；職責分離落在退貨核准、退款執行、角色授予、完整個資及 Audit 權限邊界。

縮寫：SA=SuperAdmin、CAT=CatalogManager、INV=InventoryManager、ORD=OrderManager、FIN=FinanceManager、CS=CustomerService、CSS=CustomerServiceSupervisor、MKT=MarketingAnalyst、PRIV=PrivacyAdmin、SEC=SecurityAdmin。

AI 用量頁只允許 `SuperAdmin`、`FinanceManager`、`CustomerServiceSupervisor`、`MarketingAnalyst`。`FinanceManager`／`SuperAdmin` 可查看 Token 與成本金額；客服主管／行銷分析只取得遮蔽成本金額的營運彙總。第一線 `CustomerService` 與 `SecurityAdmin` 不具此頁權限。

- `P` 只能透過用途專用 DTO 取得遮蔽或彙總資料，不得呼叫完整資源 Endpoint。
- 一人多角色採權限聯集；但資源所有權、狀態、2FA、RowVersion、理由與稽核仍是額外必要條件。
- 不新增 `ReportReviewer`、`ReportViewer` 或 `OperationsManager`。一般檢舉由 CustomerService 專用佇列處理；個資、安全、詐欺、法律及其他高風險檢舉必須由 CustomerServiceSupervisor 指派或覆核。
- 成本欄位只在 Catalog 維護 SKU 成本、Finance／SuperAdmin 財務報表中可見；其他角色的商品 DTO 不回傳成本。
- 高風險操作即使由 `SuperAdmin` 執行仍需完成 TOTP、二次確認、填寫原因並寫入 AuditLog；SuperAdmin 是緊急與展示例外，不得繞過狀態、金額、所有權或併發規則。

### 高風險 Policy

| Policy | 允許角色 | 額外條件 |
|---|---|---|
| `Return.Approve` | OrderManager、SuperAdmin | Return 狀態合法、附審核理由、RowVersion、Audit |
| `Refund.Execute` | FinanceManager、SuperAdmin | 已核准退貨／退款分攤、金額上限、冪等鍵、TOTP、Audit |
| `Invoice.Manage` | FinanceManager、SuperAdmin | 後台模擬發票查詢、開立、作廢與折讓；沿用管理員 TOTP／MFA，狀態、冪等、RowVersion 與 Audit 仍由 Use Case 驗證 |
| `Coupon.Manage` | FinanceManager、MarketingAnalyst、SuperAdmin | 後台優惠券查詢、建立、修改、啟用、暫停與停用；不涵蓋前台購物車套券，規則完整性、狀態、名額、RowVersion 與 Audit 仍由 Use Case 驗證 |
| `Report.HighRiskReview` | CustomerServiceSupervisor、SuperAdmin | 個資、安全、詐欺、法律或其他高風險旗標；須指派或覆核、填理由並 Audit |
| `RoleAssignment.Manage` | SuperAdmin | 不得移除系統最後一位有效 SuperAdmin；更新 Security Stamp；Audit |
| `PersonalData.ViewFull` | PrivacyAdmin、SuperAdmin | 必填用途；每次讀取 Audit；回應禁止快取 |
| `PersonalData.Export` | PrivacyAdmin、SuperAdmin | 二次確認、用途與範圍、短效下載、匯出本身 Audit |
| `Audit.ViewSecurity` | SecurityAdmin、SuperAdmin | 只讀；敏感差異仍遮蔽 |
| `Audit.ViewPrivacy` | PrivacyAdmin、SuperAdmin | 只限個資存取／匿名化／匯出事件 |
| `Audit.Export` | SuperAdmin | 白名單欄位、二次確認、原因、匯出 Audit |
| `Outbox.Retry` | SuperAdmin | 管理 Session 必須已完成 TOTP／MFA；只允許 Failed、必填穩定 reasonCode、不可改 Payload／AttemptCount，並與狀態更新同次寫入中央 Audit |
| `SupportTicket.Handle` | CustomerService、CustomerServiceSupervisor | 案件在可處理狀態；承辦人或共用佇列範圍符合；公開回覆、內部備註、claim、一般優先級調整、合法狀態處理、取消與重開均須 RowVersion，要求理由的操作另須填寫理由 |
| `SupportTicket.Supervise` | CustomerServiceSupervisor、SuperAdmin | 指派、轉派及優先級覆核／覆寫；必須驗證狀態、RowVersion、理由並寫入歷程與 Audit；不得繞過案件狀態或併發規則 |

### 客服工作台權限

- 一般客服案件進入自領佇列，`CustomerService` 可以領取未指派的一般客服案件。
- 日常案件處理統一要求 `SupportTicket.Handle`；`SuperAdmin` 單一角色不符合此 Policy。若 SuperAdmin 帳號也要回覆、寫內部備註、自領或執行一般案件狀態操作，必須另外被授予 `CustomerService` 或 `CustomerServiceSupervisor`。
- 一般檢舉進入獨立檢舉佇列，`CustomerService` 可以自領；高風險檢舉必須通過 `Report.HighRiskReview`。
- 指派、轉派與優先級覆核／覆寫統一要求 `SupportTicket.Supervise`；`CustomerServiceSupervisor` 與 `SuperAdmin` 可以執行，但仍不得跳過狀態、RowVersion、理由、歷程或 Audit。
- 統一工作台會顯示客服、檢舉及退貨摘要，但不因此授予跨領域處理權限。
- 檢舉及退貨保留各自佇列；一般檢舉沿用 CustomerService，退貨仍依售後權限承接及處理。
- 所有自領、指派、轉派、優先級異動及 SLA 升級都必須留下歷程與稽核紀錄。

## 個資存取

- 一般客服只看得到遮蔽後的 Email、電話及必要訂單資訊。
- `OrderManager` 可以查看完成履約所需的訂單收件快照，包括收件人、電話、地址、配送方式及必要聯絡資料；此權限不延伸到會員完整檔案或其他訂單。
- 訂單收件快照與會員目前資料分開保存；會員日後修改個資不改變既有訂單。
- `PrivacyAdmin` 與 `SuperAdmin` 才能查看完整會員檔案。
- 查看完整個資本身也必須留下稽核紀錄。

## 庫存與物流高風險操作

- `InventoryManager` 與 `SuperAdmin` 可以手動釋放仍為 `Active` 的庫存保留；必須二次確認、填寫原因並稽核。
- `OrderManager` 與 `SuperAdmin` 可以修改超商包裹限制；修改必須建立設定版本。
- `OrderManager` 與 `SuperAdmin` 可以新增、編輯或停用示範門市；`CatalogManager` 只有檢視權限。已被訂單引用的門市不得實體刪除，所有異動使用 RowVersion 並寫入 AuditLog。
- `OrderManager` 可以執行批次出貨，但每筆訂單仍需獨立通過狀態、付款、組裝、庫存及物流驗證。

## 管理員登入安全

- 管理員強制啟用 TOTP 雙因素驗證。
- 支援 Google Authenticator 與其他標準 TOTP App。
- 支援 QR Code 綁定、Recovery Codes、重新綁定與解除流程。
- Recovery Code 使用及 2FA 設定異動必須稽核。

## 稽核紀錄

重要商業操作應寫入資料庫 `AuditLog`，不能只依賴一般文字 Log。

- Owner／Assignee 等現行作業欄位使用 Identity FK；append-only History 的 `ActorUserId` 可為 Null。交易資料仍相依帳號時，只能停權、軟刪除或匿名化，不實體刪除 Identity。
- 中央 AuditLog 保存不可變 Actor PublicId、角色快照、操作、理由與結果；各領域 History 不重複保存完整 Audit Snapshot。

- `SecurityAdmin` 可依職責查詢登入、角色、安全與系統操作稽核；`PrivacyAdmin` 可查詢個資存取、匿名化與資料匯出稽核。
- 只有 `SuperAdmin` 可匯出 AuditLog；所有查詢與匯出本身也必須被稽核。
- 第一版不提供 Legal Hold 操作介面，只在資料模型保留延長保存期限與原因的設計點。
