# DEC-BATCH-021｜退款分攤與折讓映射裁定

## 背景

PR #6 的折讓 Reader 只將 `ItemRefund` 轉成折讓明細，會漏掉原發票已收取、且本次退款確實退還的原始運費與組裝費；若完整退款包含商品、原始運費與組裝費，折讓金額會低於原發票可折讓金額，發票也可能無法正確進入 `FullyAllowed`。另一方面，退貨寄回運費與退款扣回並不是原發票銷售金額，不能為了讓現金退款總額相等而建立虛構或負值折讓明細。

## 正式決策

| ID | 決策 |
|---|---|
| DEC-P298 | 成功 Refund 轉成模擬折讓時，`ItemRefund` 建立折讓明細；`OriginalShipping` 只有在原發票確實收取且本次退款退還該金額時建立折讓明細；`AssemblyFee` 只有在原發票確實收取且本次退款退還該金額時建立折讓明細。`ReturnShipping` 不屬於原發票銷售金額，不建立折讓明細。`DiscountClawback` 與 `ShippingClawback` 是退款扣回，不建立獨立負值折讓明細；兩者仍依 DEC-P278 參與退款淨額計算。`OtherAdjustment` 第一版禁止寫入，也不得建立折讓明細。折讓只能引用同一張原發票的交易快照，累計數量與金額不得超過原發票各明細的可折讓上限。 |

## 最低成本分析

1. 維持 Reader 只處理 `ItemRefund`：完整退款會漏記原始運費與組裝費，無法滿足財務完整性與 `FullyAllowed` 狀態，不採用。
2. 只在 PR 留言提醒開發者：無法形成後續 Reader、Writer、測試與對帳的權威規則，不採用。
3. 沿用既有七類 `RefundAllocation`、原發票交易快照及折讓明細，補上固定映射與測試：不新增 Schema、服務或套件即可滿足完整性，採用。
4. 將所有分攤都轉成正／負折讓明細：會把退貨寄回運費與退款扣回事後寫成原發票銷售內容，扭曲財務歷史，不採用。

## 商業影響

- 受影響者：收到退款與折讓結果的顧客、執行退款的財務管理員，以及後續對帳與稽核人員。
- 目前風險：含原始運費或組裝費的退款可能少開折讓；退款扣回或退貨寄回運費也可能被錯誤寫進原發票折讓。
- 觸及頻率：每次成功 Refund 建立模擬折讓時；實際退款量未提供，不建立虛假估算。
- 預期成果：每種退款分攤只有一個明確處理方式；完整退款涵蓋原發票可折讓商品、原始運費與組裝費，且不把非原銷售金額寫入折讓。
- 建置與持續成本：調整既有 Reader／Calculator 與自動化測試；不新增外部服務、套件、Schema 或持續費用。
- 主要風險成本：若原發票交易快照無法識別原始運費或組裝費，PR #6 必須等待契約補齊，不得以目前商品或設定重算歷史。
- 信心：高；七類分攤方向、原發票不可變歷史與折讓累計上限均已有正式契約。
- 成功指標：七類映射測試通過；商品＋原始運費＋組裝費完整退款能建立完整折讓並進入 `FullyAllowed`；ReturnShipping、兩種 Clawback 與 OtherAdjustment 不建立折讓明細；累計上限仍受保護。
- 停止／回復條件：無法由同一張原發票交易快照辨識可折讓來源時拒絕建立折讓，不得猜測或改讀目前價格；政策變更時以新決策覆寫本紀錄，不修改既有歷史折讓。
