# 組員分工與資料表設計任務書

本文件整理自 [[05-規劃/重新分工看板]] 的目前結果，供五位組員開始閱讀需求、確認模組邊界並提出資料表設計。這一階段只進行分析與提案，不直接建立 Entity、DbContext Mapping 或 Migration。

## 本階段目標

每位組員需要回答三件事：

1. 自己負責的功能需要保存哪些資料，哪些只是查詢或計算結果。
2. 現有資料字典是否已經足以實作；若不足，要修改或新增什麼，以及理由。
3. 其他模組要如何安全取得資料，是否需要 API、Application Query、DTO、Outbox Event 或同一交易協調。

## 共同限制

- 不為畫面上的每個欄位直接新增資料庫欄位；先確認資料來源與生命週期。
- 不以 JSON 逃避可查詢、可限制的正式欄位；只有已定義 Schema Version 的彈性資料才考慮 JSON。
- 不跨模組直接使用別人的 Repository 或修改別人的資料表。
- 對外 API 使用 `PublicId`，不可暴露內部 `bigint Id`。
- 交易資料、狀態歷程、庫存異動、付款、退款與 Audit 不可 Cascade 刪除。
- 訂單、付款、物流及發票等歷史資料需要快照時，必須標示 `transaction_snapshot`，不能與主資料混為一談。
- 反正規化必須先提出量測與重建方式；第一版報表先查正規化交易來源。
- 在跨模組 ERD Review 通過前，不建立正式 Migration。
