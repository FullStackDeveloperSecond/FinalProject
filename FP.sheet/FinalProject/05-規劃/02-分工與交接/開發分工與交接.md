# 開發分工與交接

本頁是五人正式開發主責與交接的唯一文字入口；[[05-規劃/02-分工與交接/重新分工看板]] 是工作包分配的互動介面，拖曳調整只有在組長確認並同步回寫本頁與決策紀錄後才生效。工作包完整範圍以 [[05-規劃/02-分工與交接/重新分工項目池]] 為準。時程與整合會議見 [[05-規劃/01-時程與進度/40天開發計畫]]；逐項測試主責見 [[03-架構/08-測試與驗收/M功能測試案例目錄]]；每次實作異動必須依 [[日誌/日誌|開發日誌模板]] 留下交接資訊。

### DEC-BATCH-012 跨模組固定交接

- `terry → yinyin／Checkout`：提供 COD Eligibility Query／DTO，輸入 SKU、組裝與配送摘要，輸出可否 COD 及受控理由碼；不得開放 Repository。Terry 同時擁有 Order-only Reservation、完整 ReviewStatus、ImportBatch 契約與營運報表公式修正版。
- `terry → kafen`：只提供 Carrier／ShippingMethod Lookup；退貨寄回物流不進 Terry 的 outbound Shipment Aggregate。
- `kafen`：擁有 ReturnShipment／Event、退貨補件流程、正式檢舉狀態與 12 欄工作台來源投影；ReturnRequest 不依賴 SupportTicket。
- `yinyin`：擁有 Checkout-bound CouponRedemption、訪客 HMAC 使用鍵、Payment／Refund／Invoice 契約；跨模組資料只經公開 Query／DTO。
- `alex`：覆核 Identity FK／匿名化、AuditLog、HMAC Secret 與三方 Schema 整合；本批只更新規格，不建立 EF Core Migration。

## 固定配對與驗收

- `haru ↔ yinyin`：互為第一線備援與測試覆核。
- `kafen ↔ terry`：互為第一線備援與測試覆核。
- `alex`：負責跨模組契約、安全與最終整合，並在第一線配對無法接手時作第二線備援。
- 全部 AI 實作由 `alex` 主責；`terry` 提供商品、庫存、組裝、相容性及 M-15 營運報表資料契約與測試覆核，`kafen` 提供客服與案件資料契約及測試覆核，`haru` 提供登入、同意與本人訂單授權案例。AI 功能不得由主責人單獨完成最終驗收。
- 主責人不得單獨完成自己功能的最終驗收；至少取得固定備援人的測試覆核。
- 備援人需能依日誌啟動、呼叫、測試及修正該模組，不能只知道畫面名稱。

## 共用資料取得原則

跨模組不得直接讀取其他模組的 EF Core Repository、資料表或內部 Entity。依下列順序取得資料：

1. 前端透過已發布 API 與 OpenAPI 產生的 TypeScript Client。
2. 後端跨模組查詢透過 Application 層公開 Query／Service 契約及專用 DTO。
3. 同一商業交易需要跨模組一致性時，由 Application Use Case 協調，不由前端串接補償交易。
4. 非同步副作用透過 Outbox Event；Event 名稱、版本與 Payload 必須記錄在開發日誌。
5. 對外只使用 PublicId；不得把資料庫 bigint Id 放入 API、URL、Log 或跨模組契約。

## 開發日誌責任

每次符合任一條件都必須建立日誌：

- 新增或修改 API、DTO、Enum、錯誤碼、Policy 或狀態轉移。
- 新增資料表、欄位、索引、Migration 或資料回填規則。
- 新增跨模組 Query、Service、Event 或共用 Composable／Store。
- 更改其他成員會呼叫的資料取得方式、命名、限制或預設值。
- 完成一個可交接功能、修正跨模組問題，或留下未完成／阻塞工作。

日誌只說「改了會員功能」不算完成；必須讓另一位成員知道：可使用什麼契約、輸入輸出是什麼、從哪裡取得、禁止怎麼取，以及是否有相容性影響。
