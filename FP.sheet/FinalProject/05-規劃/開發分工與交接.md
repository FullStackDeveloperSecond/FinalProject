# 開發分工與交接

本頁是五人開發分工的主要入口。時程與整合會議見 [[05-規劃/40天開發計畫]]；逐項測試主責見 [[03-架構/M功能測試案例目錄]]；每次實作異動必須依 [[日誌/日誌|開發日誌模板]] 留下交接資訊。

## 分工總覽

| 成員 | 核心主責 | 第一線備援／交叉覆核 | 必須交接的主要界面 |
|---|---|---|---|
| `alex` | 系統架構、共用能力、跨模組整合、文件、Code Review、小型共用模組 | 所有模組第二線備援；最終整合驗收 | 共通 API、授權 Policy、錯誤碼、PublicId、Outbox、Secrets、CI 與跨模組契約 |
| `haru` | 會員、登入、Email 驗證、忘記密碼、管理員登入與 TOTP、會員／訪客訂單存取 | `yinyin` | Current User、會員 PublicId、登入狀態、角色／Policy、GuestOrderAccessToken、通知事件 |
| `kafen` | 客服、檢舉、退貨案件、SLA、統一案件工作台、營運報表 | `terry` | 案件 PublicId、訂單只讀摘要、附件、SLA 時間、退貨狀態、報表 Filter／Row DTO |
| `yinyin` | 優惠券、促銷、模擬付款、退款財務執行 | `haru` | Cart 金額、優惠分攤、PaymentAttempt、Refund、Idempotency-Key、付款／退款 Outbox |
| `terry` | 商品、SKU、分類／規格、搜尋、自由組裝、相容性、購物車、庫存、物流 | `kafen` | Product／SKU PublicId、價格／庫存快照、Compatibility Result、Cart、Reservation、Shipment |

## 固定配對與驗收

- `haru ↔ yinyin`：互為第一線備援與測試覆核。
- `kafen ↔ terry`：互為第一線備援與測試覆核。
- `alex`：負責跨模組契約、安全與最終整合，並在第一線配對無法接手時作第二線備援。
- 主責人不得單獨完成自己功能的最終驗收；至少取得固定備援人的測試覆核。
- 備援人需能依日誌啟動、呼叫、測試及修正該模組，不能只知道畫面名稱。

## 共用資料取得原則

跨模組不得直接讀取其他模組的 EF Core Repository、資料表或內部 Entity。依下列順序取得資料：

1. 前端透過已發布 API 與 OpenAPI 產生的 TypeScript Client。
2. 後端跨模組查詢透過 Application 層公開 Query／Service 契約及專用 DTO。
3. 同一商業交易需要跨模組一致性時，由 Application Use Case 協調，不由前端串接補償交易。
4. 非同步副作用透過 Outbox Event；Event 名稱、版本與 Payload 必須記錄在開發日誌。
5. 對外只使用 PublicId；不得把資料庫 bigint Id 放入 API、URL、Log 或跨模組契約。

## 開發日誌責任

每次符合任一條件都必須建立日誌：

- 新增或修改 API、DTO、Enum、錯誤碼、Policy 或狀態轉移。
- 新增資料表、欄位、索引、Migration 或資料回填規則。
- 新增跨模組 Query、Service、Event 或共用 Composable／Store。
- 更改其他成員會呼叫的資料取得方式、命名、限制或預設值。
- 完成一個可交接功能、修正跨模組問題，或留下未完成／阻塞工作。

日誌只說「改了會員功能」不算完成；必須讓另一位成員知道：可使用什麼契約、輸入輸出是什麼、從哪裡取得、禁止怎麼取，以及是否有相容性影響。
