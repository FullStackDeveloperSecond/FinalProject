## 必須維持的規則

- **修改不影響既有訂單。** 金額、名稱、門檻與規則版本在下單當時已抄進 `OrderCoupon`
  （優惠券規則「訂單快照與折扣分攤」），所以進行中的券也能改。
- **規則變動必須推進 `RuleVersion`。** 那是「兩張訂單套用的是不是同一版規則」的唯一憑據。
- **只改 `NameZhTw` 不推進 `RuleVersion`。** 名稱不參與計算，且已另抄進
  `OrderCoupon.CouponName`；推進版本只會讓稽核分不清哪一次才是真正的規則異動。
- **有 Redemption 後 `Code` 凍結。** 優惠碼已寫進 `OrderCoupon` 快照，改掉會讓歷史訂單
  指向一個對不上的代碼。凍結檢查比對**正規化後的值**，不是「有沒有出現在請求裡」——
  管理端送的是整份規則，Code 一定會被送回來。
- **`Expired`／`Disabled` 是終態，不接受修改。**
- **修改不是狀態轉移。** 把結束時間改到過去也不會自動到期；進入 `Expired` 只能由
  `MarkExpired` 觸發。
- **後台顯示的使用量必須與試算引擎同一個定義。** 沿用
  `CouponRuleReader.OccupiesUsageSeatAt`（Consumed 加上尚未過期的 Reserved）。
  數字不同會讓管理員依一個不存在的餘額做決策。
- **無總量上限時 `remainingCount` 是 `null`，不是 0。**
- **分頁超出範圍回 400，不夾擠。** API共通規範第 88 行明文。
- **未知的分類／商品 PublicId 一律拒絕**，不靜默略過 —— 略過會產出一張適用範圍與送出
  內容不同的券，而畫面上看不出來。

## 修正過程中發現的三個缺陷

### 1｜UTC 缺陷（會壞掉每一次 PUT 往返）

SQL Server 的 `datetime2` 不保存時區，EF 讀回來一律是 `DateTimeKind.Unspecified`。
後果有兩個：System.Text.Json 序列化時不加 `Z`，客戶端只能猜；而把同一個值原樣送回
`PUT` 時會被服務自己的 UTC 檢查擋成 400。

已在 `ToDto` 以 `AsUtc` 修正。**這是 SQL Server Provider-backed 測試抓到的，
InMemory 抓不到。**

需要注意的是：**專案裡沒有任何全域 UTC 處理**（`DoSelectDbContext` 與各
Configuration 都沒有 value converter），所以其他模組的 DTO 應該有同樣的問題。
這超出本工程包範圍，已另行回報。

### 2｜`{action}` 是 MVC 保留的路由 token

`[HttpPost("{id:guid}/actions/{action}")]` 會與 Action Method 名稱的路由值衝突，
該路由永遠比對不到、一律回 404。改成 `{couponAction}` 並以 `[FromRoute]` 繫結，
URL 維持 `/actions/{activate|pause|disable}` 不變。

### 3｜`TestAuthHandler` 沒有註冊 `Coupon.Manage` 測試 Policy

只註冊了 `Member`、兩個 Support 與 `Invoice.Manage`，因此新端點會落回真實 Policy 的
Admin scheme，測試一律 401。已補上（與 `Invoice.Manage` 只差多允許 MarketingAnalyst）。

## 已知缺口（需要 alex 裁定）

**`activate`／`pause`／`disable` 的 `reasonCode` 與 `note` 目前沒有寫進任何地方。**

依 DEC-P289 的原則，執行理由只能寫中央 Audit、不得在 `Coupon` 新增欄位，但
`AuditWritePolicy` 的動作白名單沒有任何 `coupon.*` 項目，而該白名單屬 alex 的共用
Audit 元件，不由本工程包新增。

兩個值仍照契約驗證（必填、長度上限），但不會被保存。已在
`EfAdminCouponService.ExecuteActionAsync` 的 XML 註解明確標示，不只寫在 PR 說明。

alex 今天在 PR #16 的 P2 也指出相關限制：`AuditWriteRequest.Reason` **上限 64 字，
只接受 ASCII 英數與 `._-:`**。因此就算白名單補上 `coupon.*`，`note` 仍需要一個
定義好的安全表示法，不能直接串進去。

## 一個決策，想請 review 時確認

Action 白名單只有三個值，但 Entity 依來源狀態提供三條不同的啟用路徑
（`ActivateNow`／`ActivateScheduled`／`ReactivateAfterQuotaRelease`），而且沒有
`schedule` 動作。

本次讓 `activate` 依目前狀態分派，其中**尚未進入有效期間的 `Draft` 會走
`ScheduleForLaterStart`**。理由是若在此直接拒絕，`Scheduled` 會變成 API 到不了的狀態。
若這個讀法不對，改回拒絕只是一行，但 `Scheduled` 就需要第四個動作。
