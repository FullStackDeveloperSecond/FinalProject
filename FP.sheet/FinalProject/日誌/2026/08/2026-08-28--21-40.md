## P1｜歷史已退款數量的來源不成立

`RefundTrustedInputsReader` 把 `OrderItem.ReturnedQuantity` 當成
`AlreadyReturnedQuantity`。查證後比 alex 留言寫的更糟：

- Returns 模組在 `ReturnPorts.cs:157` 明文寫它**不維護**那個欄位。
- 全專案唯一呼叫 `Order.RecordReturnedQuantity` 的地方是
  `OrderServiceFixture.cs:193`（測試種子），**沒有任何生產程式碼寫入**。

所以那個值**恆為 0**。影響 `RefundCalculator` 五處：剩餘可退數量、最後一批折扣
尾差、完整退貨判斷、原運費退還、優惠券追回。

**而完整退貨判斷正是我上一輪拿來決定「要不要要求運費快照」的那條** —— 上一輪的
修正建立在一個恆為 0 的輸入上。

改為在同一筆 Serializable 交易內，從本模組自己寫下的
`RefundAllocation(ItemRefund).Quantity` 累計。狀態與排除條件刻意與
`CalculateRefundableBalanceAsync` 一致：只算 `Succeeded`、排除本次退款自身。

### 測試設計：讓淨額相同、只有路徑不同

新增 `ASecondPartialRefundSeesTheQuantityTheFirstOneAlreadyRefunded`。
訂單一列 3 件、單價 500、訂單級折扣分攤 100（除以 3 除不盡）：

| | 已退 | 本次 | 折扣分攤 | 淨額 | 完整退貨 |
|---|---|---|---|---|---|
| 第一次 | 0 | 2 | Round(100×2/3)=66.67 | 933.33 | 否 |
| 第二次 | 2 | 1 | 100−66.67=33.33 | 466.67 | **是**，加退原運費 60 → 526.67 |

缺陷未修時，第二次算成 0+1≠3 的部分退貨：**淨額同樣是 466.67**，只是少了
OriginalShipping 60。所以只斷言金額抓不到，必須連分攤組成一起斷言。

已實測：把讀取端改回恆為 0，這條測試會紅（第二筆被對帳擋成
`refund_calculation_mismatch`）。

## P2｜並行測試沒有證明競爭路徑

alex 說對了：舊 barrier 放在 `ExecuteAsync` **之前**，放行時兩筆 SQL 交易都還沒
建立。我寫在那段的註解「兩個交易因此真的同時存在」，程式碼並沒有做到。

### 兩條走不通的路，記下來

1. **把 barrier 移進交易內、讀取之後** —— `DbDataReader` 還開著，卡在那裡會讓
   同一條連線後續的 rollback 直接拋「已經開啟與這個 Connection 建立關聯的
   DataReader」。
2. **把 barrier 移到寫入之前** —— 在持有 Serializable 範圍鎖時等待對方，對方會卡
   在那些鎖上永遠到不了會合點，兩邊互等到逾時。**任何要求雙方到齊的同步點，
   放在交易內都是死結。**

### 實際的競爭點不在退款層

用 command interceptor 記錄兩邊每道 SQL 的時間後看到：

```
FIRST   292ms  INSERT INTO [IdempotencyRecords] ...
SECOND  292ms  INSERT INTO [IdempotencyRecords] ...
SECOND 1915ms  （被擋 1.6 秒後才繼續）
FIRST  2510ms  INSERT INTO [IdempotencyRecords] ...   ← 整筆交易重跑
```

**競爭發生在共用 Executor 寫冪等紀錄的那一刻**，早於退款的餘額讀取與
rowversion 比對。被擋住的那筆整個交易被回滾重跑，重跑時才讀到餘額不足。

### 最終做法：強制競爭，並量測它

只靠「同時起跑 + 量測」不夠穩。在**滿載的完整測試回合**中，兩筆仍可能錯開而循序
完成 —— 我第一版就是這樣：單獨跑連綠 5 次，併進整個 Infrastructure 回合跑就紅了
一次（331ms 完成，代表根本沒有重疊）。

改為讓第一筆在**讀完可退款餘額之後、寫入之前**多握住交易兩秒。此時它已持有
`Refunds(OrderId)` 的 Serializable 範圍鎖，第二筆的寫入必定卡在上面；放行後兩邊
互相需要對方的鎖，由資料庫判定死結。這個持有是**單向**的（只等時間、不等對方），
所以不會重蹈上面第 2 點的死結。自己刻意的持有不計入「被對方擋住」的量測。

證據仍然是量測出來的，不是假設出來的：

- 交易重跑次數：數 `INSERT INTO [IdempotencyRecords]`，兩邊合計 ≥ 3
  才代表有一筆真的被資料庫回滾重跑。循序完成永遠是 2。
- 交易內最長等待 ≥ 200ms：被對方鎖擋住的證據。

已實測：改成循序執行時這條測試會紅，訊息是「兩筆交易本體合計只執行 2 次，
沒有任何一筆被資料庫回滾重跑」。加上強制持有後，單獨跑與整個 Infrastructure
回合各連跑 3 次全綠。

## P3｜清理失效註解

`ExecuteRefundService.cs` 的 `RefundTrustedInputs` 還寫著三項可信欄位「在資料庫
沒有任何持久化來源」「讀取端目前一律回 null」，但上游早就落地。已改成描述現況，
並保留 E1 的拒絕規則（任一項缺漏就整筆拒絕，不得猜測）。
`RefundExecutor.FindTrustedInputsAsync` 的同類註解一併更新。

## 必須維持的規則（新增）

- **歷史已退數量只能取本模組自己寫下的分攤。** 其他模組的欄位沒有人維護。
- **交易內不得放需要雙方到齊的同步點。** 那是在持有鎖時互等。
- **並行測試要量測交易重跑與等待，不能只看結果。** 循序完成也會得到「一成功
  一失敗」。
- **並行測試要在完整測試回合裡驗證，不能只單獨跑。** 單獨跑穩定不代表滿載時
  仍會重疊 —— 這次就是單獨連綠 5 次、併進回合才紅。
