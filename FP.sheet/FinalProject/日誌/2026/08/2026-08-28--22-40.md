## P2｜管理員 activate 不得消耗系統事件

權威狀態機（`狀態機設計.md`「優惠券狀態」）寫得很清楚：

- `Scheduled → Active` 是**到達開始時間**的事件。
- `Exhausted → Active` 是**名額返還**的事件。
- `activate` 只接受 `Draft` 或符合條件的 `Paused`。

我原本依來源狀態把同一個管理員 `activate` 分派成三條轉移，等於讓管理端點吃掉
scheduler 與名額返還的轉移。**而且稽核全部記成 `coupon.activate`** —— 事後再也
分不出這張券是被排程喚醒、名額返還，還是有人手動提前放行，而那三件事的責任
歸屬完全不同。

已改為兩者都回 `coupon_state_conflict`。已裁定的 B1 維持不變：未開始的 `Draft`
執行 activate → `Scheduled`。

### 我寫在註解裡的理由不成立

原註解寫「白名單沒有 `schedule`，若在此拒絕，`Scheduled` 將是一個 API 到不了的
狀態」。alex 指出這不是理由 —— **`Scheduled` 的進入路徑就是未開始 Draft 的
activate（B1），本來就到得了**；而 `Scheduled → Active` 本來就是背景事件，
不需要一個管理員 API 去取代它。註解已改寫。

## 差點又寫出一條「為了錯誤理由變綠」的測試

`AnAdministratorCannotActivateAScheduledCoupon` 第一版是這樣寫的：建立一張三天後
才開始的券 → activate 變成 `Scheduled` → 再 activate 一次，斷言 409。

**它在舊實作下也是綠的。** 因為舊實作走 `ActivateScheduled`，而那張券還沒進入
有效期間，Entity 會因為「尚未到開始時間」而拒絕 —— 拒絕的理由根本不是我要測的
那一條。

修正：先把時鐘推到開始時間之後（`CreateServiceAt(context, NowUtc.AddDays(4))`），
讓「條件其實都滿足、只差還沒到排程喚醒」的那一刻成立，這時舊實作會成功轉成
`Active`，測試才真的擋得住。

已實測：把兩個 case 加回舊實作，兩條測試都變紅。第一版只有 Exhausted 那條會紅。

**這與 PR #16 那條並行測試是同一種錯誤** —— 測試是綠的，但綠的原因不是我以為的
那個。反向驗證（把修正拿掉看會不會紅）是唯一能抓到它的方法。

## 兩條新測試

- `AnAdministratorCannotActivateAScheduledCoupon`
- `AnAdministratorCannotActivateAnExhaustedCoupon`

兩條都額外斷言**狀態與 RowVersion 原封不動**，確認拒絕路徑零寫入。

HTTP 層的 409 對應已由既有的 `AnIllegalTransitionSurfacesAsCouponStateConflict`
覆蓋，沒有重複再寫一條。

## 必須維持的規則（新增）

- **系統事件的轉移不得由管理員 action 消耗。** 否則稽核失去事件來源。
- **拒絕路徑要斷言 RowVersion 沒變。** 只斷言狀態沒變，擋不掉「改了又改回來」。
