## P2｜守門漏掉 query comprehension，而我又宣稱它不會漏

`ReadTableMemberAccesses` 只用 `alias =>` 認 lambda 參數。但 `RefundExecutor`
的角色查詢用的是 C# query 語法：

```csharp
from userRole in _context.UserRoles.AsNoTracking()
join role in _context.Roles.AsNoTracking() on userRole.RoleId equals role.Id
where userRole.UserId == admin.Id && role.Name != null
select role.Name!
```

**這段沒有任何 `alias =>`**，所以 `boundTable` 是空的，四個欄位存取
（`userRole.RoleId`、`userRole.UserId`、`role.Id`、`role.Name`）全部沒有進入白名單斷言。

我上一輪寫「解析不了的寫法不會被誤放行」—— **那句話當時不成立**。
而我拿來支撐它的 `Orders.GrandTotal` 反向驗證只涵蓋 lambda 寫法，
是用一個窄的驗證去支撐一個寬的宣稱。這是這幾輪同一類錯誤的第三次：
敘述比實作多。

## 修正順序：先讓漏洞自己現形

依 alex 建議先加 **fail-closed** 斷言，而不是先修解析器 ——
這樣漏洞是被測試照出來的，不是我宣稱的。

加上去之後第一個被照出來的其實**不是** query syntax，而是：

```
這段查詢用到 RefundAllocations，但守門測試解析不出任何可檢查的參數
_context.RefundAllocations.Add(new RefundAllocation(...))
```

那是**寫入本模組自有的表**，本來就沒有參數可解析、也沒有欄位需要比對。
所以 fail-closed 必須更精準：**只在這段碰到「有欄位上限」的表時才要求解析得出參數**。
全部是自有表（`*`）就不要求。

同時把「資料表比對」與「參數解析」拆開：即使一個參數都認不出來，
用到白名單以外的表仍然要當場失敗。

## 解析器支援兩種寫法

| 寫法 | 綁定方式 |
|---|---|
| method syntax | `_context.Orders.Where(candidate => ...)`：參數宣告在表**之後**，綁到前面最近的表 |
| query syntax | `from alias in _context.Table`、`join alias in _context.Table`：參數寫在表**前面**，直接一次綁定 |

兩種規則相反，所以 query syntax 必須單獨認，不能沿用「取前一個 marker」。

## 為什麼 fail-closed 比「把語法列舉齊全」重要

我列舉語法的能力已經被證明不可靠兩次（先是 Join，再是 query syntax）。
fail-closed 讓「沒看懂」直接變成紅燈，以後任何我沒想到的寫法都會被擋下來，
而不是靜默通過。**這條規則本身比它現在擋下的任何一種語法都重要。**
