## 更改內容

### 摘要

Rebase `feature/build-compat-api`到最新 `dev`（含中央 Audit Log、DES-21 退款快照兩支新 Migration）後，EF Core 的 `PendingModelChangesWarning` 第一次真正觸發，發現 `SkuCompatibilityAttributes`／`SkuStorageInterfacePorts`（後者是 round-4 review 修正引入的結構化儲存埠資料表）從未產生過 Migration，只存在 C# Model 裡。已用 `dotnet ef migrations add AddSkuStorageInterfacePorts` 補上，讓既有 3 個 Migration 完整性測試（`CentralAuditSqlServerTests`／`InvoiceAllowanceWriterSqlServerTests`／`Des21MigrationSqlServerTests`）恢復通過。**依最新版 `Terry-商品庫存物流與報表工程包.md` 的規則（「不得在功能分支自行 scaffold／apply 新 Migration；Schema 需求交 alex 走 Migration Gate」），這支 Migration 在合併前需要 alex 的 Migration Gate 覆核，不可視為已自行核准。**

### 新增

### 命名與型別

| 名稱 | 型別／格式 | 是否可為空 | 說明／範例 |
|---|---|---|---|
| `SkuStorageInterfacePorts.InterfaceCode` | `varchar(64)` | 否 | 例如 `SATA`、`M2_NVME` |
| `SkuStorageInterfacePorts.PortCount` | `int`，DB CheckConstraint `> 0 AND <= 32` | 否 | 該介面在此 SKU 上實際埠數 |

### 必須維持的規則

- 每個 `(SkuId, InterfaceCode)` 只能有一筆（`UX_SkuStorageInterfacePorts_SkuId_InterfaceCode`），避免 round-4 review 指出的「同一主機板可以有多筆 SATA 埠數、讀取順序不確定」問題。

### 禁止或不建議的取用方式

- 不可由前端直接存取資料庫。
- 不可跨模組直接操作其他模組的 Repository 或資料表。
- 不可對外暴露資料庫內部 `bigint Id`；對外識別使用 `PublicId`（此表本身無 PublicId，僅供內部規則引擎使用）。
- 其他：**不得在其他功能分支自行 scaffold 第二支處理相同缺口的 Migration**——這支已經涵蓋 `SkuCompatibilityAttributes` 與 `SkuStorageInterfacePorts` 兩張表。
