## 第三次同一個毛病

這一輪他找到的繞法是：

```csharp
this._context.Orders.Select(order => order.GrandTotal);
```

上一版的 `TableAccesses` 與 `BypassViolations` 都要求 `access.Expression is IdentifierNameSyntax`。
`this._context` 是 `MemberAccessExpressionSyntax`，所以**完全不會進入資料表與 bypass 檢查**；
而欄位宣告仍在，「找不到入口」那條 fail-closed 也**不會觸發** —— 結果是回報零違規。

而我上一輪在同一個檔案的註解裡寫的是「名稱怎麼取都躲不掉」。**這已經是第三次
我宣稱的比實作做到的多。**前兩次是 regex 版本，這次換成語法樹之後仍然一樣，
因為我處理的還是「我想得到的形狀」。

## 這次改成問型別，不問形狀

用 `SemanticModel.GetTypeInfo` 判斷接收者的型別是不是 `DoSelectDbContext`。
`this.`、`base.`、括號、cast、區域別名全部一視同仁 —— **判斷的是型別，不是寫法**，
所以「下一種形狀」不存在。

三層，由精確到保守：

1. **語意**：型別是 `DoSelectDbContext` 就算
2. **語法備援**：語意解析不出來時，遞迴拆掉 `this`／`base`／括號／cast／`!` 取出識別字
3. **fail-closed 網子**：兩者都認不出來，但接收者裡出現已知的 DbContext 識別字 —— 直接違規

第三層是 alex 明確要求的「對任何已知 DbContext reference 的未分類用法 fail-closed」。

## 網子第一版太寬，兩次才收斂

第一版的網子把 `_context.Refunds.AsNoTracking().SingleOrDefaultAsync` 也判成違規 ——
那個外層存取的接收者是 `IQueryable` 不是 DbContext，但它的子樹裡有 `_context`。
守門立刻對**合法的正常寫法**變紅。

收斂成：先算出所有「接收者確實是 DbContext」的存取，掛在它們後面的鏈一律跳過。
留下來的才是「DbContext 被傳來傳去而不是被點出來」的形狀，例如 `Pick(_context).Orders`。

第二次撞到的是 `new RefundTrustedInputsReader(_context).FindAsync(...)` ——
把 context 交給**另一個同樣列在白名單裡**的 Refund 元件。那是允許的：那個元件有自己的
資料表與欄位清單，會在它自己的檔案裡被檢查。所以多傳一個「已核准元件」清單進來，
`new` 出白名單內的型別放行，白名單外的照樣違規。

## 備援路徑差點沒被測到

補完之後跑破壞式驗證：把 `IsContextReference` 退回只認裸識別字，
`this._context` 的兩條變紅 —— 但 `var db = this._context` 那條**仍然是綠的**。

原因是語意模型直接解析出 `db` 的型別是 `DoSelectDbContext`，根本用不到我寫的語法備援。
也就是說**備援路徑一行都沒有被執行過**，真的需要它的時候才會發現壞掉。

加了 `useSemanticModel: false` 的測試專用開關，把兩條 receiver 測試各跑一次語意版與
語法版。再跑一次同樣的破壞式驗證，語法版那條就紅了。

**要記的是**：有備援分支的程式，一定要有辦法從外面強制走備援，否則它等於沒寫。

## 另一條也綠得沒有意義

`CatchesSetReachedThroughThis` 原本斷言「訊息裡有 `Set` 這三個字」。
但 fail-closed 網子的訊息會把原文 `this._context.Set<object>` 一起印出來，也含有 `Set` ——
所以那條測試分不出是 **bypass 規則**抓到的，還是網子抓到的。改成斷言
「繞過 B1 的逐欄位白名單」這句 bypass 專屬訊息之後，破壞式驗證才讓它變紅。

## 2026-08-31 第四輪：DbContext 當成「值」傳出去仍能逃逸

alex 找到的兩種寫法：

```csharp
ExternalHelper.Read(_context);   // member access 是 ExternalHelper.Read，_context 在引數裡
holder.Context = _context;       // member access 的 receiver 是 holder，_context 在指派右手邊
```

上一版的網子只巡覽 `MemberAccessExpressionSyntax` 並檢查**它的接收者**，
所以這兩種的 `_context` 都不在任何接收者裡，完全不會進入檢查；
而欄位宣告仍在，「找不到入口」的 fail-closed 也不會觸發。

**第四次同一個模式**：我每次都在補「我想得到的形狀」。前三次是 regex、語法樹、
接收者型別；這次的教訓是**問錯了問題** —— 我一直在問「這個存取的接收者是不是 DbContext」，
而該問的是「**這個 DbContext 最後被拿去做什麼**」。

### 改成逃逸分析

列出檔案裡所有指向 DbContext 的 reference，逐一看它的用途。只允許四種：

1. 當作 `ctx.Table`／`ctx.Set`／`ctx.Database` 的接收者（各自有規則檢查）
2. 欄位或區域變數的初始化，且被指派的名字本身也在追蹤範圍內
3. 指派給另一個已追蹤的名字，或寫進自己已追蹤的欄位
4. 交給白名單內 Refund 元件的建構子，或 `ArgumentNullException.ThrowIfNull`

其餘一律 fail closed：交給任意 method／delegate、指派到未知物件的屬性、直接 `return` 出去。

### 過程中踩到兩個自己的坑

**一｜型別名稱也被當成 reference。** `private readonly DoSelectDbContext _context;` 裡的
`DoSelectDbContext` 是個 `IdentifierNameSyntax`，`GetTypeInfo` 對它也回 DbContext 型別，
於是每個欄位宣告都變成一次「逃逸」，守門對所有真實檔案立刻變紅。
改成看**符號種類**（欄位／區域變數／參數／屬性才算值）。

**二｜指派的左手邊沒放行。** `_context = context;` 裡 `_context` 本身也是一個 reference，
而規則只處理了「在右手邊」。每個 Reader 的建構子都長這樣，所以又是全紅。
補上「寫進自己已追蹤的欄位」；`holder.Context = ...` 因為正規化不出名字，仍然被擋。

這兩個都是**先讓守門對合法程式碼變紅**才發現的 —— 逃逸分析的預設是拒絕，
所以每一種合法用法都必須被明確列出來，漏一種就會擋到自己人。

### P3：類別文件與實作矛盾

第 20–23 行還寫著「只用語法不用語意模型」，那是加入 `SemanticModel` 之前的說法，
與同一份文件第 32–38 行及實作互相矛盾。已改成「語意優先、語法正規化備援、
兩者都認不出來就 fail closed」。

## 2026-08-31 第五輪：兩個放行清單還在用名字比對

alex 找到的：

```csharp
using RefundReader = ExternalNamespace.SneakyReader;
new RefundReader(_context);                    // 被當成核准元件

using ArgumentNullException = ExternalHelper;
ArgumentNullException.ThrowIfNull(_context);   // 被當成 null 檢查
```

兩個放行都比對**原始碼上的名字**：`creation.Type.ToString().Split('.')[^1]` 與
identifier 的 `ValueText`。C# 的 using alias 可以讓拼字完全正確、指的卻是別的型別。

**這是同一個病灶的第五次**，而且特別難看：我在同一個檔案裡才剛把接收者判斷從
名字改成語意，卻在自己新增的兩個允許清單上又退回比對字串。**逃逸分析的允許清單
才是最需要嚴格的地方** —— 那是唯一能讓 context 合法離開視野的出口。

### 改法

- `IsApprovedComponent`：`GetSymbolInfo(creation.Type)` 解析成 `INamedTypeSymbol`，
  比對 `ToDisplayString()`（**完整型別名稱含命名空間**）
- `IsNullGuard`：`GetSymbolInfo(invocation)` 解析成 `IMethodSymbol`，
  比對 `Name == "ThrowIfNull"` 且 `ContainingType` 是 `System.ArgumentNullException`
- 兩者**符號解析不出來就不放行**

呼叫端改傳完整型別名稱（`DoSelect.Infrastructure.Refunds.<元件名>`）。

### 踩到的坑：臨時編譯沒有 ImplicitUsings

改成用符號比對之後，真實檔案的建構子 null guard 全部被擋 —— 因為專案開了
`ImplicitUsings`，而我是臨時把單一檔案編成一個 compilation，沒有那些隱含 using，
`ArgumentNullException` 根本解析不出來。

補了一段 `ImplicitUsings` 常數，parse 前接在來源前面。

**要記的是**：改用語意判斷之後，「解析不出來」從一個罕見狀況變成日常狀況 ——
編譯環境要盡量貼近真實專案，否則 fail-closed 會擋到自己人。

### 一條測試改成驗性質而不是驗訊息

`FailsClosedWhenItCannotFindAnyContextEntryPoint` 原本斷言訊息含
「辨識不出任何 DbContext 入口」。加上 ImplicitUsings 之後，語意模型解得出那個
區域變數的型別，於是改由逃逸分析攔下 `return context;`，訊息不同了。

兩條都是 fail-closed，所以改成 `Assert.NotEmpty` —— 這條測試要驗的性質是
「這個檔案不會乾淨地通過」，指定哪一條規則反而會在另一條生效時假性變紅。

### 破壞式驗證

退回用名字比對，兩條 alias 偽裝測試變紅；真 symbol 的正向測試維持綠。
