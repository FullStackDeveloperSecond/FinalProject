## 依據

alex 2026-08-30 於 PR #36 的 review：`CostChange` **採用 A1，視為正式庫存異動類型**，
要求同步 `庫存規則.md` 的異動類型清單、`InventoryMovementTypes.All`，並補 API／SQL Server
測試確認 `movementTypes=CostChange` 可正常篩選。同一輪另外交辦修正 PR 描述與過期的 Audit 註解。

裁定理由是它已由 SKU 成本修改流程實際寫入、庫存週轉報表也會使用，未篩選的異動列表已會顯示它，
拒絕其篩選值會造成 API 契約不一致。

## `CostChange` 之外，同一個裁定還有一個沒被點到的出口

`InventoryMovementListRequest.MovementTypes` 上是 `[MaxLength(9)]` —— 一個沒有註解的數字，
正好等於**舊**詞彙表的 9 個型別。加入第 10 個之後，「一次篩選全部型別」的請求會在 model
validation 就被擋掉，**根本走不到白名單檢查**，而且錯誤訊息是 maxItems 而不是未知型別，
從症狀很難反推原因。

改成 10，並加 `MovementTypeFilterCapMatchesTheVocabulary` 斷言它等於
`InventoryMovementTypes.All.Count`。attribute 參數必須是編譯期常數、沒辦法直接引用該集合，
所以用測試把兩者綁住，而不是再留一個裸數字。

## PR #37：兩條庫存路由完全沒有 route meta

rebase 的衝突區塊剛好把 alex 在 PR #35 round-3（P2-3）對 `/catalog/compatibility` 的裁定
註解攤在旁邊，才發現本 PR 的兩條路由是同一個缺口 —— 它們是 admin-web router 裡**唯一**
沒有 meta 的功能性路由，而 guard 的第一行是「三個旗標都沒有就直接放行」，等於未登入也能
打開後台庫存頁。

角色不是自行決定的：`AdminInventoryController` 掛 `[Authorize(Policy = InventoryManager)]`，
該 Policy 在 `AddAdminPolicy` 對應 `InventoryManager` 與 `SuperAdmin`，前端對齊同一組。
前端 guard 是體驗與最小揭露，不是後端 Policy 的替代品。

順帶查證兩件事，結論都是不必動：釋放按鈕以 `availableActions.includes('release')` 為條件，
而後端永遠回空陣列，所以不會出現打到已撤回端點的死按鈕；導覽列的慣例是「全部顯示、由路由
守衛把關」，只有營運報表那條是例外，本 PR 的連結符合多數慣例。

## `dev` 的 #66 讓本分支編譯不過

`dev@e41ef51` 在 `InventoryMovement` 建構子加了必填的 `decimal unitCostSnapshot`，位置插在
`reasonCode` 之前，本分支 4 個寫入端全部中斷。值一律取 `Sku.UnitCost`，與 `dev` 上既有寫入端
一致（`EfOrderService` 讀成字典、`EfSkuAdminService` 取 request、`ReturnInventoryRestockWriter`
取訂單項目快照），沒有自創來源。

和解修正那筆是 zero-delta 標記，成本本身沒有估值意義，但參數不可為 null，寫死 0 會讓 M-15
週轉報表的成本基礎失真，所以照樣記該 SKU 當下成本。

先取 `dev` 版本，rebase 完成後把 API 實際跑起來用 `npm run api:check` 重產。驗證方式是比對
path 總數 —— `dev` 109 → 本分支 114，差異正好是 5 個 admin inventory 端點，沒有任何既有
path 被移除。本次裁定造成的契約變更只有 `maxItems` 9 → 10。

正規的 5126 重產後實質內容零差異。
