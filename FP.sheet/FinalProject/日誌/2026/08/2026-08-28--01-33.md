## 更改內容

### 摘要

組長在 PR #34 的 review 中引用 DEC-BATCH-027（相容性來源多值規格與 Checkout 原子交易定版），裁定本 PR 自建的 `SkuCompatibilityAttributes`／`SkuStorageInterfacePorts`／`CompatibilityRuleEngine` 一整套平行模型不再是正式來源，改以 Catalog 模組既有的 `ICompatibilityCatalogReader`／`EfCompatibilityCatalogReader`（建構於 `SpecificationDefinition.AllowsMultiple`＋`SkuSpecificationOptionSelection` 正規化多值 join 表）與 Domain.Builds 的 `CompatibilityEvaluator`（PR #52 既有產物）為正式相容性事實來源與規則引擎。已依此完成：

- 刪除本 PR 自建的整套平行模型（entity、admin service、DTO、規則引擎），並將 `EfCompatibilityCheckService`／`EfCompatibilityRuleAdminService`／`EfBuildListService` 全部改接正式的 `ICompatibilityCatalogReader`＋`CompatibilityEvaluator`。
- 改寫全部 13 個受影響測試檔（`EfBuildListServiceTests`、`CompatibilityCheckServiceTests`、`EfCompatibilityRuleAdminServiceTests` 等），改用正式多值模型的 seeding 方式；刪除兩個已無對應正式邏輯可測的測試檔（`EfSkuCompatibilityAttributeAdminServiceTests`、`ProductCategoryChangeCompatibilityGuardTests`，後者的 scalar/decimal 值涵蓋已由 `CatalogAdminServiceTests` 既有測試證實，另補一支涵蓋多值 `SkuSpecificationOptionSelections` 路徑的測試）。
- 整個 solution 重新建置為 0 錯誤、0 警告；已用本機啟動的後端重新產生 `contracts/openapi.v1.json` 與前端 `schema.d.ts`，差異剛好等於被移除的兩個 SKU-attributes 端點。

**Migration 清理未完成，需要 alex 的 Migration Gate 覆核才能繼續：** `20260826060901_AddSkuStorageInterfacePorts`（先前已在 [[2026-08-26--20-28]] 提出待覆核）在這次 rebase／後續 dev 演進後，已不再是 Migration 歷史中的最後一支（`dev` 上又疊了多支後續 Migration），`dotnet ef migrations remove` 因此無法直接刪除它——唯一乾淨的清理方式是另外新增一支「drop `SkuCompatibilityAttributes`／`SkuStorageInterfacePorts` 兩張表」的新 Migration。依最新工程包規則（「不得在功能分支自行 scaffold／apply 新 Migration；Schema 需求交 alex 走 Migration Gate」），本次**未**自行 scaffold 這支新 Migration，也**未**手動修改 `DoSelectDbContextModelSnapshot.cs` 讓 `has-pending-model-changes` 看起來乾淨（那樣只是掩蓋、不是解決：目前 Migration 歷史重播出來的 DB 仍會建出這兩張表，但正式 C# Model 已經沒有對應 Entity，兩者不一致）。目前 `dotnet ef migrations has-pending-model-changes` 會正確回報有 pending changes，這是預期中、如實反映問題的狀態，會維持到 alex 排出 drop migration 為止。

## 組長 Migration Gate 覆核結果（2026-08-28）

本節取代本日誌前段「只能新增 drop Migration」的暫定判斷。`20260826060901_AddSkuStorageInterfacePorts` 與舊的 `20260827075322_AddCompatibilityCheckRunsEvaluatedAtUtcIndex` 都只存在 PR #34，未進入 `dev`，且依先前 Gate 明確不得套用共享資料庫；因此不應讓正式 Migration 歷史先建立再刪除兩張從未上線的平行來源表。

組長採用的處理方式如下：

1. 將 PR #34 的有效線性 commits rebase 到最新 `dev`。
2. 移除兩支未合併的舊 Migration 與其 Designer，ModelSnapshot 回到最新 `dev` 基準。
3. 只重新 scaffold `AddCompatibilityCheckRunsEvaluatedAtUtcIndex`；新 `Up()` 僅建立 `IX_CompatibilityCheckRuns_EvaluatedAtUtc_Id`，沒有 `CreateTable`、`DropTable` 或資料搬移。
4. 確認新 Designer／ModelSnapshot 不再含 `SkuCompatibilityAttribute`／`SkuStorageInterfacePort`，且 `dotnet ef migrations has-pending-model-changes` 回報乾淨。

本機補充驗證：Domain 425／425、Application 325／325、Infrastructure persistence model 52／52；customer-web 76／76、admin-web 129／129，兩個前端的 typecheck、lint、build 皆通過。完整 SQL Server 測試不以本機結果結案，因 `SQL2025` 目前回報強制加密能力不相容；必須以 PR Required CI 的 disposable SQL Server 結果為準。

若未來查到任何共享環境曾違反 Gate 套用已移除的建表 Migration，必須另開資料庫事件處理並先盤點資料；不得直接以本次分支重建推論共享資料庫 Schema 已同步。本次沒有對任何資料庫套用 Migration 或 SQL。
