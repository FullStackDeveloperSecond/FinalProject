## 更改內容

### 摘要

組長 Review `feature/catalog-search`（PR #12）後給了修正書：後台管理 API 不可匿名、CI 缺 SQL Server 導致必要檢查全紅、OpenAPI schema 前後台各自產生一份違反規範。本次照意見拆成 3 條分支並逐項修正，尚未重新送審。

### 新增

- 5 個後台 Catalog Controller（brands/categories/tags/products/skus）全部加上 `[Authorize(Policy = DoSelectPolicies.CatalogManager)]`
- `CatalogAdminAuthorizationTests`：401（未登入）、403（無權限角色）、CatalogManager／SuperAdmin 成功，共 13 個測試
- SQL Server Provider-backed 測試類別加 `[Trait("Category","RequiresSqlServer")]`，`ci.yml` 加 `--filter "Category!=RequiresSqlServer"` 排除，讓 required CI 恢復全綠
- `FP.dev/contracts/openapi.v1.json`（正式契約檔）＋ `frontend/shared` 的 `api:export`／`api:generate`／`api:check` script
- admin-web：品牌／分類／標籤／商品／SKU 管理頁面（含建立／編輯／刪除、RowVersion 併發處理）、對應 Vitest 測試
- admin-web：401 導向 `/unauthorized`、403 導向 `/forbidden`（原本兩個路由存在但沒人導過去）

### 修改

- `Program.cs`：rebase 到含 SH-05 的 dev 時處理衝突，同時保留 `AddDoSelectSecurity` 與 `AddDoSelectCatalogServices`
- `customer-web`／`admin-web` 的 `client.ts` 與 admin-web 5 個 `features/*/types.ts`：改吃 `frontend/shared` 的共用 schema

### 刪除或淘汰

- `customer-web/src/api/generated/schema.d.ts`、`admin-web/src/api/generated/schema.d.ts`（app 各自的 schema，已違反單一共用規範）
- 兩個 app 各自的 `generate:api` script

### 正確取用方式

| 項目 | 定義 |
|---|---|
| 前端 API 路由與 HTTP Method | `GET/POST/PUT /api/v1/admin/{brands,categories,tags}`、`GET/POST/PUT /api/v1/admin/products`、`POST /api/v1/admin/products/{id}/skus`、`GET/PUT/DELETE /api/v1/admin/skus/{id}` |
| Request DTO | 不變（`CreateBrandRequest` 等，見既有 Controller） |
| Response DTO | 不變 |
| 後端介面／Application Service | 不變（`IBrandAdminService` 等） |
| 領域事件／整合事件 | 無新增 |
| 必要權限或 Policy | 新增：`[Authorize(Policy = DoSelectPolicies.CatalogManager)]`（`CatalogManager` 或 `SuperAdmin` 角色） |
| 成功條件 | 不變 |
| 可能錯誤碼 | 新增 `401`（未登入）、`403`（無權限）；沿用既有 `409 concurrency_conflict` 等 |

### 命名與型別

| 名稱 | 型別／格式 | 是否可為空 | 說明／範例 |
|---|---|---|---|
| `contracts/openapi.v1.json` | JSON | 否 | 從 `/openapi/v1.json`（Development 環境）匯出的固定契約，手動更新 |
| `frontend/shared/src/api/generated/schema.d.ts` | TypeScript | 否 | 由 `openapi-typescript` 從上述契約產生，禁止手改 |

### 必須維持的規則

- 產生檔（`schema.d.ts`）不得手動修改，只能透過 `npm run api:generate`（於 `frontend/shared`）重新產生
- 兩個前端 app 一律從 `@doselect/web-shared/api` 取型別，不得再各自 `generate:api`

### 禁止或不建議的取用方式

- 不可由前端直接存取資料庫。
- 不可跨模組直接操作其他模組的 Repository 或資料表。
- 不可對外暴露資料庫內部 `bigint Id`；對外識別使用 `PublicId`。
- 其他：不可繼續在 `customer-web`／`admin-web` 各自新增 `api/generated/schema.d.ts`。

## 相容性、風險與注意事項

- 相容性影響：5 個後台 Catalog API 從匿名變成需要登入且具 `CatalogManager`／`SuperAdmin` 角色，屬 Breaking Change；目前僅內部測試呼叫，尚無正式使用者受影響
- 已知風險：admin-web 完全沒有登入／Session UI，401 導頁後使用者卡在「需要登入」頁面無法真正登入；需等對應登入功能完成才算真正可用
- 回復方式：Controller 上移除 `[Authorize]` 即可回到匿名（不建議，會回到組長指出的安全問題）
- 需要其他負責人配合：kafen 覆核；組長決定 PR base 策略、PR #12 去留、OpenAPI Typed Client 歸屬（是否與 alex 的產出衝突）
