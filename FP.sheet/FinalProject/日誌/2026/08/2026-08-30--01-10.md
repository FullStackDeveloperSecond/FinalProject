## 兩個繞過，兩個都成立

### 1｜fail-closed 的粒度錯了

斷言寫的是「整段至少解析到一個欄位」（`statement.Accesses.Length > 0`），
但漏洞在**單一參數**層級。alex 的反例：

```csharp
_context.UserRoles
    .Where(userRole => userRole.UserId == admin.Id)
    .Join(
        _context.Roles,
        userRole => userRole.RoleId,
        role => role.Id,
        (outer, inner) => inner.ConcurrencyStamp)
```

`(outer, inner) =>` 不符合我單一參數的正則，所以 `inner.ConcurrencyStamp` 完全沒進斷言；
但同段已經解析到三個合法欄位，`Accesses.Length > 0` 成立 —— **綠燈**。

**「至少一個」永遠不等於「全部」。** 改成逐參數 fail-closed：受限查詢裡只要有任何一個
lambda 參數綁不到資料表就失敗，並補上多參數 lambda 的辨識。

### 2｜`_context` 是字面比對

```csharp
var db = _context;
var values = db.Orders.Select(order => order.GrandTotal);
```

零個 table marker，直接在 `markers.Length == 0` 被略過。而且把欄位改名成
`_dbContext`，**整個檔案**都會離開守門範圍。

改成**依型別**找 DbContext 欄位（掃 `DoSelectDbContext` 宣告），名稱怎麼取都躲不掉；
同時禁止把它指派給別的區域變數。

## 這是第三次同一類錯

- 第一次：Join 的參數綁定
- 第二次：query comprehension 沒有 `alias =>`
- 這次：多參數 lambda ＋ 字面 `_context`

三次都是**我宣稱「解析不了的寫法不會被誤放行」，而實際上會**。共通點不是「我漏了某種
語法」，是**我用來支撐那句話的驗證，範圍都比那句話窄**：上一輪只驗了單參數與 query
syntax 兩種，就宣稱涵蓋全部。

所以這次除了修，還把 DEC-B1 與日誌裡的敘述改成**與實測案例逐條對應**——
七種情況、七條實測結果，不再寫概括句。

一種是仍在檢查、一種是整個檔案被跳過，兩者長得一模一樣。

## 必須維持的規則（新增）

- **fail-closed 的粒度要對準漏洞的粒度。** 漏洞在參數層級，斷言就不能只看整段。
- **「至少一個」不等於「全部」。**
- **靜態掃描不要綁變數名稱。** 依型別辨識，改名才躲不掉。
- **驗證範圍要涵蓋宣稱範圍。** 驗兩種語法就只能宣稱那兩種。
