## P2｜RowVersion 必須驗證為 8 bytes

`UpdateCouponRequest.RowVersion` 與 `CouponActionRequest.RowVersion` 原本只有
`[Required]`。空陣列會通過 model validation，一路走到 `RequireCurrentRowVersion`
被當成過期 token 回 `409 concurrency_conflict` —— **那個錯誤碼會讓管理員以為有人
同時改了資料，實際上是他自己送錯格式。**

改用專案既有的 `RowVersionRequiredAttribute`，沒有另寫一套。補 Update、Action
各三條錯誤長度（0／4／16 bytes）的 API 測試，並斷言 `fake.Calls == 0`。

## P3｜移除已失效的 Audit 缺口註解

`EfAdminCouponService.ExecuteActionAsync` 的 XML 註解還寫著「`ReasonCode`／`Note`
目前沒有寫進任何地方」「白名單沒有 `coupon.*`」，但同一個方法已經呼叫 `WriteAudit`。
過期註解比沒有註解更糟 —— 後續維護者或 AI 會照著它重做一次已經存在的能力。

改寫成描述現況：兩個值以 `reason`／`note` 兩個獨立參數傳給 `IAuditWriter`，
與狀態變更同一交易提交，**不得串接成單一字串**。

## 自查發現：#16 剛修好的 500 缺陷，這支一模一樣

alex 在 PR #16 指出「不安全的 `reasonCode`／`note` 會回 500 而不是 400」。
我照他的要求「重新做一次完整功能範圍比對」時，順手看了這支 ——
`CouponActionRequest` 有完全相同的問題：

```csharp
[Required, StringLength(64, MinimumLength = 1)] string ReasonCode,
[StringLength(1000)] string? Note,
```

只驗長度。兩個值原封不動傳進 `WriteAudit`，中央 Audit 會拒絕含 Email、`@`、
禁用詞或不合法 safe-code 的輸入並丟 `ArgumentException` —— 那個例外沒有專屬
handler，最後變成 `500 unexpected_error`。

**alex 沒有在 #50 點名這一項，但它就在那裡。** 這正是他反覆講的「只修點名的單點、
不重新比對整個功能」會漏掉的東西。

已一併修正並補 4 條 API 負面測試（2 條不安全 note、1 條不安全 reasonCode、
外加原有的缺 reasonCode）。
