## 更改內容

### 摘要

完成會員客服案件的第一個前後端切片，並加入後台客服自領所需的內部 Application／Persistence 核心。Claim 使用 RowVersion 條件更新與 AssignmentHistory 同一交易，經獨立代理撰寫與執行測試；正式 Route 因共用 Policy 尚未核准而刻意不開放。

### 新增

- 顧客客服 Controller、Application Service／Store、DTO、Problem Details、開發登入支援與客服前台頁面／Query／型別。
- OpenAPI v1 匯出與 shared TypeScript 產生型別。
- `IAdminSupportTicketService`、`IAdminSupportTicketStore`、`AdminSupportTicketService`、`AdminSupportTicketStore` 與 claim DTO。
- Domain／Application／SQL Server claim 測試：狀態、RowVersion、原子交易、Rollback、雙人競態、AdminProfile 身分與隱私契約。
- Pipeline 稽核報告位於 `.workflow/runs/20260819T073615Z-support-claim/`。

### 修改

- `SupportTicket` 活動／狀態行為、客服 DI、API Authentication／CORS／開發端點與顧客前台 Router。
- Claim assignee 回應改用 active `AdminProfile.PublicId + DisplayName`；不回 Email、Identity string Id 或資料庫 bigint Id。
- 缺少或停用 AdminProfile 時，在任何案件寫入前回 `AdminNotEligible`，Application 映射為 `403 authorization_forbidden`。

### 刪除或淘汰

- 無；本輪未刪除既有 API、資料表、Migration 或契約。

## 定義與對外契約

### 提供給其他模組的能力或資料

| 能力／資料 | 提供者 | 使用者 | 用途 |
|---|---|---|---|
| 顧客客服案件 API／DTO | Kafen | customer-web、後續 AI 客服只讀整合 | 建立、查詢、回覆與取消本人案件 |
| `IAdminSupportTicketService.ClaimAsync` | Kafen Application | 未來經正式 Policy 授權的 Admin API | 自領 Open／未指派案件 |
| `AdminSupportTicketDto` | Kafen Application | 未來 Admin API／admin-web | 回傳案件與公開安全承辦摘要 |

### 正確取用方式

| 項目 | 定義 |
|---|---|
| 前端 API 路由與 HTTP Method | 顧客端 `/api/v1/support-tickets*` 已存在；後台 claim Route 尚未核准、不得呼叫 |
| Request DTO | `CreateSupportTicketRequest`、`CreateSupportMessageRequest`、`CancelSupportTicketRequest`；內部 claim 使用 `ClaimSupportTicketRequest{RowVersion}` |
| Response DTO | `SupportTicketDto`／`SupportTicketSummaryDto`；內部 claim 回 `AdminSupportTicketDto` |
| 後端介面／Application Service | `ISupportTicketService`；`IAdminSupportTicketService.ClaimAsync` |
| 領域事件／整合事件 | 無；claim 同步新增 `SupportAssignmentHistory(Action=Claim)` |
| 必要權限或 Policy | 顧客端要求已登入本人；後台正式 CustomerService／Supervisor Policy 等待 alex 核准 |
| 成功條件 | Claim 僅限 active AdminProfile、自領 Open＋未指派案件、RowVersion 相符，案件更新與歷程同一交易 |
| 可能錯誤碼 | `resource_not_found`、`concurrency_conflict`、`support_ticket_assignment_conflict`、`authorization_forbidden` |

### 命名與型別

| 名稱 | 型別／格式 | 是否可為空 | 說明／範例 |
|---|---|---:|---|
| `ClaimSupportTicketRequest.RowVersion` | Base64 對應 SQL Server 8-byte rowversion | 否 | 缺少或長度錯誤在 Application 驗證失敗 |
| `AdminAssigneeSummaryDto.PublicId` | UUID | 否 | 來自 active `AdminProfile.PublicId` |
| `AdminAssigneeSummaryDto.DisplayName` | string | 否 | 公開安全顯示名稱；不得改成 Email |
| `SupportTicketClaimOutcome` | enum | 否 | `Claimed/NotFound/AssignmentConflict/ConcurrencyConflict/AdminNotEligible` |

### 必須維持的規則

- Claim 的 Ticket 條件更新與 `SupportAssignmentHistory` 必須同一 Transaction。
- `WHERE` 必須同時限制 PublicId、Open、未指派與 expected RowVersion；雙人競態只能一人成功。
- 缺少／停用 AdminProfile 不得先修改 Ticket。
- 會員 API 固定限制 Owner；內部備註不得出現在會員回應。
- 不可對外暴露 Email、Identity string Id、資料庫 bigint Id 或內部資料表識別。
- 正式 Policy 未核准前不得新增或開放後台 claim Route。

### 禁止或不建議的取用方式

- 不可由前端或其他模組直接操作 `DoSelectDbContext`、`SupportTickets` 或 Repository。
- 不可用單純先查後寫取代 RowVersion 條件更新。
- 不可用 raw role check 假冒尚未核准的正式 Policy。
- 不可把 CORS 當成 Antiforgery；正式 POST 上線前仍需團隊統一 CSRF 防護。
