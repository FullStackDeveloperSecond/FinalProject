## 更改內容

### 摘要

建立 ASP.NET Core API 橫切管線，使成功與失敗 Request 都能取得一致 Correlation ID，並將 Model Validation、無 Body HTTP 錯誤及未處理例外轉為具穩定 code 的安全 Problem Details。

- `DoSelect.Api/Common/CorrelationIdMiddleware.cs`
- `DoSelect.Api/Common/GlobalExceptionHandler.cs`
- `DoSelect.Api/Common/ApiFoundationExtensions.cs`
- `DoSelect.Api.IntegrationTests/ApiFoundationTests.cs`

### 修改

- `Program.cs` 改用 `AddApiFoundation()`／`UseApiFoundation()`。
- API、錯誤碼、Logging、決策紀錄、追蹤表與開發 README 同步實作契約。

### 正確取用方式

| 項目 | 定義 |
|---|---|
| 前端 API 路由與 HTTP Method | 本次沒有新增正式商業 Route；所有 Request 可傳 `X-Correlation-ID` |
| Request DTO | 使用目的專屬 DTO＋DataAnnotations；不要直接綁定 Entity |
| Response DTO | 錯誤使用 RFC Problem Details＋`code`／`traceId`／`correlationId`；Validation 另有 `errors` |
| 後端介面／Application Service | 無新增 Application Service |
| 領域事件／整合事件 | 無 |
| 必要權限或 Policy | 本次尚未導入認證授權；後續端點仍須自行宣告 Policy |

| 可能錯誤碼 | `validation_failed`、`authentication_required`、`authorization_forbidden`、`resource_not_found`、`request_method_not_allowed`、`request_conflict`、`request_content_type_unsupported`、`rate_limit_exceeded`、`service_unavailable`、`unexpected_error`；明確 RowVersion 衝突仍用 `concurrency_conflict` |

### 命名與型別

| 名稱 | 型別／格式 | 是否可為空 | 說明／範例 |
|---|---|:---:|---|
| `X-Correlation-ID` | Header；ASCII 英數、`-`、`_`、`.`；1～64 字元 | 是 | 缺少或無效時 API 產生 32 字元小寫十六進位值 |
| `code` | snake_case string | 否 | 前端依此決定流程與語系文案 |
| `traceId` | W3C Trace ID／TraceIdentifier | 否 | 定位本次技術呼叫鏈 |
| `correlationId` | string | 否 | 串接 Request、後續工作與 Log |
| `type` | URI | 否 | `urn:doselect:problem:{code}` |

### 必須維持的規則

- `CorrelationIdMiddleware` 必須在例外、Status Code、HTTPS、授權及 Controller 之前。
- 外部 Correlation ID 必須先驗證，不可信任任意長度或字元。
- 未處理例外的 Response 不得出現 Exception Message、型別、Stack Trace、SQL、Secret 或內部路徑。
- 業務錯誤需使用錯誤碼目錄的精確 code；不可只依 HTTP Status 猜測所有商業原因。
- `[ApiController]` 驗證失敗不得進入 Action。

### 禁止或不建議的取用方式

- 不要在各 Controller 重複 try/catch 未處理例外。
- 不要自行建立另一種錯誤 Envelope 或回 200 表示失敗。
- 不要把 Correlation ID 當成授權 Token、Secret 或 Idempotency-Key。
- 不可由前端直接存取資料庫，也不可對外暴露內部 `bigint Id`。

## 相容性、風險與注意事項

- 相容性影響：成功 DTO 與 Route 不變；原本空白的框架錯誤新增 Problem Details Body，屬 Additive Contract。
- 已知風險：Identity／Cookie 與正式 Authorization Pipeline 尚未建立，因此 401／403 本次只驗證無 Body Status 的共通轉換，不代表認證授權流程已完成。
- 已知風險：正式 Serilog JSON Request Logging 尚未導入；本次只建立 Correlation Logging Scope。
- 回復方式：移除 `Program.cs` 的兩個 Foundation Extension 呼叫及 `Common` 新增檔即可回復原最小骨架。
- 需要其他負責人配合：後續模組需使用 `ApiErrorCodes`／Problem Details，不建立平行錯誤格式；前端共用 Wrapper 需處理 code 與 Correlation ID。
