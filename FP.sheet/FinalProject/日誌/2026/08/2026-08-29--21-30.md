## 契約先讀清楚：這是無狀態試算

`優惠券規則` 第 99～100 行寫死語意：

- **購物車不保存已輸入的優惠碼**，前端每次帶入。
- **購物車預覽不建立或保留 `CouponRedemption`**。

`Cart` entity 也確實沒有優惠券欄位。所以 `POST /api/v1/cart/coupon` 是無狀態試算：
算出折扣、回傳更新後的 `CartDto`，不寫任何東西；占用名額發生在 Checkout。

`CouponQuoteService`（PR #8 已合併）本來就是這個 use case，註解寫著「只做預覽，
不建立或保留 CouponRedemption」。這一層只是把它接到購物車。

## 為什麼要一個讀取埠

`CouponCalculationLine` 需要每列的 `ProductId`、`CategoryIds`、`FinalUnitPrice`、
`IsOnSale`，但 `CartItem` 只有 `SkuId` 與 `Quantity` —— 其餘都在 Cart／Sku／Product／
Category，屬 Shopping 與 Catalog 模組。

依工程包第 7 節不得直接讀，因此定義 `ICartCouponLineReader`，實作交 Shopping 模組。
**DEC-B1 是退款執行的個別例外，不可類推到這裡** —— #16 才剛因為跨模組讀取耗掉四輪 review。

## 為什麼這支 PR 不含端點

寫完 Controller 後才發現：DI 驗證在 **host 啟動時**就跑。只要註冊了
`ApplyCartCouponService` 而 `ICartCouponLineReader` 沒有實作，整個 API 建不起來：

```
Unable to resolve service for type 'ICartCouponLineReader'
while attempting to activate 'ApplyCartCouponService'
```

一開始把端點加進 `CartController`，**全部購物車測試變紅**。改成獨立的
`CartCouponController` 想縮小影響範圍 —— 沒有用，因為失敗在啟動期不是請求期，
整個 API 的測試照樣紅。

所以這支只交付**埠與 Use Case，不註冊 DI、不上 Controller**：可安全合併、
不影響任何現有功能（購物車 28 條測試維持全綠），而且 terry 拿到的是程式碼裡的
明確契約，可以跟我平行做。端點在他實作進 `dev` 之後另一支 PR 補上。

## 兩個實作決定

**`cartRowVersion` 用於樂觀比對。** 使用者輸入優惠碼的期間購物車若被改過，
試算結果對應的就不是他眼前那個購物車。回一個對不上、永遠結不了帳的折扣比直接拒絕
更難查，因此不符即回 `concurrency_conflict`。
（Endpoint 目錄的「主要錯誤」欄沒有列這個碼，但 `ApplyCouponRequest` 契約裡有
`cartRowVersion`，這是它唯一合理的用途。已在 PR 說明請 alex 確認。）

**~~訪客雜湊必須與 Checkout 一致。~~** ⚠️ **這一段已被 alex 的 C1 裁定推翻，請勿沿用。**
（2026-08-30 回頭訂正；原文保留在下方以免同樣的錯誤再被推導一次。）

> ~~沿用 `EfCheckoutTransactionGateway.HashGuestKey` 的 `SHA256(UTF8(guestCartKey))`。
> 不一致的話同一位訪客在預覽與結帳會被算成兩個人，剩餘名額對不起來。已用測試釘住。~~

**錯在哪裡：** `DEC-P262` 寫的是伺服器 Secret 對**正規化訂單 Email** 的 HMAC-SHA-256，
不是 `SHA256(guestCartKey)`。我拿一個有偏差的既有實作（Checkout）當成規格來對齊 ——
**對齊既有程式碼不等於對齊規格。** 更糟的是我加了測試把它釘住，那不是保護而是負債：
之後有人照 `DEC-P262` 改對，測試會變紅，看起來像「改壞了」。

**正確做法：** 購物車預覽沒有訂單 Email，所以傳 `GuestUsageKeyHash: null`，
只檢查總名額；每人次數留給 Checkout 依 `DEC-P262` 的正式規則權威重驗。
Checkout 自己的偏差是另案（alex 已裁定不在本 PR 範圍）。

## 測試

| 測試 | 證明 |
|---|---|
| `PutsTheDiscountOnTheCartAndDeductsItFromTheTotal` | 折扣同時反映在 `couponDiscount` 與 `totalEstimate` |
| `LeavesEveryOtherAmountToTheCartModule` | 不重算小計／運費／組裝費，避免兩邊各算一次而漂移 |
| `RejectsAStaleCartRowVersionAsAConcurrencyConflict` | 過期版本回 409 |
| `ReturnsNotFoundWhenTheCallerHasNoCart` | 找不到購物車回 404 |
| `MapsAnInvalidCodeTo400AndTheRestTo409` | `coupon_invalid` 400、其餘 409 |
| `DoesNotIdentifyAGuestForThePerPersonLimit` | 預覽不送任何訪客身分（原為 `CountsAGuestByTheSameHashCheckoutUses`，已隨 C1 改寫） |
| `CountsAMemberByIdentityNotByHash` | 會員以 Identity 計數 |
| `RemoveAsync_ReturnsTheCartWithoutACoupon` | 移除回不帶券的購物車 |
| `NeitherActionWritesAnything` | 兩個動作皆零寫入 |

## 必須維持的規則（新增）

- **購物車套券是無狀態試算。** 不保存優惠碼、不建立 `CouponRedemption`。
- **未完成的功能不得讓已完成的功能失效。** DI 驗證在啟動期，缺實作會弄垮整個 API；
  因此埠與使用它的服務要分兩支 PR。
- **~~訪客使用量的雜湊只能有一份。~~** ⚠️ 這條規則本身就是錯的，已隨 C1 移除 ——
  它把「與既有實作一致」誤當成正確性標準。取而代之的是：
  **對齊既有程式碼不等於對齊規格；規格與實作不一致時以正式決策文件為準，
  並把偏差另案提出，不要用測試把偏差釘住。**
