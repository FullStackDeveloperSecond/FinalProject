# 開發日誌

依 alex 在 PR #4 的並行測試回報修正死結處理。

## 問題

alex 以真實 SQL Server 建了並行退款測試：訂單已付 100 元，同一訂單兩筆各核准 70 元的退款同時執行。
連續兩次都是一筆成功 70 元、另一筆成為 SQL Server 死結受害者（錯誤 1205）。

資料完整性有守住（成功退款總額只有 70 元，沒有超額），冪等重送也正確回原金額。
**問題在例外處理**：`SqlException 1205` 被包成 `DbUpdateException`，外層再成為 `InvalidOperationException`，
而 `RefundExecutor` 只捕捉 `DbUpdateConcurrencyException`，因此該例外會直接離開 `IRefundExecutor`。
接上 API 後，這個並行情境會變成非預期的 500，而不是可處理的 conflict。

## 修正

**在交易邊界重跑整段**，而不是只重試 `SaveChangesAsync`。alex 特別指出後者會沿用死結前讀到的舊餘額。

- `ExecuteAsync` 外層包重試迴圈，最多三次；每次呼叫 `ExecuteOnceAsync`，
  由它自行開啟新交易並**重新讀取退款與重新計算餘額**。
- 重試前呼叫 `_context.ChangeTracker.Clear()`，丟掉前一次失敗交易的追蹤實體，
  否則重讀會拿到已套用變更的舊實體。
- `IsRetryableConflict` 往內層走訪 `InnerException`，找 `SqlException { Number: 1205 }`；
  `DbUpdateConcurrencyException` 也納入重試。
- 重試用盡回 `concurrency_conflict`（目錄既有代碼，不新增別名）。

`DbUpdateConcurrencyException` 的對應也從 `refund_state_conflict` 改為 `concurrency_conflict`。
兩者都是「他人已更新，重新載入後再操作」的語意，後者才是目錄定義的用途。

重試對已被別人結案的退款是安全的：重讀會看到 `Succeeded`，相同金鑰即回重播結果。
