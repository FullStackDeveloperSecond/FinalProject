## 修正內容

### P1｜純 Scope 修改不推進版本、也不受 RowVersion 保護

`UpdateRules` 原本只比對 Entity 上的欄位，看不到三張關聯表。只改分類／商品、
`ScopeType` 不變時判定為「無變動」，直接早退且不呼叫 `MarkUpdated` ——
Entity 維持 `Unchanged`，EF 不對 `Coupons` 發出 UPDATE，**我設定的 RowVersion
原始值因此從未被比對**。拿過期版本做純範圍修改會直接覆蓋別人的變更。

修正兩層：

- `UpdateRules` 新增 `scopeChanged` 參數，範圍變動一併計入 `ChangedFields`
  並推進 `RuleVersion`（欄位名 `Coupon.ScopeFieldName`）。
- 前置 `RequireCurrentRowVersion`：EF 的 `OriginalValue` 只在實體真的被修改時
  才比對，完全沒有變動的請求同樣不會發 UPDATE。前置檢查讓過期版本在任何
  情況下都被擋下。

Scope 差異以**集合語意**比較，順序不同不算變更。

### P1｜Redemption 相依讀寫沒有原子性

`hasRedemptions` 與名額計數都是**範圍查詢**，`ReadCommitted` 下讀完仍可被插入
新的 `CouponRedemption`。關鍵是 alex 指出的那一點：**新增 Redemption 不會更新
`Coupons` 那一列，所以 Coupon 的 RowVersion 攔不到這個競爭**。我原本以為
RowVersion 已經涵蓋，那是錯的。

Create／Update／ExecuteAction 三條路徑一律納入 `IsolationLevel.Serializable` 交易。
只對 SQL Server 死結（1205）重試一次；`DbUpdateConcurrencyException` **不重試** ——
那代表呼叫端持有的版本已過期，重跑只會再失敗一次。

### P1｜接上中央 Audit

alex 已於 `dev@8ef986c` 落地 `coupon.*` 白名單、`Coupon` ResourceType、
`ChangedFieldsJson` schema v2 的受限 `note`、`IdempotencyActorScope.ForAdmin`
與可指定 Serializable 的 Executor。

- `create`／`update`／`action` 三條路徑接上 `IAuditWriter`。
- `reasonCode` 寫 safe-code `Reason`；`note` 走新的 note 參數。
- Audit 與 Coupon／Scope 在**同一次 SaveChanges、同一個交易**內提交。
- Actor 在同一交易內把 Identity Id 換成 `ApplicationUser.PublicId` 與角色快照，
  並重新確認執行當下仍具 `Coupon.Manage` 角色（Token 可能簽發於角色撤銷之前）。
- **沒有任何變動的 update 不寫稽核** —— 一筆「什麼都沒改」的紀錄只會稀釋
  真正的異動。

### P2｜兩條 Scope 不變量

- `ScopeType=All` 不得帶包含範圍。這不只是資料整潔：`CouponCalculator.cs:128`
  在 All 模式直接 `return true`、完全不看包含集合，存進去等於讓 API 回一份
  **實際上不生效**的設定。
- 同一商品不得同時 include／exclude。規則另定「排除商品優先」，所以不會壞掉，
  但那兩個設定表達相反的意圖，靜默讓排除勝出等於幫管理員選了一邊。

## 一個我自己做的決定

不合規的 `note`（含 Email、HTML 標記等）在 `AuditWriteRequest.Create` 會丟
`ArgumentException`。不接住就會變成 500 —— 呼叫端送了格式不合的理由，卻看到
「伺服器錯誤」。

現在接住並映射為 400 `validation_failed`，交易整筆回滾。**刻意不複製那些格式規則**：
共用契約是唯一判準，另寫一份必然漂移。這對應 alex 在 PR #16 P2 的同類要求。

## `changedFields` 的慣例（新定義）

`changedFields` 在本專案先前沒有任何使用者，慣例由本工程包定義（`CouponAuditFields`）：
camelCase 欄位名依序用 `-` 串接。safe-code 上限 64 字元，欄位大量變動時串接必然
超過，此時改記 `count:{n}` —— 明確表示「這裡是筆數不是名稱」，而不是靜默截斷成
一份看起來完整、實際上少了幾個欄位的清單。

**這一條需要 alex 確認**，因為它會成為其他模組的參考。

## 兩個我在寫測試時犯的錯

兩次都是 **arrange 寫錯，不是生產碼有問題**，記下來提醒自己：

1. `ATerminalCouponCannotBeModified` 直接對 `Draft` 呼叫 `MarkExpired`。
   轉移表不允許 `Draft → Expired`，必須先進入 `Scheduled` 或 `Active`。
2. `AnUnsafeNoteIsRejected...` 對 `Draft` 呼叫 `Pause`。`Draft → Paused` 同樣
   不在轉移表內，於是在到達稽核之前就先回了 409。

寫狀態機的測試時，arrange 用的轉移本身也要先確認合法。
