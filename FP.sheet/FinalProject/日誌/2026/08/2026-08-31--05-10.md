## 幾個實作決定

**批次解析用 `POST` 而不是 `GET`。** 200 個 GUID 塞進 query string 會超過多數反向代理的
URL 長度上限，而且 `PublicId` 不該進網址（會留在存取紀錄裡）。這支沒有副作用，只是查詢。

**分類整棵樹一次撈回來再在記憶體接路徑。** 分類是參考資料、量級數十筆，
用遞迴 CTE 或逐層查詢換來的複雜度買不到什麼。接路徑時有一個走訪上限，
資料若出現環狀 parent 才不會在那裡無限繞。

**搜尋多取一筆判斷 `hasMore`**，不另外打一次 `COUNT`。

**`ToOption` 的 `switch` 對未知狀態丟例外**，不預設成「可選」——
那會讓一個沒人審過的新狀態自動取得排進優惠券的資格。

**超量批次丟例外而不是截斷。** 靜默截斷會讓被切掉的那幾筆看起來像「這個商品不存在」，
而呼叫端正要用它來顯示既有規則。

## 測試

十條 provider-backed（真實 SQL Server）。核心是 alex D1 的驗收條件：

> provider-backed 測試要斷言多筆輸入維持固定、有限的 SQL 往返，不得隨選取數量形成 N+1。

`ResolvingManyProductsTakesTheSameOneRoundTripAsResolvingOne` 用 `DbCommandInterceptor`
數實際命令數：解析 1 筆與解析 25 筆都必須是 **1 個命令**。
只斷言「回傳內容正確」不夠 —— 逐筆查也會回傳正確內容。

破壞式驗證：把批次解析改成迴圈裡逐筆查，這條立刻變紅。

四種 `ProductStatus` 的 `IsSelectable` 全部列出來；停售商品「解析得到但搜不到」
分成兩條測試，因為那是兩個不同的性質。

## 2026-08-31 追記：我宣告了一個沒有出口的狀態

alex #69 P2：`SearchProductsAsync` 只有 `pageSize`、**沒有 `pageNumber`**。
每次都從排序第一筆 `Take(size + 1)`，所以就算回 `hasMore: true`，
呼叫端也拿不到第二頁 —— 超過一頁的商品在這個契約下根本選不到。

而且 `TotalCount` 我填的是 `items.Length`。有下一頁時它不是總數，是個會誤導呼叫端的數字。

**我寫了 `hasMore` 卻沒給翻頁的方法。** 一個回應欄位在告訴呼叫端「還有更多」，
卻沒有任何 API 能拿到那些更多的東西 —— 這比不做分頁更糟，因為它看起來像做了。

### 修法

- `SearchProductsAsync` 與 request 都加 `pageNumber`（由 1 起算），reader 補 `Skip((page - 1) * size)`
- **移除 `TotalCount`**：真正的總數要多一次 `COUNT`，而 picker 只需要知道「還有沒有更多」。
  不提供比提供一個假的好
- 排序維持 `ProductCode`（唯一索引）。排序鍵不唯一的話，SQL Server 對相同鍵值的回傳順序
  沒有保證，同一筆可能同時出現在兩頁、也可能兩頁都漏掉

### 測試

新增三條：

| 測試 | 證明 |
|---|---|
| 第二頁接得上第一頁且不重複 | 五筆分三頁取完，總數 5、去重後也是 5 |
| 超出範圍的頁碼回空、`hasMore` 為 false | 不會繞回第一頁 |
| `pageSize: 5000` 仍被夾住 | 上限不能只靠 request 的 `Range` 屬性，這個埠不只被 Controller 呼叫 |

第一條刻意**同時**驗「總數是 5」與「去重後是 5」——只驗沒重複的話，漏掉一筆也會通過。

破壞式驗證：拿掉 `Skip`，第二頁與超出範圍那兩條變紅。
