## 更改內容

### 摘要

對帳案件的結案動作在 dev 上只有服務層（`ResolveAsync` 用 `dismissed` 布林走兩條路），端點自 PR #36 round 4 撤回、對帳也不在 Endpoint 目錄。本次依裁定：兩條獨立路由、共用 Request、reasonCode 依動作白名單、note 必填；dismiss 案件狀態＋Audit 同一次 SaveChanges，resolve 維持兩次 SaveChanges（Balance＋Movement／案件＋Audit）但同一個 SQL transaction；Reserved > OnHand 改用專用錯誤碼。

### 新增

- 路由 `POST /api/v1/admin/inventory/reconciliation-cases/{id:guid}/actions/dismiss`、`…/actions/resolve` → 204；`ReconciliationCaseResolutionRequest { reasonCode 1..32, note 1..500, rowVersion }`（`AdminInventoryController`）。
- `InventoryReconciliationReasonCodes`（Domain）：`ForDismiss = false_positive/system_error/other`、`ForResolve = count_verified/system_error/other`。
- `AuditActions.InventoryReconciliationDismiss/Resolve`、`AuditResourceTypes.InventoryReconciliationCase`；`AuditWritePolicy` 兩個 `DefinitionWithNote`：共同 `status`／`reasonCode`／`skuPublicId`，resolve 另 `onHandQuantity`／`reservedQuantity`（Expected→Actual）／`resolutionMovementPublicId`。
- 錯誤碼 `inventory_reconciliation_ledger_inconsistent`（409）。
- `ReconciliationCaseResolutionCommand`（Application）取代原 `ResolveReconciliationCaseRequest`。
- Provider-backed 測試（`EfInventoryReconciliationServiceTests` 29 支，其中 16 支是本次新增／改寫）：dismiss 不動 Balance／不建 Movement＋稽核內容；Acknowledged 也可結案；稽核 INSERT 失敗兩條都整筆 rollback；resolve 修正＋零差額 Adjustment＋稽核前後值；RowVersion 重送不重複；Balance 快照過期、帳本快照過期（偵測後多一筆 StockIn）；Reserved > OnHand 專用碼零副作用；reasonCode／note 七組非法值；非 InventoryManager 403；已結案不可再處理；不存在 404。
- API 測試（`AdminInventoryApiTests` +13）：dismiss／resolve 204＋Correlation／角色快照；重送 409 `inventory_reconciliation_case_not_open`；帳本不一致 409 專用碼；五組 400 `validation_failed`；403／401／404。

### 修改

- `IInventoryReconciliationService`：`ResolveAsync(…, ResolveReconciliationCaseRequest)` 改為 `DismissAsync`／`ResolveAsync(casePublicId, command, adminUserId, auditContext, now, ct)`。
- `EfInventoryReconciliationService`：注入 `IAuditWriter`；共用 `CloseAsync`——reasonCode／note／角色（從 UserRoles）／案件狀態／稽核 request 全部在開 transaction 前驗完；Movement PublicId 在 client 端先產生，resolve 的稽核可以在任何寫入前組好；案件狀態與稽核同一次 SaveChanges。
- `InventoryWriteExceptionMapper` 新碼對 409。
- 測試夾具：`SeedAdminUserIdAsync(context, params roles)`／`CreateAuthenticatedAdminClientAsync(params roles)` 沿用 #100 已合併的版本；本支只加 `AdminInventoryApiFixture.SeedReconciliationCaseAsync`。
- 文件：Endpoint 目錄新增「UC-ADM-INV-01 對帳」列（四條路由）；錯誤碼目錄補 `inventory_reconciliation_case_not_open`（原本漏登）與新碼；DTO 契約補 `InventoryReconciliationCaseQuery`／`InventoryReconciliationCaseDto`／`ReconciliationCaseResolutionRequest`；M 矩陣 M-10 註記。
- OpenAPI 契約與 `shared/src/api/generated/schema.d.ts` 以本機 API 重新產生（新增兩條路徑與一個 schema）。

## 定義與對外契約

### 提供給其他模組的能力或資料

| 能力／資料 | 提供者 | 使用者 | 用途 |
|---|---|---|---|
| `inventory_reconciliation.dismiss`／`resolve` 中央稽核列 | M-10 | 稽核查詢（A-27）、稽核保留 | 誰、用哪個 reasonCode、寫了什麼說明、哪個 SKU、OnHand／Reserved 的 Expected→Actual、修正 Movement |

### 正確取用方式

| 項目 | 定義 |
|---|---|
| 前端 API 路由與 HTTP Method | `POST /api/v1/admin/inventory/reconciliation-cases/{id}/actions/dismiss`、`…/actions/resolve` |
| Request DTO | `ReconciliationCaseResolutionRequest { reasonCode, note, rowVersion }` |
| Response DTO | 204 No Content |
| 後端介面／Application Service | `IInventoryReconciliationService.DismissAsync`／`ResolveAsync(casePublicId, command, adminUserId, auditContext, now, ct)` |
| 領域事件／整合事件 | 無 |
| 必要權限或 Policy | `InventoryManager`（InventoryManager／SuperAdmin）＋MFA；稽核角色快照另從 UserRoles 讀 |
| 成功條件 | dismiss：案件 Dismissed＋稽核一列，Balance／Movement 不動。resolve：Balance＝帳本重算值、零差額 Adjustment 一列、案件 Resolved 指向該 Movement、稽核一列，四者同一個 transaction |
| 可能錯誤碼 | `validation_failed`、`resource_not_found`、`inventory_reconciliation_case_not_open`、`concurrency_conflict`、`inventory_reconciliation_ledger_inconsistent` |

### 命名與型別

| 名稱 | 型別／格式 | 是否可為空 | 說明／範例 |
|---|---|---|---|
| `reasonCode` | 白名單 | 否 | dismiss：`false_positive`／`system_error`／`other`；resolve：`count_verified`／`system_error`／`other` |
| `note` | string 1..500 | 否 | trim 後存案件 `ResolutionReason` 與稽核 note；不收 `@ < > & \ " '` 與控制字元 |
| `rowVersion` | base64 | 否 | 列表回傳的 RowVersion；結案後即失效 |
| Movement `ReasonCode` | 固定 `reconciliation_correction` | 否 | 不跟著 reasonCode 變（裁定 D1） |

### 必須維持的規則

- 所有驗證在第一個資料寫入之前完成；任何一步失敗整筆 rollback。
- Movement 是零差額（before＝after＝Actual*），否則下一次偵測會把修正本身算進去再開一次案件。
- `false_positive` 不得 resolve、`count_verified` 不得 dismiss。

### 禁止或不建議的取用方式

- 不要在 HTTP 層加回 `dismissed` 布林；不要把 note 放進 safe-code 欄位。
- 不要把 `inventory_reconciliation_ledger_inconsistent` 當 `concurrency_conflict` 自動重試。
