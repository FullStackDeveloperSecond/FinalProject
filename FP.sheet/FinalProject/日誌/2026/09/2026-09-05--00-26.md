## 更改內容

### 摘要

DEC-BATCH-038 把 COD 的付款投影、通知、稽核與發票留給「未來正式物流狀態命令在進入 Delivered／PickedUp 的同一交易邊界內接線」。這支就是那個命令：整筆交給共用的 `IIdempotencyExecutor` 開交易，裡面依序做狀態轉移、歷程、Order 投影、COD 收款、Completed、通知／付款事件／發票 Outbox、中央 Audit，一次 SaveChanges，任何一步失敗整體回滾。

### 新增

- Application `ShipmentStatusContracts.cs`：`ShipmentStatusActions`（六個 action ↔ 目標狀態、delivery-failed／returned 必填原因）、`ShipmentStatusReasonCodes` 白名單、`ShipmentStatusPolicy`（狀態機邊＋宅配／超取限制＋`AvailableActions`——後端計算、前端照單）、`IShipmentStatusService`、`ShipmentStatusActionRequest`。
- Application `OrderShipmentContracts.cs`：`AdminShipmentDto`／`AdminShipmentHistoryDto`（含 Actor PublicId、availableActions、RowVersion）、`OrderShipmentDto`／`OrderShipmentHistoryDto`（只有單號、狀態、時間）。
- Infrastructure `EfShipmentStatusService`：冪等 Actor Scope 在交易外算（`admin:{PublicId}`，Operation `shipping.status`，RequestHash 含 ShipmentPublicId／action／RowVersion／reasonCode／note）；交易內比對並鎖定 RowVersion、`ShipmentStatusPolicy.IsAllowedForMethod`、`Shipment.ChangeStatus`、`ShipmentStatusHistory`、`Order.ApplyFulfillmentProjection`＋`OrderStatusHistory`（FulfillmentStatus 維度，帶 reasonCode）；進入 Delivered／PickedUp 時找訂單的 COD 嘗試，交給 `CashOnDeliveryCompletionService.Decide`，計畫套用為嘗試狀態轉移、`ApplyPaymentProjection`、PaymentStatus 維度歷程、`PaymentEvent`（`cod-delivery:{shipment}:{target}`）、`payment.succeeded` 通知、`SimulatedInvoiceRequestedV1`；付款為 Paid 時把 Order 推進 Completed（Confirmed 先經 Processing）；每個命令都寫 `shipment.updated` 通知（Email＋會員站內）與中央 Audit。收不了款（計畫被拒）整筆 409 `payment_state_conflict` 回滾。
- Infrastructure `ShipmentProjection`：訂單 DTO 上的物流摘要，後台與顧客兩種形狀共用同一次查詢。
- Api：`AdminShipmentsController.ExecuteStatusAction`（`Idempotency-Key` header 必帶、`ShippingManage`），成功回更新後的 `AdminOrderDto`。
- 稽核：`shipment.mark_in_transit`／`mark_delivered`／`mark_pickup_ready`／`mark_picked_up`／`mark_delivery_failed`／`mark_returned`（Resource Order、允許 note）；欄位 `fulfillmentStatus` 前後、`reasonCode`、`orderStatus` 前後、`paymentStatus`（只記改過——中央稽核安全代碼不收含 payment 的值，前後值在 PaymentStatus 維度歷程與 PaymentEvent）。

- admin-web A-15：「物流」區塊（摘要、歷程、依 `availableActions` 的命令按鈕、原因白名單與備註表單、Idempotency-Key 失敗沿用成功才換）、`executeShipmentStatusAction`／`useShipmentStatusActionMutation`（回應直接寫進詳情快取）。customer-web C-03：「配送資訊」區塊（配送方式、單號、追蹤號、狀態、送達時間、歷程）。

### 正確取用方式

| 項目 | 定義 |
|---|---|
| 前端 API 路由與 HTTP Method | `POST /api/v1/admin/shipments/{shipmentPublicId}/actions/{action}`，action ∈ `in-transit`、`delivered`、`pickup-ready`、`picked-up`、`delivery-failed`、`returned` |
| Request DTO | Header `Idempotency-Key`（1..128）；Body `ShipmentStatusActionRequest { shipmentRowVersion, reasonCode?, note? }` |
| Response DTO | 200 更新後的 `AdminOrderDto`（含 `shipment`） |
| 後端介面／Application Service | `IShipmentStatusService.ExecuteAsync(command, adminUserId, auditContext, ct)` |
| 領域事件／整合事件 | Outbox：`shipment.updated`（Email＋站內，Resource Shipment）；COD 完成時 `payment.succeeded`、`SimulatedInvoiceRequestedV1` |
| 必要權限或 Policy | `ShippingManage`（OrderManager／SuperAdmin）；稽核角色快照另從 UserRoles 驗同一組角色 |
| 成功條件 | Shipment 與 Order 的 FulfillmentStatus 同步推進、各留一列歷程、一列稽核；Delivered／PickedUp 且付款 Paid 時 Order Completed；COD 時付款嘗試 Paid、PaymentEvent 一筆、發票 Outbox 一筆 |
| 可能錯誤碼 | `validation_failed`、`resource_not_found`、`shipping_status_transition_invalid`、`payment_state_conflict`、`concurrency_conflict`、`idempotency_payload_conflict`、`idempotency_request_in_progress`、`authorization_forbidden` |

### 命名與型別

| 名稱 | 型別／格式 | 是否可為空 | 說明／範例 |
|---|---|---|---|
| `reasonCode` | `ShipmentStatusReasonCodes` 白名單 | delivery-failed／returned 否，其餘是 | `recipient_absent`、`pickup_expired`、`redelivery`… |
| `note` | string ≤500 | 是 | 只進管理端 Audit，不進顧客歷程；寫入前以中央 Audit note 規則（`AuditWriteRequest.ValidateNote`）驗證，不合規 400 `validation_failed`（組長 round 1 P2） |
| `AdminShipmentDto.availableActions` | `string[]` | 否 | 依現況狀態＋配送方式種類由 `ShipmentStatusPolicy` 計算 |
| `OrderShipmentDto.status` | `FulfillmentStatus`（顧客側 camelCase 列舉） | 否 | `inTransit`、`delivered`… |

### 必須維持的規則

- 狀態轉移、歷程、Order 投影、COD 收款、Completed、Audit、Outbox 同一筆交易（`IIdempotencyExecutor` 擁有交易）；不得把任何一項移到交易外。
- 宅配才允許 Delivered；超取才允許 PickupReady／PickedUp；`AvailableActions` 與命令執行用同一份規則。
- 進入 Returned 不得自行取消訂單、取消 COD 或回補庫存。
- 不接受呼叫端 `occurredAtUtc`；一律伺服器 UTC。
- 重播同鍵同 payload 不得產生第二次付款、歷程、Audit、通知或發票；重播回傳的是目前最新的 `AdminOrderDto`，不是第一次的快照（組長 round 1 裁定 A1：不保存完整 DTO、不擴充 ResponseSummary）。

### 禁止或不建議的取用方式

- 不可由前端直接存取資料庫。
- 不可跨模組直接操作其他模組的 Repository 或資料表。
- 不可對外暴露資料庫內部 `bigint Id`；對外識別使用 `PublicId`。
- 其他：顧客 DTO 不得回 Actor、原因備註或內部 ID；前端不得自行推算可用命令。
