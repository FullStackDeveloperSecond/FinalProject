## 更改內容

### 摘要

批次出貨的三個核心問題：冪等鍵只被驗非空卻沒有使用、Active 保留只檢查「至少有一筆」且在交易外、createLabel 之後沒有任何路徑能把訂單推到已出貨。三項都會讓管理員看到與事實不符的結果，本次一併修正並補 SQL Server provider-backed 測試。

### 新增

- `DoSelect.Infrastructure/Shipping/BatchShipmentIdempotency.cs`：批次出貨的冪等協調器。沿用既有 `IdempotencyRecords`、`IdempotencyCommand`（Actor Scope Hash ＋ Operation ＋ Key ＋ Request Hash）與同一把 `sp_getapplock`，但把交易切成三段——認領、逐筆出貨（各自的交易）、寫回結果。
- `AuditActions.ShipmentCreateLabel`（`shipment.create_label`）、`AuditActions.ShipmentMarkShipped`（`shipment.mark_shipped`）與對應的 `AuditWritePolicy` 定義（resourceType `Order`，允許欄位 `fulfillmentStatus`／`shipmentNumber`／`trackingNumber`）。
- `BatchShipmentResultDto.IsReplay`：這份結果是否來自先前那一次送出。
- 測試：`EfBatchShipmentServiceTests` 由 11 支擴為 20 支；`ShippingAdminApiTests` 新增 2 支；`ShipmentBatchesPage.spec.ts` 新增 3 支。
- Fixture：`SeedSkuWithBalanceAsync`、`SeedReservationForSkuAsync`；`SeedOrderAsync` 可指定品項的 SKU 與數量。

### 修改

- `EfBatchShipmentService`：
  - 服務簽章由 `correlationId` 改收 `AuditRequestContext`（稽核需要 traceId 與來源 IP）。
  - 開頭解析稽核 Actor（必須是持有 OrderManager／SuperAdmin 的真管理員），冪等的 Actor Scope 也由它算出。
  - 交易內以追蹤查詢讀出 Active 保留，逐 SKU 比對訂單品項數量；消耗後再驗一次全部轉為 Consumed，否則整筆回滾為 `concurrency_conflict`。
  - `markShipped` 會載入既有的 Preparing 物流單並走 `Preparing → Shipped`，不建立第二筆；`createLabel` 對已有物流單的訂單回錯誤並指向 markShipped。
  - 每一筆成功出貨在自己那筆交易內寫中央 Audit。
- `AdminShipmentsController`：改組 `AuditRequestContext`；補 409 的 `ProducesResponseType`。
- `ShipmentBatchesPage.vue`：重播提示、冪等衝突的具體訊息、選 createLabel 但清單含已印單訂單時的事前警告。
- 文件：Endpoint 目錄移除 `GET /api/v1/admin/shipments/batches/{id}/result.csv` 並補冪等說明；API DTO與Schema契約補 `BatchShipmentResultDto` 的 BatchPublicId 與 `isReplay` 說明。

### 命名與型別

| 名稱 | 型別／格式 | 是否可為空 | 說明／範例 |
|---|---|---|---|
| `idempotencyKey` | string(1..128) | 否 | 識別包含操作者、動作與訂單清單；同鍵同 payload 重播，同鍵不同 payload 衝突 |
| `isReplay` | bool | 否 | true 代表這份結果來自先前那次送出，沒有訂單被重複出貨 |
| 冪等 Operation | `shipping.batch` | 否 | 寫入 `IdempotencyRecords.Operation` |
| 冪等保存期限 | 24 小時 | — | 與 `EfIdempotencyExecutor` 一致 |

### 必須維持的規則

- 批次出貨**不得**改用 `IIdempotencyExecutor`：它會把整個 handler 包進單一交易，違反「一筆失敗不回滾其他已成功出貨的訂單」。
- Active 保留的驗證必須在該筆的交易內，且逐 SKU 覆蓋數量；消耗後要再確認全部轉為 Consumed。
- 一張訂單只有一張主要物流單：`markShipped` 接續既有 Preparing 物流單，不得新建第二筆。
- 每一筆成功出貨要在同一筆交易寫中央 Audit；失敗的列不留稽核紀錄。

### 禁止或不建議的取用方式

- 不可由前端直接存取資料庫。
- 不可跨模組直接操作其他模組的 Repository 或資料表。
- 不可對外暴露資料庫內部 `bigint Id`；對外識別使用 `PublicId`。
- 其他：不得把整批包成單一交易；不得為了推進狀態而替同一張訂單再開一張物流單。

## 相容性、風險與注意事項

- 相容性影響：`IBatchShipmentService` 的簽章改變只影響本 PR 自己的控制器。
- **已知風險（要說清楚）**：逐筆出貨跑到一半進程中斷時，冪等記錄會停在 Processing，之後用同一把鍵重送一律回 `idempotency_request_in_progress`，而且不會自動解除。這是刻意選的安全那一邊——不會重複出貨，也不會謊報成功。收拾殘局的方式是換一把新的冪等鍵重送，已出貨的訂單會被逐筆的「已有出貨」擋下來。若之後要自動接管，需要為 Processing 記錄加上租約（lease）機制，那是跨模組的共用行為，應由組長決定。
- 已知風險：`ResponseSummary` 有 32 KB 上限。100 筆結果約 22 KB；極端情況（每列訊息都很長）會先捨棄輔助訊息，保留列號、訂單、狀態、單號與錯誤碼——結果 CSV 的「安全訊息」欄在那種情況下會是空的。
- 回復方式：`git revert 2e2d893b`；無 Schema 異動。
- 需要其他負責人配合：無。
