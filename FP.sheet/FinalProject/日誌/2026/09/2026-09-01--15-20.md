## 一條規則貫穿這輪所有 review：**輸入錯誤不可以變成 500**

alex 這幾輪抓的東西表面上分散在物流與匯入兩個模組，本質是同一件事——**某個外部輸入沒有在服務入口被擋下，一路走到 Domain 建構子或資料庫約束才炸開，於是使用者看到的是 500 而不是可讀的 400/409**。整理成一張表後，後面幾輪我改成先拿這張表回頭掃自己的程式，而不是等他抓：

| 情境 | 舊行為 | 現行為 |
|---|---|---|
| 非 UTC 的生效時間 | Domain 丟 `ArgumentOutOfRangeException` → 500 | 400 `validation_failed` |
| 窗口已結束的 Draft 被發布 | 舊版本被收窗、新版本永不生效 → Provider 零有效版本 | 400，且交易內零寫入 |
| 兩個 Draft 同時 Publish | 撞單一 Published 唯一索引 → 500 | 409 `concurrency_conflict` |
| 大頁碼 `int.MaxValue` | OFFSET 溢位成負值 → 500 | 回空頁 |
| 65 字元的 `product_key` | 撞 64 字元欄位 → 整批 Preview 500 | 有界合成鍵，批次成為 Invalid |
| 超長 `displayNameZhTw` | 撞 nvarchar(160) → 500 | 400 `validation_failed` |

## #73：時間窗才是權威，`Published` 只是狀態字

B1 裁定落地時最大的改動不是新功能，而是**把「可用性」的判準從 `Status == Published` 換成「不是 Draft ＋ 當下落在自己的 `[From, To)` 窗內」**，Checkout 與 Shipping Options 兩處同時改。

理由：排定未來生效的版本一發布，舊版本立刻變 `Superseded` 但窗口還沒到 cutoff——只篩 `Published` 會讓 cutoff 之前完全找不到有效 profile，該 Provider 的配送方式全面不可用。`Superseded` 的語意是「已被接班」，不是「已失效」。

同一次也修了兩個 alex 沒點到、但走生命週期時自己發現的洞：

- **limit 列的窗口沒有跟著 profile 收**：`Supersede` 只收 profile，limit 會留下比 profile 更長甚至開放式的窗口，讓「窗內恰好一個有效限制」的不變量在解析時失準。
- **「結束不晚於開始」沒有擋**：與非 UTC 同一類會讓 Domain 丟例外的輸入。

round-5 又補上一個時序問題：`now` 原本在等 provider lock **之前**取得，而 `sp_getapplock` 最長等 15 秒——若在等鎖期間跨過了 Draft 的 `EffectiveToUtc`，鎖後的到期檢查會用一個已經過時的時戳而誤放行。改成鎖後才取，並讓到期檢查、cutoff、`Supersede`、limit 收窗、`Publish` 與 audit 全部共用它。

## #74：合成儲存鍵與資料庫比較規則的三次交手

這條線 alex 抓了三輪，每一輪都是同一個根因往外擴一圈，值得記下來：

1. **round-3**：重複的 `product_key` 被標了錯誤，但儲存鍵仍是那個重複的 key → 後續 `ToDictionary` 丟 `ArgumentException`、寫 `ImportRows` 撞唯一索引 → 整批 500，管理員連錯誤檔都下載不到。改用合成儲存鍵。
2. **round-4**：合成鍵用 `Ordinal` 比較，但 CI 的 SQL Server container 沒設 `MSSQL_COLLATION`，預設 `SQL_Latin1_General_CP1_CI_AS` **不分大小寫**——使用者的 `__DUP4` 與合成的 `__dup4` 在應用層是兩個鍵、資料庫卻是同一個。改用 `OrdinalIgnoreCase`。
3. **round-5／6**：`_CI_AS` 沒有 `_WS`，所以還是 **width-insensitive**；而 `NormalizeKey` 刻意不做 NFKC，於是全形的 `＿＿ＤＵＰ３` 與 `__dup3`、以及**兩個使用者自己的 key**（`PK1` 與 `ＰＫ１`）都會撞。最終改用「NFKC ＋ 大寫」的 canonical form，且**同一套形式同時用於配置合成鍵與偵測 business key 重複**——round-5 只改了配置器沒改 parser，正是那個落差讓 round-6 又被抓一次。

教訓寫在這裡：**應用層的字串比較規則若與資料庫的 collation 不同，唯一索引就是一顆定時炸彈**，而且「改一半」比沒改更危險，因為前一輪的測試會讓人以為問題已經解決。

## rebase 把一個 commit 判成 empty 而丟掉

#73 合併進 `dev` 之後，#74 重放時 git 把 round-3 那個 commit 判為 empty 直接跳過，連帶帶走嚴格 UTF-8 解碼、RFC 4180 引號位置檢查、decimal precision/scale 契約與規格 parser 的對應部分（**少了 198 行**）。

自動化腳本重試了多次也沒進展，`--abort` 兩次後改成手動逐個 cherry-pick 才走完。真正救回來的不是重放技巧，而是**驗收標準**：我不是看「rebase 有沒有跑完」，而是比對「重放結果與 rebase 前**逐檔一致**」，才發現內容掉了。修正後匯入相關檔案與 `a0280e4c` 零差異。

以後遇到跨越已合併姊妹 PR 的多 commit rebase，先寫下「完成的定義是逐檔一致」再開始動。

## 開 PR 前的自我審查抓到的問題

alex 這幾輪都要求「先依功能範圍完整自我 review，不要只逐行修改留言內容」。新開的三支 PR 都照做，而且每一項都**先用測試重現才修**：

**#77 規格範本（三項）**

- 超長 `displayNameZhTw` → 未映射的 `DbUpdateException`（探測輸出：`PROBE displayName: DbUpdateException`）。
- 建立是兩次 SaveChanges 卻沒有交易：超長選項名稱讓第二次失敗，**留下一筆已提交的定義**（探測輸出：`committed definitions left behind = 1`）。已包進單一交易。
- 語意鍵查重與寫入之間的競態 → 唯一索引違反映射成穩定 409。

**#78 物流後台（四項）**

- 發布確認訊息顯示「undefined 的版本」：`PROVIDER_LABELS[providerCode]` 在 `<script setup>` 裡少了 `.value`，而 **`vue-tsc` 完全沒抓到**。補了斷言訊息內容的測試。
- 包裹限制頁零筆版本時只剩空表格。
- `store_code_duplicate`（新增門市最常撞到的錯誤）沒有中文訊息；順帶移除多加的 `shipping_store_inactive`（那是結帳路徑的錯誤，這兩頁收不到）。
- 兩條新路由沒有 guard 測試覆蓋。

**#79 購物車配送（三項）**

- **購物車變動後配送選項不會重算**：購物車的每個 mutation 都只用 `setQueryData` 寫回 cart 的快取鍵，沒有任何東西讓配送選項失效——改完數量後畫面上的超取資格與運費仍是舊包裹的結果。修法**不是**在每個 mutation 補 invalidate（日後新增 mutation 的人會忘記），而是把購物車 `RowVersion` 放進 query key，讓舊結果**結構上**不可能被當成新的用。後端的 `ShippingOptionsDto` 本來就回傳 `cartRowVersion`。
- 門市選擇器只記得「這次點選的門市」，父層帶入的 `modelValue` 永遠不顯示已選門市。
- 門市選擇器完全沒有測試。

## 兩個假通過的測試

- **#74**：引號位置的 Theory 用 `ab"cd,2` 當輸入，但它其實是被**既有的**「未收尾引號」檢查擋下的——通過的理由是錯的。改成 `ab"cd",2`（引號中途開、正常收尾）後，破壞狀態下兩個 case 才都真的轉紅。
- **#73**：併發 publish 測試第一版把錯誤碼寫死成 `concurrency_conflict`，連跑就發現不穩定。輸家拿到哪個碼取決於誰先搶到鎖，而 `validation_failed`（亂序發布）與 `concurrency_conflict` **都是正確的產品行為**；改成斷言「必為已映射的穩定錯誤 ＋ 不變式成立」。
