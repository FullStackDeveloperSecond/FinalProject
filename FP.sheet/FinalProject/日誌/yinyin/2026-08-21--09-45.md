# 開發日誌

依 alex 在 PR #5 的 review 修正兩點。

## P1：發票金額沒有保證為 TWD 整數元

alex 指出輸入含稅 `10.50` 會得到 `net=10, tax=0.50, gross=10.50`，違反
`DEC-BATCH-014` 第 10 項「未稅、稅額及含稅金額均為 TWD 整數元」。
訂單與優惠券金額允許兩位小數，因此這是可到達的資料。

### 採取「在發票邊界拒絕」而不是「整數化」

alex 給了兩個選項。選擇拒絕的理由：

- 含稅金額帶小數時，**無法同時滿足**「三者皆為整數元」與「含稅總額等於顧客實付金額」。
- 若改為四捨五入含稅金額，發票金額會與實收金額不符，那是更嚴重的問題。
- 因此在 `InvoiceCalculator.Calculate` 的明細驗證階段，遇到非整數含稅金額直接丟
  `ArgumentException`，與既有的「已付款訂單卻無任何金額」同樣視為快照錯誤。

## P2：尾差應由最後一筆吸收

`DistributeRemainder` 原本從 index 0 開始走訪，導致首筆吸收尾差。
兩列各 1,000 實際得到首列 `953/47`、末列 `952/48`，與規格相反。

改為**從最後一筆往前**走訪，現在首列 `952/48`、末列 `953/47`，符合
「最後一筆合法明細吸收尾差」。

alex 另外指出 PR 說明引用的 `TheLastLineAbsorbsTheRoundingRemainder` 測試在測試檔中不存在
—— 那是我先前改測試時沒同步更新 PR 說明。本次以正確的期望值重新建立該測試。

- `TheLastLineAbsorbsTheRoundingRemainder`：兩列各 1,000 得到 `952/48` 與 `953/47`。
- `EveryHeaderAndLineAmountIsAWholeTwdAmount`：七種組合，斷言表頭與每列的
  Net／Tax／Gross **小數位皆為 0**，且三個範圍不變式與合計相等仍成立。
- `AFractionalGrossAmountIsRejectedAtTheInvoiceBoundary`：五個帶小數的含稅金額全數拒絕。

原本以小數金額驗證負稅額的兩個測試已移除，因為那些輸入現在會被邊界拒絕；
負稅額的防護改由整數輸入下的範圍不變式涵蓋。

## 需要 alex 裁定

**拒絕非整數含稅金額會讓帶小數的訂單無法開立發票。** 而這種訂單是可產生的：
百分比優惠券的折扣四捨五入到兩位小數，例如單價 `1000.05` 套九折得到折扣 `100.01`，
品項成交金額就帶小數（本模組 `Percentage_RoundsAwayFromZeroToTwoDecimals` 即為此案例）。

兩個要求目前互斥，需要決定哪一個優先：

1. 上游強制訂單金額為整數元（例如優惠券折扣改取整數元），發票即可維持整數元；或
2. 放寬發票金額必須為整數元的要求，改為允許兩位小數並保證等於實付金額。

在裁定前，本模組維持拒絕，讓衝突在邊界顯現而不是被靜默四捨五入。
