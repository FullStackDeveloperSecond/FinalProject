# 開發日誌

依 PR #4 Review 修正書處理 P0 原子性與 P1 冪等。

## 更改內容

### P0：退款檢查與寫入改為同一交易

原本 `ExecuteRefundService` 只產生 Plan，`RefundExecutionReader` 分三次 `AsNoTracking` 查詢，
兩個並行請求可讀到相同 `RefundableBalance` 並都通過，造成超額退款競態。

- 新增 `IRefundExecutor`（Application 埠）與 `RefundExecutor`（Infrastructure 實作）。
- `RefundExecutor` 以 `IsolationLevel.Serializable` 開啟交易，在交易內以**追蹤查詢**讀出退款、
  重新計算可退款餘額、判定、呼叫 `BeginProcessing` 與 `Complete`、`SaveChangesAsync` 後 Commit。
- `Refund.RowVersion` 已設定 `IsRowVersion()`，`DbUpdateConcurrencyException` 對應
  `refund_state_conflict`，不自行重試。
- Serializable 的範圍鎖保護餘額所依據的查詢，rowversion 保護退款列本身。
- `ExecuteRefundService` 更名為唯讀預覽（`PreviewAsync`），並在 XML 註解明確標示
  **不保證原子性、不得用來決定是否寫入**。

### P1：真正驗證 Idempotency-Key

- `RefundExecutionSnapshot` 新增 `StoredIdempotencyKey`，來源是 `Refund.IdempotencyKey`。
- 新增 `RefundExecutionDecision.Evaluate`，預覽與實際執行共用同一份判定，避免兩處漂移。
- 判定順序：
  - 請求金鑰與保存金鑰不符 → `idempotency_payload_conflict`。**已成功的退款也不例外**，
    因此不同金鑰無法對已完成的退款產生第二次副作用。
  - 金鑰相符且狀態為 `Succeeded` → 回既有金額（Replay）。
  - 金鑰相符且狀態為 `Approved` → 檢查餘額後放行。

### 修正計算缺陷

`CalculateRefundableBalanceAsync` 現在排除本次退款自身（`candidate.Id != refundId`），
否則重試時會把自己算成已用額度。
