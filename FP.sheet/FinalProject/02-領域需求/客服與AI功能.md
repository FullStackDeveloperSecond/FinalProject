# 客服與 AI 功能

狀態：已確認

## AI 定位

AI 是專題亮點，但基本電商功能必須在 OpenAI API 不可用時繼續運作。預算以 100 美元為基準。

## AI 商品搜尋與推薦

優先級：M

- 對訪客與會員開放。
- 理解預算、使用目的、規格、品牌偏好與零件相容性需求。
- 推薦結果必須解釋原因。
- 只能推薦後端查到且已通過相容性驗證的商品。
- AI 失敗時降級為關鍵字搜尋與一般篩選。

### 結構化查詢與檢索

- OpenAI 只負責把自然語言轉成版本化 JSON Schema 定義的結構化搜尋條件，並產生基於後端結果的解釋。
- 後端必須再次驗證預算、用途、規格、品牌與相容性等欄位；必要資訊不足時要求使用者補充，不得自行猜測。
- 發生拒絕、輸出截斷、Schema 不合法或業務驗證失敗時，不執行商品查詢，改為請使用者重述或使用一般搜尋。
- 第一版不使用向量資料庫或 Embedding。商品候選由 SQL Server 條件查詢取得，再交由相容性規則與排序邏輯處理。
- 只有在評估證明 SQL 與既有搜尋無法滿足需求後，才另立決策評估 Embedding。
- Structured Output 使用小型業務 Schema，涵蓋用途、預算上下限、商品／整機意圖、品牌偏好與排除、必要規格、軟性偏好、既有零件及待澄清問題。
- Schema 不得暴露資料庫欄名、SQL、任意排序欄位或任意布林運算式；後端將業務條件轉成白名單查詢。
- 商品搜尋 OpenAI 呼叫逾時為 8 秒；只對限流或暫時性服務錯誤重試一次，Schema 格式錯誤最多修復一次，仍失敗立即降級。

## AI 客服

優先級：M

- 所有客服功能都必須登入。
- 使用者必須先同意內容交由外部 AI 處理。
- 不同意時直接轉人工客服案件。
- AI 只提供問答，不能取消訂單、申請退貨、退款或修改資料。
- 第一版 AI 客服不使用串流輸出；API 完成安全驗證後一次回傳結構化答案、引用、免責與轉人工資訊。
- AI 只能查詢當前會員自己的訂單。
- 無法解決或信心不足時顯示提示並轉人工客服。
- AI 客服 OpenAI 呼叫逾時為 12 秒；暫時性服務錯誤最多重試一次，格式修復最多一次，仍失敗轉人工客服。

### AI 客服只讀工具

- AI 只能使用 Application 層提供的白名單只讀工具，例如本人訂單摘要、公開 FAQ、退換貨政策及核准商品資料。
- 會員識別只能取自後端登入內容，不接受模型或前端傳入的會員 ID 作為授權依據。
- 每個工具內再次驗證登入、資源所有權及用途，回傳最小化且去識別化的 DTO。
- 第一版不允許模型直接查詢資料庫、不接受模型產生 SQL，也不建立向量 RAG。
- 工具回傳需包含可供答案引用的來源類型與來源識別，但不得包含其他顧客資料。

### Prompt、Schema 與工具版本

- Prompt、JSON Schema 與工具契約以不可覆寫的版本化檔案保存於 Git。
- 每次 AI Interaction 保存用途、Prompt Version、Schema Version、Tool Contract Version 及模型識別。
- 已被 Interaction 使用的版本不得原地覆寫；修改需建立新版本。
- 部署設定可切換至前一個已驗證版本，回復不刪除新版或歷史 Interaction。

## AI 可使用資料

允許：

- 公開商品資料。
- FAQ 與退換貨規則。
- 去識別化訂單狀態。
- 訂單商品內容。
- 顧客目前對話。
- 該顧客自己的歷史客服對話。
- 去識別化銷售統計。

禁止傳送：

- 姓名。
- Email。
- 電話。
- 地址。
- 密碼。
- Access Token、Refresh Token 或其他祕密。
- 其他顧客資料。

訂單問答流程：

```text
驗證登入者
→ 驗證訂單所有權
→ 取得必要資料
→ 移除個資
→ 傳送最低必要資料給 OpenAI
→ 保存允許保存的客服紀錄
```

歷史客服對話不能成為其他顧客的共用知識來源。

## 客服案件

優先級：M

已確認需求：

- 會員可以建立客服案件。
- 案件可關聯會員與訂單。
- 支援顧客訊息、客服回覆、圖片附件與內部備註。
- AI 無法處理時轉成人工客服案件。
- 後台客服角色處理案件。
- AI 客服摘要列為 S，於顧客送出案件後自動產生。

### 領域邊界與統一工作台

- 一般客服案件、檢舉及退貨退款使用三套獨立領域資料與生命週期。
- 三者不得因後台畫面統一而共用同一個案件主表。
- 管理後台提供統一工作台，彙整三個領域的待辦資料供人員篩選及進入各自詳情。
- 只有一般客服案件進入客服自領佇列。
- 檢舉及退貨保留各自佇列，由具對應領域權限的角色承接；統一畫面不授予跨領域權限。
- 各領域投影共同欄位 `attentionLevel`、`dueAt`、`createdAt` 及穩定 ID；原始領域狀態仍分別保存。
- 預設排序依序為已逾時、注意等級、最早期限、最早建立時間、穩定 ID；沒有期限的項目排在有期限項目之後。
- 統一工作台只回傳摘要及導向資訊；寫入操作仍呼叫各自領域 Use Case 並重新授權。

### 客服案件分類

一般客服案件使用以下七類：

1. 訂單。
2. 付款。
3. 物流。
4. 商品與保固。
5. 退貨協助。
6. 帳號。
7. 其他。

檢舉不是客服分類；退貨協助是一般諮詢，正式退貨申請仍進入獨立退貨領域。

### 客服案件狀態

客服案件使用：

```text
Open
Assigned
InProgress
WaitingForCustomer
WaitingForInternal
Resolved
Closed
Cancelled
```

- 重開不是獨立 `Reopened` 狀態，而是一筆狀態轉移與歷程事件。
- `Resolved` 後 3 天沒有重開時自動轉為 `Closed`。
- `Closed` 是終態，不允許重開；若顧客仍需協助，建立一筆關聯原案件的新客服案件。
- 合法轉移、角色權限與已確認的取消條件以 [[03-架構/狀態機設計]] 為準。
- 顧客只可在 `Open` 或 `Assigned` 且尚無人工公開回覆時取消案件。
- 承辦客服或 `CustomerServiceSupervisor` 可在 `Open`、`Assigned`、`InProgress` 取消，但必須填寫原因。
- 已有實質處理結果時使用 `Resolved`，不得以取消隱藏處理歷程。

### 指派與共用佇列

- 尚未指派的客服案件進入共用佇列。
- 客服人員可以自行領取未指派案件。
- `CustomerServiceSupervisor` 可以指派及轉派案件。
- 每次自領、指派及轉派都必須保存操作者、原負責人、新負責人、時間及原因。
- 客服案件的自領佇列不涵蓋檢舉與退貨。

### 客服優先級

優先級使用 `Low`、`Normal`、`High`、`Urgent`：

- 系統依案件分類及關鍵條件產生預設優先級。
- 會員不能自行選擇或提高優先級。
- 客服人員可以依實際情況調高或調低，必須填寫原因。
- `CustomerServiceSupervisor` 可以覆核優先級異動。

| 優先級 | 建立時條件 |
|---|---|
| `Urgent` | 疑似帳號遭盜用、重複扣款／付款安全、已付款但系統完全無訂單且需立即止損 |
| `High` | 已付款訂單無法履約、配送遺失／嚴重損壞、組裝錯誤或即將超過退貨／退款關鍵期限 |
| `Normal` | 一般訂單、付款、物流、退貨協助、帳號問題及需處理的商品保固問題 |
| `Low` | 購買前商品詢問、一般操作教學、非緊急建議與其他無交易風險問題 |

- 不確定或沒有命中高風險條件時預設 `Normal`，不得由關鍵字單獨把案件升為 Urgent。
- 同優先級依 `IsOverdue DESC → SlaDueAtUtc ASC → CreatedAtUtc ASC → PublicId ASC` 排序；無期限排在有期限之後。
- 建立後不因到達 SLA 80%／100% 自動改變優先級；既有 SLA 提醒、Overdue 標記及置頂足以反映急迫性。
- 系統偵測到疑似安全或重複扣款條件可建立「建議升級」旗標，但由客服確認後才改級；所有人工調整需原因並可由主管覆核。

### 客服 SLA

優先級：M，第一版實作完整 SLA。SLA 只套用一般客服案件；檢舉及退貨若需要期限，必須在各自領域另行定義。

- 採 24×7 日曆時間，以 UTC 計算期限，畫面轉換為台灣時間。
- 「首次回覆」是第一則人工客服公開回覆；AI 自動回答與內部備註不計入。

| 優先級 | 首次人工回覆期限 | 目標結案期限 |
|---|---:|---:|
| `Low` | 24 小時 | 5 天 |
| `Normal` | 8 小時 | 3 天 |
| `High` | 4 小時 | 24 小時 |
| `Urgent` | 1 小時 | 8 小時 |

- `WaitingForCustomer` 暫停目標結案 SLA；案件因等待顧客而暫停的時間最多計 3 天，超過後恢復計時。
- `WaitingForInternal` 不暫停 SLA。
- `Resolved` 後 3 天內發生重開時，保留原首次回覆結果，並從重開時間依當前優先級重新計算目標結案期限。
- 到達任一 SLA 期限的 80% 時通知案件負責人。
- 到達 100% 時通知案件負責人與 `CustomerServiceSupervisor`，標記 `Overdue` 並提升至佇列頂端。
- SLA 逾時不自動轉派，也不自動改變案件優先級。
- 首回及結案逾時需可查詢；報表公式如下：
  - 首次回覆時間＝第一則人工公開回覆 UTC－建立 UTC。
  - 有效結案時間＝Resolved UTC－建立 UTC－可扣除的 WaitingForCustomer 時間（每次累加、總扣除最多 72 小時）。
  - 首回達成率＝期限內首次人工回覆案件數／具有首回期限且已回覆或已到期案件數。
  - 結案達成率＝期限內 Resolved 案件數／已 Resolved 或已超過結案期限案件數。
  - 尚未進入分母或分母為零時顯示 `—`，不顯示 0%。

### 客服附件

- 檔案存放於網站根目錄之外的本機私有目錄。
- 只能透過需要驗證與授權的 API 下載，不提供靜態公開 URL。
- 允許 PNG、JPG 及 PDF。
- 客服、檢舉及退貨三個領域均為每案最多 3 個附件，每個附件最大 10 MB；附件資料仍關聯各自領域，不建立共用案件主表。
- 資料庫只保存必要的檔案中繼資料與私有儲存識別，不保存大型檔案內容。
- 上傳時同時驗證副檔名、MIME Type 與檔案簽章，並由系統重新產生私有檔名。
- Application 透過 `IFileScanner` 掃描暫存檔；第一版 Infrastructure 使用展示電腦的 Microsoft Defender。
- 掃描不可用、逾時或結果不明時拒絕保存，不得以「先保存後補掃描」降級。
- 客服、檢舉及退貨附件在案件結束後保存 180 天；未完成關聯的上傳暫存檔與孤兒檔在 24 小時後清除。
- 每日執行清理；實體刪除失敗最多重試 2 次，仍失敗時保留可追蹤錯誤並通知管理人員。
- 案件進入爭議、申訴或其他需保留情境時可設定 Legal Hold；Hold 期間不得自動刪除，解除必須稽核。

## 保存期限

| 資料 | 保存期限 |
|---|---:|
| 未結客服案件與對話 | 案件存續期間 |
| 已結案件原始對話 | 結案後 180 天 |
| OpenAI 原始請求與回答紀錄 | 90 天 |
| 去識別化使用統計 | 1 年 |
| 使用者同意紀錄 | 與案件保存期限一致 |
| 稽核紀錄 | 1 年 |

需提供設定化保存期限、自動清理排程、管理員手動刪除、個資遮蔽及刪除結果紀錄。

## 使用限制與成本

- 訪客 AI 商品搜尋：每個 IP＋瀏覽器識別每日 10 次。
- 會員 AI 商品搜尋：每位會員每日 30 次。
- 會員 AI 客服：每位會員每日 20 則訊息。
- 需記錄功能、使用者類型、模型、Token、估算成本、成功／失敗與降級情況，不保存不必要個資。
- 累計預估成本達 US$70 時通知組長；達 US$90 時停用非 Demo 用 AI 流量。
- 每日額度於 `Asia/Taipei` 00:00 重設。
- 訪客以遮蔽 IP 的帶 Salt Hash 加第一方隨機 Browser ID 組合識別；Browser ID 保存 30 天，不使用裝置 Fingerprinting。共用網路仍同時受 IP 維度保護。
- Demo Allowlist 由組長控管，設定兩個展示會員 PublicId 與一個展示 Browser ID；只允許在 US$90 成本停止門檻後繼續展示，不繞過登入、AI 同意、授權、個資遮蔽或安全測試。
- 商品搜尋與摘要使用 `gpt-5.6-luna`，AI 客服使用 `gpt-5.6-terra`；統一採 Responses API，凍結後優先鎖定通過評估的 Snapshot。

## 多語系

優先級：S

- 前台目標支援繁體中文、日文與韓文。
- 後台第一版只支援繁體中文。
- AI 可以產生翻譯草稿，必須經管理員確認後發布。
- 商品頁不得每次開啟都即時呼叫 AI 翻譯。
- AI 客服依使用者目前語言回答。
- 第一版只啟用繁體中文，但保留語系資源與翻譯資料結構。
