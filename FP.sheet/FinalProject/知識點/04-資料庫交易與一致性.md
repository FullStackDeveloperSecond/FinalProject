# 資料庫、交易與一致性

## EF Core 與 SQL Server 基礎

- `DbContext` 是 change tracker 與 unit-of-work 邊界，不是跨 request 共用的 thread-safe cache。
- `AsNoTracking` 適合唯讀；要更新時需追蹤或明確 attach，不能無腦套用。
- `Include` 可能產生巨大 join；投影 `Select` 往往更精準。警覺 N+1、笛卡兒爆炸與過早 materialize。
- Migration 是 schema 版本，不是備份。CI 套 migration 並查 model snapshot，正式上線仍需回復計畫。
- 索引改善特定讀取，也增加寫入、儲存與維護成本；依欄位順序、selectivity 與 execution plan 決定。

## 四個要連在一起的概念

### Transaction

一組變更要全部成功或回滾。DoSelect 結帳在 server 重新讀取與計算商品、價格、優惠、運費、相容性與庫存，再於共享 SQL transaction 建立訂單相關資料；不能相信前端總金額。

### `rowversion` 樂觀併發

SQL Server 更新 row 時改變 binary version。client 送回舊 version，更新條件包含它；若已被改過，affected rows 為 0，EF Core 丟 `DbUpdateConcurrencyException`，API 通常回 409。它不是日期時間，也不保證跨表商業順序。

### Idempotency

同 actor、operation、key、相同 payload 重送，只產生一次副作用並重播；同 key 不同 payload 應衝突。前端 disable 按鈕不夠，timeout、重整與代理重試仍會重送。

### Transactional Outbox

在業務資料同一 transaction 寫待處理訊息，commit 後由 worker 發送，解決「DB 成功但寄信／事件失敗」的雙寫裂縫。通常仍是 at-least-once，因此 consumer 需冪等，並監控重試、人工處理與保留期。

## 結帳回答範例

> 前端只送識別碼、使用者輸入、row version 與 Idempotency-Key。後端在交易內重驗購物車、價格、優惠、運送限制、相容性與庫存，建立可信快照並保留庫存。冪等紀錄和訂單共享 transaction，所以 timeout 後同 key 重送不會再建訂單；通知等外部副作用走 Outbox。併發修改回 409 讓 client refresh，不用 silent last-write-wins。

## 高機率題

### 樂觀鎖與悲觀鎖？

衝突少時用 version 偵測的樂觀併發吞吐較好；高競爭且衝突成本高時可能需鎖或更強隔離。依衝突率、交易長度與失敗成本選。本專案多處用 `rowversion`，特定付款／匯入用 Serializable，不是一種策略套全站。

### Serializable 的代價？

可避免 phantom 等異常，但鎖範圍與時間增加，可能降低吞吐並提高 blocking/deadlock。交易要短，deadlock retry 要有清楚邊界。

### Offset 與 cursor pagination？

Offset 易懂但深頁成本高，動態資料可能重複／漏項。Cursor 用穩定排序鍵（常為時間＋唯一 ID）延續，適合大型動態清單，但不能任意跳頁；cursor 應 opaque 且排序固定。

### 正規化與反正規化？

正規化減少重複與更新異常；反正規化用儲存換讀取。訂單快照是保留成交當下價格、名稱、地址，避免主檔更新改變歷史帳務。

### 如何處理 N+1？

先由 log/profiling 看 SQL 次數，再以投影、適當 Include、batch query 或讀模型修正；用真實資料量與 execution plan 驗證。

## 情境題

「最後一件商品同時被兩人結帳」：先定義可售量不可小於零；說明 transaction 內條件更新/version 檢查、其中一方回 409/缺貨、冪等重送、保留過期與並發整合測試。不要只說 `lock`，要說鎖哪裡、多久、如何回復。
