# AI、背景工作與外部服務

## OpenAI 整合

DoSelect 透過 OpenAI Responses API 做商品意圖解析與客服輔助，但模型不是商業規則或資料庫。後端仍驗證結構化輸出，查詢核准資料，檢查預算、分類、規格、權限；服務不可用或輸出無效時，商品搜尋降級 keyword search，客服可轉人工。

- Structured output/JSON schema 提高格式可靠性，不代表內容正確。
- 把模型視為不可信決策者：工具只讀、輸入輸出驗證、權限在 API/工具層。
- 記 model、prompt version、token usage、latency、fallback reason，但不記秘密與不必要個資。
- 用固定 dataset 比較版本；live provider 驗證有預算與核准。Mock 不證明真實品質。
- Feature flag 關閉 AI 時，核心流程仍可用。

## Hangfire 與 Outbox

Hangfire 用 SQL Server storage 跑 durable jobs；設定 `critical`、`notifications`、`maintenance`、`ai` queues，排程 retention 與 SLA scan。Outbox dispatcher 把已提交業務訊息交給 consumer。

- Job 可能至少一次執行，handler 要冪等。
- retry 區分 transient/permanent，採 bounded backoff；永久資料錯誤不一直重試。
- 監控 queue starvation、stuck lease、poison message、dashboard 權限與告警。
- request 內 `Task.Run` 不 durable，process 重啟會遺失。

## Brevo SMTP 與 MailKit

Brevo 是 transactional email provider；MailKit 是後端 SMTP client。專案用 `smtp-relay.brevo.com:587`、STARTTLS、User Secrets；feature flag 關閉時用 local sender。兩者不可混為一談。

外部 provider 與 OpenAI 都可能產生費用；免費額度與價格會變，不能把測試免費說成永久零成本。啟用前應查 provider dashboard、限制、預算告警與停止條件，不在 Repository 寫死易過期價格。

- 認證失敗、明確拒收：通常 permanent，修設定/地址，不盲目 retry。
- timeout、連線、4xx：通常 transient，可有限 retry。
- SMTP accepted 不等於最終投遞；還要查 provider log、bounce/complaint、SPF/DKIM/DMARC。

## 高機率題

1. 為何寄信不能和訂單 transaction 做成同一原子操作？
2. Outbox 仍可能重複投遞，consumer 如何避免寄兩封？
3. Worker 全掛時 request 應成功或失敗？依哪個 invariant？
4. AI 回傳合法格式但不存在 SKU，如何防止？
5. 如何證明新 prompt 比舊 prompt 好？
6. Provider timeout 時能否自動重送 POST？冪等在哪裡？

## 情境題

「訂單成立但沒收到信」：確認 transaction/Outbox 是否 committed；查 correlation/trace、message 狀態、claim lease、consumer 次數、SMTP provider log；區分未派送、暫時失敗、拒收、accepted 後 bounce。人工重送要有 audit 且避免重複。
