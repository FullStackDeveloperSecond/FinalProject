# 系統設計情境題

## 回答框架

先問規模、正確性、延遲、可用性、保留與失敗容忍，再答：核心 invariant → 現有流程 → 失敗 → 最小修正 → 測試/監控 → rollback。不要一開始就丟 Redis、Kafka、微服務等名詞。

## 1. 最後一件商品被同時結帳

以資料庫 available/reserved invariant 為準；transaction 內條件更新或 `rowversion`；一方明確失敗；timeout 走 idempotency replay；做真實 SQL Server concurrency test，觀察 conflict rate。

## 2. 使用者連點兩次結帳

Disable 按鈕不夠，network retry/refresh 仍存在。Server 以 actor + operation + key + request hash 去重；同 key 不同 payload 回 409；紀錄與訂單同 transaction，並定義 retention。

## 3. 付款成功，但 API 回應前 timeout

Client 不知道結果，不應換 key 再付款；同 key 查/重播狀態；provider callback 驗簽且冪等；以 payment attempt 狀態機處理未知狀態，不只用 boolean。

## 4. 商品改名或漲價後查舊訂單

訂單保留成交快照；主檔可更新但不回寫歷史金額、名稱、地址。這是為帳務與稽核刻意反正規化。

## 5. 兩位管理員同時編輯商品

讀取帶 `rowversion`，更新 compare；第二位收到 409 並 reload/merge，不採 silent last-write-wins；記 audit actor 與 correlation。

## 6. AI provider 全面故障

Feature/admission gate、短 timeout、有限 retry、budget protection；商品搜尋降級 keyword，客服轉人工。AI 是否影響全站 readiness 取決於是否核心依賴，並告警 fallback rate。

## 7. 背景工作重複執行

假設 at-least-once；以 message/operation 唯一鍵、狀態機或 conditional update；副作用前後可恢復；retry 有上限，永久失敗進人工處理並保留 audit。

## 8. 跨來源前端突然全部 400/401

先查 browser preflight、Cookie、SameSite/Secure、CORS response、Antiforgery code、correlation；確認 deploy 是否改 origin/scheme；不以 `AllowAnyOrigin` 或關掉 CSRF 當永久修復。

## 9. 商品列表變慢

定義 p95 與資料量；從 trace、SQL 次數、execution plan、logical reads 找瓶頸；查 N+1、投影、索引、分頁、payload；量測後才加 cache。Cache 要定 key、TTL、invalidation、stale tolerance。

## 10. 要拆成微服務

先問業務/營運痛點。若只是檔案多，模組邊界可能已足夠；拆分會增加網路失敗、資料一致性、observability、deployment、on-call 成本。只有獨立擴展、故障隔離或團隊自治有證據時，才從資料所有權清楚的邊界漸進拆出。

## 加壓追問

- 「資料庫也掛了？」說 readiness、停止接單、恢復與 reconciliation。
- 「不能加新服務？」回到 DB constraint、existing queue 與程序控制的最低成本方案。
- 「怎麼知道修好？」提出重現測試、指標、log、負向案例。
- 「代價？」說 latency、吞吐、複雜度、營運與回復成本。
- 「你本人做過？」誠實區分親自執行、共同決策與讀碼理解。
