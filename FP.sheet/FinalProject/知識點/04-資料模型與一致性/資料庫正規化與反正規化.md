# 資料庫正規化與反正規化

## 簡單理解

正規化是把資料拆到每個事實只有一個主要保存位置，透過主鍵與外鍵組合使用。目標不是「表越多越好」，而是避免同一資訊在不同地方互相矛盾。

反正規化是在有明確目的時刻意保存可由其他資料取得的副本，例如交易快照、庫存即時餘額或報表彙總。它用更多儲存與同步成本，換取歷史正確性或讀取效能。

## 常見異常

假設商品表的每一列都重複品牌電話：

- 更新異常：品牌換電話時要修改大量商品，漏一筆就不一致。
- 插入異常：還沒有商品時，無法單獨建立品牌資料。
- 刪除異常：刪掉該品牌最後一個商品時，品牌資訊也一起消失。

把品牌拆成 `Brands`，商品只保存 `BrandId`，即可讓品牌成為唯一真實來源。

## 1NF、2NF、3NF

- 第一正規化（1NF）：每個欄位保存單一值，不用一格保存多個角色、標籤或明細。
- 第二正規化（2NF）：非鍵欄位依賴完整主鍵，特別注意複合鍵的 Join／明細表。
- 第三正規化（3NF）：非鍵欄位不再依賴其他非鍵欄位，例如商品不重複保存可由 `BrandId` 找到的目前品牌名稱。

本專案以 3NF 作為交易寫入模型的審核基線，不要求為了理論形式拆出沒有商業意義的小表。

## 電商為何仍需要反正規化

訂單成立後，即使商品改名、會員改地址或優惠規則改變，歷史交易仍要顯示當時內容。因此 `OrderItem` 保存商品名稱、SKU、單價、成本與折扣快照不是壞設計，而是交易事實。

庫存結帳需要快速判斷可售數量，因此保存 `InventoryBalance` 也合理；但每次異動仍要有 `InventoryMovement`，並能核對餘額。

## 判斷問題

遇到想重複保存資料時，先問：

1. 這是目前主資料、歷史快照、衍生餘額、唯讀投影，還是報表快取？
2. 哪裡是唯一可寫真實來源？
3. 副本何時更新，允許延遲多久？
4. 更新失敗或事件重複時怎麼辦？
5. 能不能從真實來源重建？
6. 如何測試兩邊沒有漂移？

答不出來時，不應先增加副本。

## 本專案例子

| 設計 | 分類 |
|---|---|
| Brand、Product、SKU 分表 | 正規化主資料 |
| OrderItem 名稱／價格／成本 | 交易快照 |
| InventoryBalance | 衍生餘額 |
| InventoryMovement | 不可覆寫異動來源 |
| 三案件統一工作台 | 唯讀投影 |
| ReportSnapshot | 尚未核准的報表反正規化候選 |
